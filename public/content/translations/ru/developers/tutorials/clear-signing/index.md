Большинство крупных эксплойтов в Эфириуме имели один и тот же финальный шаг: пользователь одобрял транзакцию, которую не мог осмысленно понять. Аппаратные кошельки показывают необработанные шестнадцатеричные данные вызова (calldata) и, что еще хуже, заставляют вас включать слепое подписание. Программные кошельки показывают декодированные поля, но только тогда, когда они распознают контракт. Когда они этого не делают — будь то из-за того, что протокол новый, приложение скомпрометировано или устройство не в сети, — пользователи подписывают вслепую.

[ERC-7730](https://eips.ethereum.org/EIPS/eip-7730) определяет стандартный формат JSON для описания того, что *означают* вызовы функций вашего контракта.

Кошелек, поддерживающий ERC-7730, читает ваш дескриптор и показывает:

> **Своп**  
> Отправить: 1,000 USDC  
> Получить минимум: 0.42 WETH  
> Протокол: Uniswap V2

Или одно составленное предложение, понятное как людям, так и агентам:

> Обменять 1,000 USDC как минимум на 0.42 WETH

Вместо селектора функции и списка необработанных целочисленных значений.

Это [понятное подписание (clear signing)](https://clearsigning.org/) — «Что вы видите, то и подписываете». В этом руководстве рассказывается, как написать дескриптор для вашего собственного контракта, проверить его с помощью официального инструмента CLI и отправить в открытый реестр.

## Предварительные требования {#prerequisites}

- Знакомство с Solidity и ABI смарт-контрактов
- Развернутый смарт-контракт с верифицированным ABI (верификация в [Sourcify](https://sourcify.dev) обязательна до того, как дескриптор будет принят в реестр)
- Python 3.12 для CLI-инструмента валидации (закрепленный пакет `erc7730` не устанавливается на Python 3.13 или новее). Если в вашей системе установлена другая версия Python, [uv](https://docs.astral.sh/uv/) может скачать и запустить Python 3.12 для вас
- Базовые знания JSON

## Что такое дескриптор ERC-7730? {#what-is-an-erc-7730-descriptor}

Дескриптор — это один JSON-файл, состоящий из трех разделов:

| Раздел | Назначение |
| :---- | :---- |
| `context` | Привязывает дескриптор к конкретным развертываниям контракта по ID цепи и адресу |
| `metadata` | Задает имя проекта и определяет переиспользуемые константы |
| `display` | Сопоставляет каждую сигнатуру функции с понятными человеку метками и форматами полей |

Поскольку дескриптор отделен от самого контракта, вы можете добавить поддержку понятного подписания в любой существующий протокол без повторного развертывания. Кошельки извлекают дескрипторы из реестра и используют их во время подписания.

## Шаг 1: Создайте каркас файла {#step-1-create-the-file-skeleton}

Создайте файл с именем `calldata-<ContractName>.json`, например `calldata-SwapRouter.json`. Префикс `calldata-` сообщает реестру, что этот дескриптор охватывает вызовы функций контракта, в отличие от `eip712-` для сообщений с типизированными данными. Если вам нужно описать несколько версий контракта, включите версию контракта в имя, как в `calldata-UniswapV3Router02.json` реестра.

```json
{
  "$schema": "https://eips.ethereum.org/assets/eip-7730/erc7730-v2.schema.json",
  "context": {},
  "metadata": {},
  "display": {
    "formats": {}
  }
}
```

## Шаг 2: Напишите раздел контекста {#step-2-write-the-context-section}

Раздел `context` привязывает дескриптор к одному или нескольким развертываниям контракта. Кошельки используют это для сопоставления входящей транзакции с правильным дескриптором.

```json
"context": {
  "$id": "example-swap-router",
  "contract": {
    "deployments": [
      { "chainId": 1, "address": "0xYourContractAddressOnMainnet" },
      { "chainId": 137, "address": "0xYourContractAddressOnPolygon" }
    ]
  }
}
```

### Поля контекста {#context-fields}

- `context.$id` — Уникальный идентификатор для этого документа дескриптора или конфигурации развертывания.
- `contract.deployments` — Набор развертываний, к которым применяется этот дескриптор.
- `deployments[].chainId` — ID цепи EVM для развертывания. Включите каждую цепь, в которой развернут ваш контракт.
- `deployments[].address` — Адрес контракта, который кошельки должны ассоциировать с этим дескриптором. Это адрес, на который пользователи фактически отправляют транзакции. Если ваш контракт обновляемый, это адрес прокси, а не адрес реализации, в то время как сигнатуры функций в `display.formats` берутся из ABI реализации.

## Шаг 3: Напишите раздел метаданных {#step-3-write-the-metadata-section}

Раздел метаданных предоставляет понятную человеку информацию о проекте и контракте, описываемых этим файлом. Кошельки могут использовать эту информацию для отображения названий протоколов, ссылок и других контекстных деталей во время подписания.

```json
"metadata": {
  "owner": "Example Swap Protocol",
  "info": { "url": "https://example.xyz" },
  "contractName": "SwapRouter"
}
```

### Поля метаданных {#metadata-fields}

- `owner` — Проект, протокол, организация или мейнтейнер, ответственные за этот дескриптор.
- `info.url` — Канонический URL-адрес проекта или документации, который кошельки могут отображать пользователям для дополнительного контекста.
- `contractName` — Имя контракта или реализации, описываемое этим файлом, обычно совпадающее с верифицированным исходным кодом или ABI.

Если ваш файл ERC-7730 описывает контракт ERC-20, вам также следует добавить объект токена. 

## Шаг 4: Напишите раздел форматов отображения {#step-4-write-the-displayformats-section}

Объект `display.formats` сопоставляет сигнатуры функций с понятными человеку инструкциями по подписанию. Именно так кошельки показывают вашу функцию пользователям перед тем, как они одобрят транзакцию!

Каждый ключ — это понятный человеку фрагмент ABI: сигнатура функции, включающая как имена параметров, так и их типы в точности так, как они указаны в вашем ABI.


### Пример: Описание свопа токенов {#eg-describing-token-swap}

Этот пример описывает `swapExactTokensForTokens` из контракта Uniswap V2 `Router02`. Входной токен — это первый элемент `path`, а выходной токен — последний (`path` может иметь более двух элементов для многошагового свопа).

```json
"display": {
  "formats": {
    "swapExactTokensForTokens(uint256 amountIn,uint256 amountOutMin,address[] path,address to,uint256 deadline)": {
      "intent": "Swap",
      "interpolatedIntent": "Swap {amountIn} for at least {amountOutMin}",
      "fields": [
        {
          "path": "#.amountIn",
          "label": "Send",
          "format": "tokenAmount",
          "params": {
            "tokenPath": "#.path.[0]"
          }
        },
        {
          "path": "#.amountOutMin",
          "label": "Receive minimum",
          "format": "tokenAmount",
          "params": {
            "tokenPath": "#.path.[-1]"
          }
        },
        {
          "path": "#.to",
          "label": "Recipient",
          "format": "addressName",
          "params": {
            "types": ["eoa", "contract"],
            "sources": ["local", "ens"]
          }
        },
        {
          "path": "#.deadline",
          "label": "Expires",
          "format": "date",
          "params": {
            "encoding": "timestamp"
          }
        }
      ]
    }
  }
}
```

### Поля отображения {#display-fields}

- **`intent`** — **(Обязательно)** Краткое, понятное пользователю описание действия, например «Своп».
- **`interpolatedIntent`** — **(Рекомендуется)** Более развернутый шаблон предложения, который встраивает отформатированные значения полей, например `"Swap {amountIn} for at least {amountOutMin}"`. Включите это вместе с `intent`, чтобы предоставить еще более удобный для пользователя дескриптор, который кошельки могут выбрать для показа с учетом любых ограничений отображения.
- **`fields`** — **(Обязательно)** Упорядоченный список полей транзакции, которые кошельки должны отображать пользователям.
  - **`path`** — **(Обязательно)** Ссылка на данные транзакции. `#.fieldName` указывает на декодированный параметр данных вызова по имени в ABI. `@.value` относится к значению ETH, отправленному с транзакцией. Элементы массива записываются с `.` перед скобками: `#.path.[0]` — это первый элемент, а `#.path.[-1]` — последний. `#.path[0]` (без точки) отклоняется линтером.
  - **`label`** — **(Обязательно)** Понятная человеку метка, отображаемая рядом со значением.
  - **`format`** — **(Рекомендуется)** Управляет тем, как должно отображаться значение. Общие форматы включают:
    - `tokenAmount`
    - `addressName`
    - `date`

    Используйте `raw`, когда дополнительное форматирование не требуется. Некоторые форматы принимают дополнительную конфигурацию **`params`**. Например:

    - `tokenAmount` может использовать `tokenPath` для определения того, какой адрес токена предоставляет метаданные о десятичных знаках и тикере.
    - `date` может использовать `encoding` для описания того, как закодирована временная метка.

    Если выбранный формат не требует дополнительной информации, опустите `params`.

## Шаг 5: Отправьте в реестр {#step-5-submit-to-the-registry}

[Реестр ERC-7730](https://github.com/ethereum/clear-signing-erc7730-registry) — это открытый репозиторий, размещенный [Фондом Ethereum](/foundation/) в качестве нейтрального управляющего. Любой желающий может клонировать его и разместить у себя — кошельки самостоятельно решают, каким экземплярам реестра они доверяют.

1. Сделайте форк репозитория на GitHub
2. Создайте папку в `registry/<your-project-name>/`
3. Поместите ваш файл внутрь нее: `registry/myproject/calldata-SwapRouter.json`
4. Обновите поле `$schema` на относительный путь, используемый внутри репозитория: `"../../specs/erc7730-v2.schema.json"`. CI отклонит URL-адрес в этом месте.
5. Добавьте тестовый файл (см. ниже)
6. Проверьте ваши файлы локально (см. ниже)
7. Откройте pull request. Каждый pull request может изменять только одну папку в `registry/`

### Добавьте тестовый файл {#add-a-test-file}

Каждому добавляемому или изменяемому дескриптору нужен тестовый файл, чтобы реализации понятного подписания могли быть проверены на его основе. Создайте `registry/<your-project-name>/testsv2/calldata-<ContractName>.tests.json` как минимум с одним тестовым случаем для каждой функции в `display.formats`. CI вычисляет селектор функции каждого формата и завершается с ошибкой, если ни одна тестовая транзакция его не вызывает.

```json
{
  "$schema": "../../../specs/erc7730-tests-v2.schema.json",
  "descriptor": "../calldata-SwapRouter.json",
  "dataProvider": {
    "tokens": {
      "0xa0b86991c6218b36c1d19d4a2e9eb0ce3606eb48": { "symbol": "USDC", "decimals": 6, "name": "USD Coin" },
      "0xc02aaa39b223fe8d0a0e5c4f27ead9083c756cc2": { "symbol": "WETH", "decimals": 18, "name": "Wrapped Ether" }
    }
  },
  "tests": [
    {
      "description": "Swap 1,000 USDC for at least 0.42 WETH",
      "rawTx": "0x02f9012f0180843b9aca00...",
      "expected": {
        "intent": "Swap",
        "interpolatedIntent": "Swap 1000 USDC for at least 0.42 WETH",
        "owner": "Example Swap Protocol",
        "fields": [
          { "label": "Send", "value": "1000 USDC" },
          { "label": "Receive minimum", "value": "0.42 WETH" },
          { "label": "Recipient", "value": "0x1234567890123456789012345678901234567890" },
          { "label": "Expires", "value": "2026-01-01 00:00:00Z" }
        ]
      }
    }
  ]
}
```

- `rawTx` — это полная сериализованная **неподписанная** транзакция (здесь сокращена), а не только данные вызова. Реальные транзакции к вашему контракту — лучшие тестовые случаи.
- `dataProvider` предоставляет метаданные токена (и, при необходимости, адреса и имена ENS), чтобы тестам не требовался доступ к сети.
- `expected` — это то, что должен отображать кошелек. CI рендерит каждый тестовый случай с реализациями понятного подписания и сообщает о любых различиях в pull request.

Смотрите [Эталонные тестовые случаи (Reference test cases)](https://github.com/ethereum/clear-signing-erc7730-registry#reference-test-cases) в README реестра для получения полного формата, включая тестовые файлы для дескрипторов EIP-712.

### Проверьте локально {#validate-locally}

Реестр проверяет дескрипторы с помощью инструмента командной строки [`erc7730`](https://github.com/sourcifyeth/python-erc7730), закрепленного в `.github/requirements.txt`. Запустите его из корня вашего форка в среде Python 3.12:

```sh
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r .github/requirements.txt
erc7730 lint registry/myproject/calldata-SwapRouter.json
```

Если вы используете [uv](https://docs.astral.sh/uv/), вы можете пропустить виртуальную среду, и uv скачает Python 3.12 при необходимости:

```sh
uvx --python 3.12 --from "$(cat .github/requirements.txt)" erc7730 lint registry/myproject/calldata-SwapRouter.json
```

Линтер проверяет дескриптор на соответствие схеме и верифицированному ABI вашего контракта. Исправьте каждую ошибку. Предупреждения, такие как `Missing display format`, означают, что в контракте есть функции, которые ваш дескриптор еще не описывает. Чтобы также проверить пути `$schema` и тестовый файл так, как это делает CI, смотрите [Как валидировать (How to validate)](https://github.com/ethereum/clear-signing-erc7730-registry#how-to-validate) в README реестра.

Когда вы открываете PR, CI автоматически запускает валидацию схемы, проверяет, что сигнатуры функций создают действительные селекторы, подтверждает, что адрес контракта верифицирован в Sourcify, и отмечает несоответствия ABI. Результаты проверки появляются прямо в PR. Мейнтейнеры реестра проверяют отправленные данные на наличие неправильно сформированных или потенциально вредоносных дескрипторов. Включение в реестр не означает аудит или одобрение.

## Что происходит после слияния? {#what-happens-after-merging}

Все дескрипторы в реестре открыты для аудиторов. После слияния вашего PR любой аудитор может проверить ваш дескриптор и опубликовать криптографическую аттестацию (в рамках [ERC-8176](https://eips.ethereum.org/EIPS/eip-8176)), подтверждающую его точность. 

Эти сигналы аттестации позволяют кошелькам применять свои собственные политики доверия — дескриптор с несколькими независимыми аттестациями имеет больший вес, чем дескриптор без них. Вы можете связаться с сообществом аудиторов через [clearsigning.org](https://clearsigning.org).

Кошельки сами выбирают, какой реестр они будут поддерживать. Как только ваш дескриптор окажется в реестре, кошельки, поддерживающие ERC-7730, начнут извлекать его, если он есть в их реестре, и будут отображать понятные человеку данные, когда пользователи взаимодействуют с вашим контрактом.
