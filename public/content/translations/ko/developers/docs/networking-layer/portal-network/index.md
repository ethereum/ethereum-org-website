[이더리움](/)은 이더리움 클라이언트 소프트웨어를 실행하는 컴퓨터들로 구성된 네트워크입니다. 이러한 각각의 컴퓨터를 '노드'라고 부릅니다. 클라이언트 소프트웨어를 통해 노드는 이더리움 네트워크에서 데이터를 송수신할 수 있으며, 이더리움 프로토콜 규칙에 따라 데이터를 검증합니다. 노드는 디스크 저장소에 많은 과거 데이터를 보관하며, 네트워크의 다른 노드로부터 블록이라고 알려진 새로운 정보 패킷을 수신할 때 이를 추가합니다. 이는 노드가 네트워크의 나머지 부분과 일치하는 정보를 가지고 있는지 항상 확인하기 위해 필요합니다. 즉, 노드를 실행하려면 많은 디스크 공간이 필요할 수 있습니다. 일부 노드 작업은 많은 RAM을 요구하기도 합니다.

실행 클라이언트는 더 이상 이 모든 데이터를 보관할 필요가 없습니다. 2025년 7월부터 실행 클라이언트는 [머지](/roadmap/merge/) 이전 블록의 본문과 영수증을 삭제할 수 있으며, 이더리움 로드맵에는 시간이 지남에 따라 체인의 기록을 더 많이 삭제하는 내용이 포함되어 있습니다. 하지만 블록 탐색기, 인덱서, 또는 오래된 트랜잭션을 조회하는 지갑 등 이를 필요로 하는 누구나 해당 기록을 계속 사용할 수 있어야 합니다.

포털 네트워크는 이 기록을 작은 조각으로 나누어 여러 노드에 공유함으로써 계속 사용할 수 있도록 유지합니다. 어떤 노드도 모든 기록을 저장할 필요가 없으며, 노드는 데이터를 보낸 노드를 신뢰하지 않고도 어떤 조각이든 가져와 자신이 이미 보유한 데이터와 대조하여 확인할 수 있습니다.

## 포털 네트워크가 필요한 이유 {#why-do-we-need-portal-network}

이더리움 노드는 이더리움 블록체인의 전체 또는 부분 사본을 자체적으로 저장합니다. 이 로컬 사본은 트랜잭션을 검증하고 노드가 올바른 체인을 따르고 있는지 확인하는 데 사용됩니다. 노드는 이렇게 로컬에 저장된 데이터를 통해 다른 주체를 신뢰할 필요 없이 수신되는 데이터가 유효하고 올바른지 독립적으로 검증할 수 있습니다.

이러한 블록체인의 로컬 사본과 관련 상태 및 영수증 데이터는 노드의 하드 디스크에서 많은 공간을 차지합니다. 예를 들어, 합의 클라이언트와 쌍을 이루는 [Geth](https://geth.ethereum.org)를 사용하여 노드를 실행하려면 4TB SSD가 권장됩니다. 전체 체인 기록을 포함할 경우 Geth는 1.8TB 이상의 디스크 공간을 차지하며(2026년 9월 기준), 이는 체인과 함께 계속 증가합니다.

이는 이더리움에 많은 디스크 공간을 할당해야 하므로 노드 실행 비용이 많이 들 수 있음을 의미합니다. [기록 만료](/roadmap/statelessness/#history-expiry)는 클라이언트가 체인을 따르는 데 필요하지 않은 오래된 블록 데이터를 삭제할 수 있게 하여 이 문제를 줄여줍니다. 2025년 7월 [부분 기록 만료](https://blog.ethereum.org/2025/07/08/partial-history-exp) 이후, 실행 클라이언트는 머지 이전의 모든 블록 본문과 영수증을 삭제할 수 있습니다. [상태 만료](/roadmap/statelessness/#state-expiry)와 [무상태성](/roadmap/statelessness/)은 현재 계속 연구 중인 추가적인 해결책입니다.

노드가 오래된 기록 저장을 중단하면 더 이상 다른 노드에 이를 제공할 수 없습니다. 아카이브, 토렌트, 그리고 제공업체들이 그 사본을 보관하지만, 포털 네트워크는 이를 여러 노드에 분산시켜 특정 노드에 의존하지 않고도 계속 사용할 수 있게 합니다.

## 포털 네트워크는 어떻게 작동하나요? {#how-does-portal-network-work}

이더리움 노드에는 서로 통신하는 방법을 정의하는 엄격한 프로토콜이 있습니다. 실행 클라이언트는 [devp2p](/developers/docs/networking-layer/#devp2p)로 알려진 하위 프로토콜 세트를 사용하여 통신하는 반면, 합의 클라이언트는 [libp2p](/developers/docs/networking-layer/#libp2p)라는 다른 하위 프로토콜 스택을 사용합니다. devp2p를 통해 노드는 피어에게 블록 본문과 영수증을 요청할 수 있지만, 오래된 기록을 삭제한 피어는 이를 제공할 수 없습니다. 앱과 지갑은 [JSON-RPC API](/developers/docs/apis/json-rpc/)를 통해 노드에서 데이터를 가져올 수도 있지만, 이는 데이터를 저장하는 단일 노드나 제공업체에 의존하며 그들이 정직할 것이라고 신뢰해야 합니다.

포털 네트워크는 기록 공유를 위해 구축된 별도의 피어 투 피어 네트워크입니다. 합의 클라이언트가 피어를 찾을 때도 사용하는 노드 디스커버리 프로토콜인 [discv5](https://github.com/ethereum/devp2p/blob/master/discv5/discv5.md)에서 실행되며, 비트토렌트(BitTorrent)와 유사하게 노드를 [분산 해시 테이블(DHT)](https://en.wikipedia.org/wiki/Distributed_hash_table)로 구성합니다. 모든 노드는 노드 ID를 가지며, 특정 블록의 영수증과 같은 모든 콘텐츠 조각은 블록 번호에서 파생된 동일한 ID 공간 내의 콘텐츠 ID를 가집니다. 각 노드는 자신의 ID와 가장 가까운 ID를 가진 콘텐츠를 자신이 선택한 거리(반경이라고 함)까지 저장합니다. 콘텐츠 조각을 가져오기 위해 노드는 자신이 알고 있는 피어 중 콘텐츠 ID에 가장 가까운 피어에게 요청합니다. 해당 콘텐츠가 없는 피어는 더 가까운 노드로 응답하며, 요청이 콘텐츠를 저장하고 있는 노드에 도달할 때까지 이 과정이 반복됩니다.

노드는 수신한 데이터를 신뢰할 필요가 전혀 없습니다. 노드는 모든 블록 헤더를 보관하며, 각 헤더는 `transactionsRoot` 및 `receiptsRoot`와 같은 루트를 통해 해당 블록의 트랜잭션과 영수증을 커밋합니다. 노드는 블록 본문이나 블록의 영수증을 사용하기 전에 이러한 루트와 대조하여 확인합니다.

### 포털 네트워크 {#the-portal-networks}

포털 네트워크는 처음에는 경량 클라이언트가 풀 노드를 신뢰하지 않고도 체인을 따를 수 있도록 하는 여러 하위 네트워크(비콘 체인 경량 클라이언트 네트워크, 상태 네트워크, 트랜잭션 가십 네트워크, 기록 네트워크)로 설계되었습니다. 2025년에 이 중 하나를 제외한 모든 사양이 레거시로 이동되었으며, 현재 개발은 모든 블록 헤더는 보관하지만 나머지 기록은 삭제한 실행 클라이언트를 위해 과거 블록의 본문과 영수증을 저장하는 <strong>기록 네트워크(History network)</strong>에 집중되어 있습니다.

## 포털 네트워크 클라이언트 {#client-diversity-as-default}

여러 팀에서 포털 네트워크 클라이언트를 구축했습니다:

- [님버스(Nimbus) 포털 클라이언트](https://fluffy.guide) (이전 명칭 Fluffy): Nim으로 작성되었으며, 현재 유일하게 활발히 개발 중입니다.
- [Trin](https://github.com/ethereum/trin): Rust로 작성되었으며, 더 이상 유지보수되지 않습니다.
- [Ultralight](https://github.com/ethereumjs/ultralight): TypeScript로 작성되었으며, 2025년 중반 이후 업데이트가 없습니다.
- [Shisui](https://github.com/zen-eth/shisui): Go로 작성되었으며, 2025년 중반 이후 업데이트가 없습니다.
