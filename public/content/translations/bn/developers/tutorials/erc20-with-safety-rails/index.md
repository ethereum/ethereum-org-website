## ভূমিকা {#introduction}

ইথেরিয়াম এর অন্যতম সেরা দিক হলো এখানে এমন কোনো কেন্দ্রীয় কর্তৃপক্ষ নেই যা আপনার ট্রানজ্যাকশনগুলো পরিবর্তন বা বাতিল করতে পারে। ইথেরিয়াম এর অন্যতম বড় সমস্যা হলো এখানে এমন কোনো কেন্দ্রীয় কর্তৃপক্ষ নেই যার ব্যবহারকারীর ভুল বা অবৈধ ট্রানজ্যাকশনগুলো বাতিল করার ক্ষমতা রয়েছে। এই নিবন্ধে আপনি [ERC-20](/developers/docs/standards/tokens/erc-20/) টোকেনগুলোর সাথে ব্যবহারকারীরা যে সাধারণ ভুলগুলো করে সে সম্পর্কে জানবেন, পাশাপাশি কীভাবে এমন ERC-20 কন্ট্রাক্ট তৈরি করতে হয় যা ব্যবহারকারীদের সেই ভুলগুলো এড়াতে সাহায্য করে, বা যা কোনো কেন্দ্রীয় কর্তৃপক্ষকে কিছু ক্ষমতা দেয় (উদাহরণস্বরূপ অ্যাকাউন্টগুলো ফ্রিজ করার জন্য)।

মনে রাখবেন যে যদিও আমরা [OpenZeppelin ERC-20 টোকেন কন্ট্রাক্ট](https://github.com/OpenZeppelin/openzeppelin-contracts/tree/master/contracts/token/ERC20) ব্যবহার করব, এই নিবন্ধটি এটি বিস্তারিতভাবে ব্যাখ্যা করে না। আপনি এই তথ্য [এখানে](/developers/tutorials/erc20-annotated-code) পেতে পারেন।

আপনি যদি সম্পূর্ণ সোর্স কোড দেখতে চান:

1. [Remix IDE](https://remix.ethereum.org/) খুলুন।
2. ক্লোন GitHub আইকনে ক্লিক করুন (![clone github icon](icon-clone.png))।
3. GitHub রিপোজিটরি `https://github.com/qbzzt/20220815-erc20-safety-rails` ক্লোন করুন।
4. **contracts > erc20-safety-rails.sol** খুলুন।

মনে রাখবেন যে রিপোজিটরিটি OpenZeppelin Contracts 4.7.2 এর জন্য লেখা হয়েছিল, যেখানে এই নিবন্ধটি যে ফাংশনটিকে ওভাররাইড করে তাকে `_beforeTokenTransfer` বলা হয়। এই নিবন্ধটি বর্তমান OpenZeppelin Contracts 5.x ব্যবহার করে, যেখানে আপনি এর পরিবর্তে `_update` ওভাররাইড করেন, তাই এই নিবন্ধের কোডটি রিপোজিটরির কোড থেকে কিছুটা আলাদা।

## একটি ERC-20 কন্ট্রাক্ট তৈরি করা {#creating-an-erc-20-contract}

সেফটি রেল কার্যকারিতা যোগ করার আগে আমাদের একটি ERC-20 কন্ট্রাক্ট প্রয়োজন। এই নিবন্ধে আমরা [OpenZeppelin Contracts Wizard](https://docs.openzeppelin.com/contracts/5.x/wizard) ব্যবহার করব। এটি অন্য একটি ব্রাউজারে খুলুন এবং এই নির্দেশাবলী অনুসরণ করুন:

1. **ERC20** নির্বাচন করুন।
2. এই সেটিংসগুলো লিখুন:

   | প্যারামিটার | মান |
   | -------------- | ------------------------- |
   | Name | SafetyRailsToken |
   | Symbol | SAFE |
   | Premint | 1000 |
   | Features | None (**Permit** আনচেক করুন) |
   | Access Control | Ownable |
   | Upgradability | None |

3. উপরে স্ক্রোল করুন এবং **Open in Remix** (Remix এর জন্য) বা অন্য কোনো পরিবেশ ব্যবহার করতে **Download** এ ক্লিক করুন। আমি ধরে নিচ্ছি আপনি Remix ব্যবহার করছেন, যদি আপনি অন্য কিছু ব্যবহার করেন তবে শুধু উপযুক্ত পরিবর্তনগুলো করুন।
4. আমাদের কাছে এখন একটি সম্পূর্ণ কার্যকরী ERC-20 কন্ট্রাক্ট রয়েছে। ইমপোর্ট করা কোড দেখতে আপনি `.deps` > `npm` প্রসারিত করতে পারেন।
5. এটি একটি ERC-20 কন্ট্রাক্ট হিসেবে কাজ করে কিনা তা দেখতে কন্ট্রাক্টটি কম্পাইল করুন, ডিপ্লয় করুন এবং এর সাথে কাজ করুন। আপনার যদি Remix কীভাবে ব্যবহার করতে হয় তা শেখার প্রয়োজন হয়, তবে [এই টিউটোরিয়ালটি ব্যবহার করুন](https://remix.ethereum.org/?#activate=udapp,solidity,LearnEth)।

## সাধারণ ভুলগুলো {#common-mistakes}

### ভুলগুলো {#the-mistakes}

ব্যবহারকারীরা মাঝে মাঝে ভুল ঠিকানায় টোকেন পাঠায়। যদিও তারা কী করতে চেয়েছিল তা জানার জন্য আমরা তাদের মন পড়তে পারি না, তবে দুটি ধরনের ত্রুটি রয়েছে যা প্রচুর ঘটে এবং সহজেই শনাক্ত করা যায়:

1. কন্ট্রাক্ট এর নিজস্ব ঠিকানায় টোকেন পাঠানো। উদাহরণস্বরূপ, [অপটিমিজম এর OP টোকেন](https://optimism.mirror.xyz/qvd0WfuLKnePm1Gxb9dpGchPf5uDz5NSMEFdgirDS4c) দুই মাসেরও কম সময়ে [120,000 এর বেশি](https://optimism.blockscout.com/address/0x4200000000000000000000000000000000000042) OP টোকেন জমা করতে সক্ষম হয়েছিল। এটি একটি উল্লেখযোগ্য পরিমাণ সম্পদের প্রতিনিধিত্ব করে যা সম্ভবত মানুষ হারিয়েছে।

2. একটি খালি ঠিকানায় টোকেন পাঠানো, যা কোনো [এক্সটার্নালি ওনড অ্যাকাউন্ট (EOA)](/developers/docs/accounts/#externally-owned-accounts-and-key-pairs) বা [স্মার্ট কন্ট্রাক্ট](/developers/docs/smart-contracts) এর সাথে মিলে না। যদিও এটি কত ঘন ঘন ঘটে তার কোনো পরিসংখ্যান আমার কাছে নেই, তবে [একটি ঘটনায় 20,000,000 টোকেন খরচ হতে পারত](https://gov.optimism.io/t/message-to-optimism-community-from-wintermute/2595)।

### হস্তান্তর প্রতিরোধ করা {#preventing-transfers}

OpenZeppelin ERC-20 কন্ট্রাক্ট এ ব্যালেন্সের প্রতিটি পরিবর্তন, তা হস্তান্তর, মিন্ট বা পোড়ানো যাই হোক না কেন, [একটি অভ্যন্তরীণ ফাংশন, `_update`](https://docs.openzeppelin.com/contracts/5.x/api/token/erc20#ERC20-_update-address-address-uint256-) এর মাধ্যমে যায়। আমরা এর উপর আমাদের নিজস্ব কার্যকারিতা যুক্ত করতে এটিকে ওভাররাইড করতে পারি, যেমন কোনো সমস্যা থাকলে রিভার্ট করার জন্য চেক করা।

এটি করার জন্য, কনস্ট্রাক্টর এর পরে এই ফাংশনটি যোগ করুন:

```solidity
    function _update(address from, address to, uint256 value)
        internal virtual
        override(ERC20)
    {
        super._update(from, to, value);
    }
```

আপনি যদি Solidity এর সাথে খুব বেশি পরিচিত না হন তবে এই ফাংশনের কিছু অংশ নতুন হতে পারে:

```solidity
        internal virtual
```

`virtual` কীওয়ার্ডটির অর্থ হলো ঠিক যেমন আমরা `ERC20` থেকে কার্যকারিতা ইনহেরিট করেছি এবং এই ফাংশনটিকে ওভাররাইড করেছি, অন্যান্য কন্ট্রাক্টগুলোও আমাদের থেকে ইনহেরিট করতে পারে এবং এই ফাংশনটিকে ওভাররাইড করতে পারে।

```solidity
        override(ERC20)
```

আমাদের স্পষ্টভাবে উল্লেখ করতে হবে যে আমরা `_update` এর ERC20 টোকেন সংজ্ঞাকে [ওভাররাইড](https://docs.soliditylang.org/en/latest/contracts.html#function-overriding) করছি। সাধারণভাবে, নিরাপত্তার দৃষ্টিকোণ থেকে, অন্তর্নিহিত সংজ্ঞাগুলোর চেয়ে স্পষ্ট সংজ্ঞাগুলো অনেক ভালো - আপনি যদি কোনো কিছু আপনার চোখের সামনে থাকে তবে আপনি ভুলে যেতে পারবেন না যে আপনি কিছু করেছেন। এটিও একটি কারণ যে আমাদের উল্লেখ করতে হবে আমরা কোন সুপারক্লাসের `_update` ওভাররাইড করছি।

```solidity
        super._update(from, to, value);
```

এই লাইনটি সেই কন্ট্রাক্ট বা কন্ট্রাক্টগুলোর `_update` ফাংশনকে কল করে যেখান থেকে আমরা ইনহেরিট করেছি এবং যেগুলোতে এটি রয়েছে। এই ক্ষেত্রে, এটি শুধুমাত্র `ERC20`, `Ownable` এ এই ফাংশনটি নেই। একটি খালি হুকের বিপরীতে, `ERC20._update` হলো যা আসলে টোকেনগুলোকে সরিয়ে নেয়, তাই এটিকে কল করা অপরিহার্য। আমাদের চেকগুলো এই কলের আগে যায়, যাতে কোনো ব্যালেন্স পরিবর্তনের আগে সেগুলো রিভার্ট করতে পারে।

### প্রয়োজনীয়তাগুলো কোডিং করা {#coding-the-requirements}

আমরা ফাংশনে এই প্রয়োজনীয়তাগুলো যোগ করতে চাই। যেহেতু টোকেনগুলো পোড়ানোর সময়ও `_update` কল করা হয়, যেখানে `to` কে `address(0)` এ সেট করা হয়, তাই আমরা শুধুমাত্র তখনই `to` চেক করি যখন এটি `address(0)` না হয়:

- `to` ঠিকানাটি `address(this)` এর সমান হতে পারে না, যা ERC-20 কন্ট্রাক্ট এর নিজস্ব ঠিকানা।
- `to` ঠিকানাটি খালি হতে পারে না, এটি হতে হবে হয়:
  - একটি বাহ্যিকভাবে মালিকানাধীন অ্যাকাউন্ট (EOA)। আমরা সরাসরি কোনো ঠিকানা EOA কিনা তা চেক করতে পারি না, তবে আমরা একটি ঠিকানার ETH ব্যালেন্স চেক করতে পারি। EOA গুলোর প্রায় সবসময়ই একটি ব্যালেন্স থাকে, এমনকি যদি সেগুলো আর ব্যবহার করা না হয় - সেগুলোকে শেষ Wei পর্যন্ত পরিষ্কার করা কঠিন।
  - একটি স্মার্ট কন্ট্রাক্ট। কোনো ঠিকানা স্মার্ট কন্ট্রাক্ট কিনা তা পরীক্ষা করা একটু কঠিন। একটি অপকোড রয়েছে যা বাহ্যিক কোডের দৈর্ঘ্য চেক করে, যাকে [`EXTCODESIZE`](https://www.evm.codes/#3b) বলা হয়। Solidity তে আপনি এটি [`<address>.code.length`](https://docs.soliditylang.org/en/latest/units-and-global-variables.html#members-of-address-types) দিয়ে পেতে পারেন, যা কম্পাইলার `EXTCODESIZE` এ পরিণত করে। এখানে আমরা [Yul](https://docs.soliditylang.org/en/latest/yul.html) ব্যবহার করি, যা হলো EVM অ্যাসেম্বলি, কীভাবে সরাসরি অপকোড কল করতে হয় তা দেখানোর জন্য। মনে রাখবেন যে [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702) এর পর থেকে একটি EOA এরও কোড থাকতে পারে (একটি কন্ট্রাক্ট এ অর্পণ), তাই এই চেকটি কোড সহ অ্যাকাউন্টগুলোকে শনাক্ত করে, কঠোরভাবে কন্ট্রাক্টগুলোকে নয়। আমাদের উদ্দেশ্য, খালি ঠিকানাগুলো প্রত্যাখ্যান করার জন্য, এটি ঠিক আছে।

এখানে সম্পূর্ণ ফাংশনটি রয়েছে:

```solidity
    function _update(address from, address to, uint256 value)
        internal virtual
        override(ERC20)
    {
        // পোড়ানো টোকেনগুলোকে ঠিকানা(0)-তে পাঠায়, এটিকে ব্লক করবেন না
        if (to != address(0)) {
            require(to != address(this), "Can't send tokens to the contract address");

            bool isToContract;
            assembly {
               isToContract := gt(extcodesize(to), 0)
            }

            require(to.balance != 0 || isToContract, "Can't send tokens to an empty address");
        }

        super._update(from, to, value);
    }
```

চলুন নতুন কোডটি লাইন বাই লাইন দেখি:

```solidity
        require(to != address(this), "Can't send tokens to the contract address");
```

এটি প্রথম প্রয়োজনীয়তা, চেক করুন যে `to` এবং `this(address)` একই জিনিস নয়।

```solidity
        bool isToContract;
        assembly {
           isToContract := gt(extcodesize(to), 0)
        }
```

এভাবেই আমরা চেক করি যে কোনো ঠিকানা একটি কন্ট্রাক্ট কিনা। আমরা সরাসরি Yul থেকে আউটপুট গ্রহণ করতে পারি না, তাই এর পরিবর্তে আমরা ফলাফল ধরে রাখার জন্য একটি ভেরিয়েবল সংজ্ঞায়িত করি (এই ক্ষেত্রে `isToContract`)। Yul যেভাবে কাজ করে তা হলো প্রতিটি অপকোডকে একটি ফাংশন হিসেবে বিবেচনা করা হয়। তাই প্রথমে আমরা কন্ট্রাক্ট এর আকার পেতে [`EXTCODESIZE`](https://www.evm.codes/#3b) কল করি, এবং তারপর এটি শূন্য নয় তা চেক করতে [`GT`](https://www.evm.codes/#11) ব্যবহার করি (আমরা আনসাইনড ইন্টিজার নিয়ে কাজ করছি, তাই অবশ্যই এটি নেতিবাচক হতে পারে না)। এরপর আমরা ফলাফলটি `isToContract` এ লিখি।

```solidity
        require(to.balance != 0 || isToContract, "Can't send tokens to an empty address");
```

এবং সবশেষে, আমাদের কাছে খালি ঠিকানাগুলোর জন্য আসল চেক রয়েছে।

## প্রশাসনিক অ্যাক্সেস {#admin-access}

মাঝে মাঝে এমন একজন অ্যাডমিনিস্ট্রেটর থাকা দরকারী যিনি ভুলগুলো বাতিল করতে পারেন। অপব্যবহারের সম্ভাবনা কমাতে, এই অ্যাডমিনিস্ট্রেটর একটি [মাল্টিসিগ](https://blog.logrocket.com/security-choices-multi-signature-wallets/) হতে পারে যাতে একাধিক ব্যক্তিকে কোনো পদক্ষেপে একমত হতে হয়। এই নিবন্ধে আমাদের দুটি প্রশাসনিক বৈশিষ্ট্য থাকবে:

1. অ্যাকাউন্ট ফ্রিজ এবং আনফ্রিজ করা। এটি দরকারী হতে পারে, উদাহরণস্বরূপ, যখন কোনো অ্যাকাউন্ট আপস করা হতে পারে।
2. সম্পদ পরিষ্কার করা।

   মাঝে মাঝে প্রতারকরা বৈধতা অর্জনের জন্য আসল টোকেনের কন্ট্রাক্ট এ প্রতারণামূলক টোকেন পাঠায়। উদাহরণস্বরূপ, [এখানে দেখুন](https://optimism.blockscout.com/token/0x2348B1a1228DDCd2dB668c3d30207c3E1852fBbe?tab=holders)। বৈধ ERC-20 কন্ট্রাক্ট হলো [0x4200....0042](https://optimism.blockscout.com/token/0x4200000000000000000000000000000000000042)। যে স্ক্যামটি এর ভান করে তা হলো [0x234....bbe](https://optimism.blockscout.com/token/0x2348B1a1228DDCd2dB668c3d30207c3E1852fBbe)।

   এমনও হতে পারে যে লোকেরা ভুল করে আমাদের কন্ট্রাক্ট এ বৈধ ERC-20 টোকেন পাঠায়, যা সেগুলোকে বের করার একটি উপায় চাওয়ার আরেকটি কারণ।

ওপেনজেপেলিন প্রশাসনিক অ্যাক্সেস সক্ষম করার জন্য দুটি মেকানিজম প্রদান করে:

- [`Ownable`](https://docs.openzeppelin.com/contracts/5.x/access-control#ownership-and-ownable) কন্ট্রাক্টগুলোর একজন একক মালিক থাকে। যে ফাংশনগুলোতে `onlyOwner` [মডিফায়ার](https://docs.soliditylang.org/en/latest/contracts.html#function-modifiers) রয়েছে সেগুলো শুধুমাত্র সেই মালিক কল করতে পারেন। মালিকরা অন্য কারো কাছে মালিকানা হস্তান্তর করতে পারেন বা এটি সম্পূর্ণভাবে ত্যাগ করতে পারেন। অন্যান্য সমস্ত অ্যাকাউন্টের অধিকার সাধারণত অভিন্ন হয়।
- [`AccessControl`](https://docs.openzeppelin.com/contracts/5.x/access-control#role-based-access-control) কন্ট্রাক্টগুলোতে [রোল বেসড অ্যাক্সেস কন্ট্রোল (RBAC)](https://en.wikipedia.org/wiki/Role-based_access_control) রয়েছে।

সরলতার খাতিরে, এই নিবন্ধে আমরা `Ownable` ব্যবহার করি।

### কন্ট্রাক্ট ফ্রিজ এবং আনফ্রিজ করা {#freezing-and-thawing-contracts}

কন্ট্রাক্টগুলো ফ্রিজ এবং আনফ্রিজ করার জন্য বেশ কয়েকটি পরিবর্তনের প্রয়োজন:

- কোন ঠিকানাগুলো ফ্রিজ করা হয়েছে তার ট্র্যাক রাখতে ঠিকানাগুলো থেকে [বুলিয়ান](https://en.wikipedia.org/wiki/Boolean_data_type) এ একটি [ম্যাপিং](https://docs.soliditylang.org/en/latest/types.html#mapping-types)। সমস্ত মান প্রাথমিকভাবে শূন্য থাকে, যা বুলিয়ান মানগুলোর জন্য মিথ্যা হিসেবে ব্যাখ্যা করা হয়। আমরা এটাই চাই কারণ ডিফল্টরূপে অ্যাকাউন্টগুলো ফ্রিজ করা থাকে না।

  ```solidity
      mapping(address => bool) public frozenAccounts;
  ```

- যখন কোনো অ্যাকাউন্ট ফ্রিজ বা আনফ্রিজ করা হয় তখন আগ্রহী যে কাউকে জানানোর জন্য [ইভেন্ট](https://docs.soliditylang.org/en/latest/contracts.html#events)। প্রযুক্তিগতভাবে বলতে গেলে এই কাজগুলোর জন্য ইভেন্টগুলোর প্রয়োজন নেই, তবে এটি অফচেইন কোডকে এই ইভেন্টগুলো শুনতে এবং কী ঘটছে তা জানতে সাহায্য করে। যখন অন্য কারো জন্য প্রাসঙ্গিক হতে পারে এমন কিছু ঘটে তখন স্মার্ট কন্ট্রাক্ট এর জন্য এগুলো এমিট করা ভালো শিষ্টাচার হিসেবে বিবেচিত হয়।

  ইভেন্টগুলো ইনডেক্স করা হয় যাতে কোনো অ্যাকাউন্ট যতবার ফ্রিজ বা আনফ্রিজ করা হয়েছে তা অনুসন্ধান করা সম্ভব হয়।

  ```solidity
    // যখন অ্যাকাউন্টগুলো ফ্রিজ বা আনফ্রিজ করা হয়
    event AccountFrozen(address indexed _addr);
    event AccountThawed(address indexed _addr);
  ```

- অ্যাকাউন্টগুলো ফ্রিজ এবং আনফ্রিজ করার জন্য ফাংশন। এই দুটি ফাংশন প্রায় অভিন্ন, তাই আমরা শুধুমাত্র ফ্রিজ ফাংশনটি নিয়ে আলোচনা করব।

  ```solidity
      function freezeAccount(address addr)
        public
        onlyOwner
  ```

  [`public`](https://docs.soliditylang.org/en/latest/contracts.html#function-visibility) চিহ্নিত ফাংশনগুলো অন্যান্য স্মার্ট কন্ট্রাক্ট থেকে বা সরাসরি কোনো ট্রানজ্যাকশন দ্বারা কল করা যেতে পারে।

  ```solidity
    {
        require(!frozenAccounts[addr], "Account already frozen");
        frozenAccounts[addr] = true;
        emit AccountFrozen(addr);
    }  // অ্যাকাউন্ট ফ্রিজ করা
  ```

  যদি অ্যাকাউন্টটি ইতিমধ্যে ফ্রিজ করা থাকে, তবে রিভার্ট করুন। অন্যথায়, এটিকে ফ্রিজ করুন এবং একটি ইভেন্ট `emit` করুন।

- একটি ফ্রিজ করা অ্যাকাউন্ট থেকে অর্থ সরানো রোধ করতে `_update` পরিবর্তন করুন। মনে রাখবেন যে অর্থ এখনও ফ্রিজ করা অ্যাকাউন্টে হস্তান্তর করা যেতে পারে। এই লাইনটি ফাংশনের শুরুতে, `if` ব্লকের বাইরে রাখুন, যাতে এটি একটি ফ্রিজ করা অ্যাকাউন্ট থেকে টোকেন পোড়ানোও রোধ করে।

  ```solidity
       require(!frozenAccounts[from], "The account is frozen");
  ```

### সম্পদ পরিষ্কার করা {#asset-cleanup}

এই কন্ট্রাক্ট দ্বারা ধারণ করা ERC-20 টোকেনগুলো রিলিজ করার জন্য আমাদের সেই টোকেন কন্ট্রাক্ট এর একটি ফাংশন কল করতে হবে যার অন্তর্গত সেগুলো, হয় [`transfer`](https://eips.ethereum.org/EIPS/eip-20#transfer) অথবা [`approve`](https://eips.ethereum.org/EIPS/eip-20#approve)। এই ক্ষেত্রে অ্যালাউন্স এর উপর গ্যাস নষ্ট করার কোনো মানে নেই, আমরা সরাসরি হস্তান্তর করতে পারি।

```solidity
    function cleanupERC20(
        address erc20,
        address dest
    )
        public
        onlyOwner
    {
        IERC20 token = IERC20(erc20);
```

যখন আমরা ঠিকানাটি পাই তখন একটি কন্ট্রাক্ট এর জন্য একটি অবজেক্ট তৈরি করার সিনট্যাক্স এটি। এটি ব্যবহার করার জন্য আমাদের [IERC20 এর সংজ্ঞা](https://github.com/OpenZeppelin/openzeppelin-contracts/blob/master/contracts/token/ERC20/IERC20.sol) প্রয়োজন, যা একটি OpenZeppelin ERC-20 কন্ট্রাক্ট এর ইন্টারফেস। উইজার্ডের `import {ERC20} from ...` লাইনটি শুধুমাত্র `ERC20` নিয়ে আসে, তাই ফাইলের শীর্ষে অন্যান্য ইমপোর্টগুলোর পাশে এই লাইনটি যোগ করুন:

```solidity
import {IERC20} from "@openzeppelin/contracts/token/ERC20/IERC20.sol";
```

```solidity
        uint balance = token.balanceOf(address(this));
        token.transfer(dest, balance);
    }
```

এটি একটি ক্লিনআপ ফাংশন, তাই সম্ভবত আমরা কোনো টোকেন রেখে যেতে চাই না। ব্যবহারকারীর কাছ থেকে ম্যানুয়ালি ব্যালেন্স পাওয়ার পরিবর্তে, আমরা প্রক্রিয়াটিকে স্বয়ংক্রিয় করতে পারি।
