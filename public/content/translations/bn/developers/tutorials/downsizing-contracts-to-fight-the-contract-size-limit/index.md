## কেন একটি লিমিট আছে? {#why-is-there-a-limit}

[22 নভেম্বর, 2016](https://blog.ethereum.org/2016/11/18/hard-fork-no-4-spurious-dragon)-এ Spurious Dragon হার্ড ফর্ক [EIP-170](https://eips.ethereum.org/EIPS/eip-170) চালু করেছিল, যা 24,576 বাইট (24 KiB)-এর একটি স্মার্ট কন্ট্রাক্ট সাইজ লিমিট যোগ করেছিল। একজন Solidity ডেভেলপার হিসেবে আপনার জন্য এর অর্থ হলো, যখন আপনি আপনার কন্ট্রাক্টে আরও বেশি ফাংশনালিটি যোগ করবেন, তখন কোনো এক পর্যায়ে আপনি এই লিমিটে পৌঁছে যাবেন এবং কম্পাইলার আপনাকে সতর্ক করবে:

`Warning: Contract code size is 25000 bytes and exceeds 24576 bytes (a limit introduced in Spurious Dragon). This contract may not be deployable on Mainnet. Consider enabling the optimizer (with a low "runs" value!), turning off revert strings, or using libraries.`

ডিপ্লয়মেন্ট কোডের (initcode) জন্যও একটি অনুরূপ সতর্কতা রয়েছে, যা [EIP-3860](https://eips.ethereum.org/EIPS/eip-3860) সাংহাই আপগ্রেডে 49,152 বাইটে সীমাবদ্ধ করেছে।

এই লিমিট স্থায়ী নয়। [EIP-7954](https://eips.ethereum.org/EIPS/eip-7954) এটিকে 65,536 বাইট (64 KiB) এবং initcode লিমিটকে 131,072 বাইটে উন্নীত করে, এবং এটি [গ্ল্যামস্টারডাম আপগ্রেডের](/roadmap/glamsterdam/) জন্য নির্ধারিত। আপনি যে নেটওয়ার্কে ডিপ্লয় করবেন সেখানে এই আপগ্রেডটি সক্রিয় না হওয়া পর্যন্ত, 24,576 বাইটই হলো সেখানকার লিমিট, এবং এর পরেও ছোট কন্ট্রাক্টগুলো ডিপ্লয় করা সস্তা এবং অডিট করা সহজ থাকে।

এই লিমিটটি ডিনায়াল-অফ-সার্ভিস (DOS) আক্রমণ প্রতিরোধ করার জন্য চালু করা হয়েছিল। কোনো কন্ট্রাক্টে কল করা গ্যাসের দিক থেকে তুলনামূলকভাবে সস্তা। তবে, ইথেরিয়াম নোডগুলোর জন্য একটি কন্ট্রাক্ট কলের প্রভাব কল করা কন্ট্রাক্ট কোডের সাইজের ওপর নির্ভর করে অসামঞ্জস্যপূর্ণভাবে বৃদ্ধি পায় (ডিস্ক থেকে কোড পড়া, কোড প্রি-প্রসেস করা, মার্কেল প্রমাণে ডেটা যোগ করা)। যখনই আপনার এমন পরিস্থিতি তৈরি হয় যেখানে আক্রমণকারীর অন্যদের জন্য প্রচুর কাজ তৈরি করতে খুব কম রিসোর্সের প্রয়োজন হয়, তখনই DOS আক্রমণের সম্ভাবনা তৈরি হয়।

প্রাথমিকভাবে এটি খুব একটা সমস্যা ছিল না কারণ একটি স্বাভাবিক কন্ট্রাক্ট সাইজ লিমিট হলো ব্লক গ্যাস লিমিট। স্পষ্টতই, একটি কন্ট্রাক্টকে এমন একটি ট্রানজ্যাকশনের মধ্যে ডিপ্লয় করতে হবে যা কন্ট্রাক্টের সমস্ত বাইটকোড ধারণ করে। আপনি যদি একটি ব্লকে শুধুমাত্র সেই একটি ট্রানজ্যাকশন অন্তর্ভুক্ত করেন, তবে আপনি সেই সমস্ত গ্যাস ব্যবহার করতে পারেন, তবে এটি অসীম নয়। বর্তমানে ব্লক গ্যাস লিমিট কয়েক কোটি গ্যাস এবং ভ্যালিডেটরদের দ্বারা এটি বেশ কয়েকবার বাড়ানো হয়েছে, তাই এটি নিজেই খুব বড় কন্ট্রাক্টগুলোকে অনুমতি দেবে। [ফুসাকা আপগ্রেডের](/roadmap/fusaka/) পর থেকে, একটি একক ট্রানজ্যাকশনও 16,777,216 গ্যাসে সীমাবদ্ধ করা হয়েছে ([EIP-7825](https://eips.ethereum.org/EIPS/eip-7825)), তবে এটি এখনও 24 KiB কন্ট্রাক্ট ডিপ্লয় করার খরচের চেয়ে অনেক বেশি, যে কারণে একটি স্পষ্ট সাইজ লিমিট প্রয়োজন।

নিচে আমরা তাদের সম্ভাব্য প্রভাবের ক্রমানুসারে কিছু পদ্ধতি দেখব। এটিকে ওজন কমানোর মতো করে ভাবুন। কারও লক্ষ্য ওজনে (আমাদের ক্ষেত্রে 24kb) পৌঁছানোর জন্য সেরা কৌশল হলো প্রথমে বড় প্রভাব ফেলে এমন পদ্ধতিগুলোতে ফোকাস করা। বেশিরভাগ ক্ষেত্রেই শুধুমাত্র আপনার ডায়েট ঠিক করলেই আপনি সেখানে পৌঁছে যাবেন, তবে কখনও কখনও আপনার আরও কিছুটা প্রয়োজন হতে পারে। তখন আপনি কিছু ব্যায়াম (মাঝারি প্রভাব) বা এমনকি সাপ্লিমেন্ট (ছোট প্রভাব) যোগ করতে পারেন।

## বড় প্রভাব {#big-impact}

### আপনার কন্ট্রাক্টগুলো আলাদা করুন {#separate-your-contracts}

এটি সর্বদা আপনার প্রথম পদক্ষেপ হওয়া উচিত। আপনি কীভাবে কন্ট্রাক্টটিকে একাধিক ছোট কন্ট্রাক্টে আলাদা করতে পারেন? এটি সাধারণত আপনাকে আপনার কন্ট্রাক্টগুলোর জন্য একটি ভালো আর্কিটেকচার তৈরি করতে বাধ্য করে। কোড পড়ার সুবিধার দৃষ্টিকোণ থেকে ছোট কন্ট্রাক্টগুলো সর্বদা বেশি পছন্দনীয়। কন্ট্রাক্টগুলো ভাগ করার জন্য, নিজেকে জিজ্ঞাসা করুন:

- কোন ফাংশনগুলো একসাথে থাকে? প্রতিটি ফাংশনের সেট তার নিজস্ব কন্ট্রাক্টে রাখা সবচেয়ে ভালো হতে পারে।
- কোন ফাংশনগুলোর কন্ট্রাক্ট স্টেট পড়ার প্রয়োজন নেই বা শুধুমাত্র স্টেটের একটি নির্দিষ্ট সাবসেট প্রয়োজন?
- আপনি কি স্টোরেজ এবং ফাংশনালিটি আলাদা করতে পারেন?

### লাইব্রেরি {#libraries}

স্টোরেজ থেকে ফাংশনালিটি কোড সরিয়ে নেওয়ার একটি সহজ উপায় হলো একটি [লাইব্রেরি](https://docs.soliditylang.org/en/latest/contracts.html#libraries) ব্যবহার করা। লাইব্রেরি ফাংশনগুলোকে internal হিসেবে ডিক্লেয়ার করবেন না কারণ সেগুলো কম্পাইল করার সময় সরাসরি [কন্ট্রাক্টে যোগ করা হবে](https://ethereum.stackexchange.com/questions/12975/are-internal-functions-in-libraries-not-covered-by-linking)। তবে আপনি যদি public ফাংশন ব্যবহার করেন, তবে সেগুলো আসলে একটি আলাদা লাইব্রেরি কন্ট্রাক্টে থাকবে। লাইব্রেরির ব্যবহার আরও সুবিধাজনক করতে [using for](https://docs.soliditylang.org/en/latest/contracts.html#using-for) ব্যবহার করার কথা বিবেচনা করুন।

### প্রক্সি {#proxies}

একটি আরও উন্নত কৌশল হতে পারে একটি প্রক্সি সিস্টেম। লাইব্রেরিগুলো ব্যাকগ্রাউন্ডে `DELEGATECALL` ব্যবহার করে যা কল করা কন্ট্রাক্টের স্টেটের সাথে অন্য একটি কন্ট্রাক্টের ফাংশন এক্সিকিউট করে। প্রক্সি সিস্টেম সম্পর্কে আরও জানতে [স্মার্ট কন্ট্রাক্ট আপগ্রেড করা](/developers/docs/smart-contracts/upgrading/) দেখুন। এগুলো আপনাকে আরও ফাংশনালিটি দেয়, যেমন, এগুলো আপগ্রেড করার সুবিধা দেয়, তবে এগুলো অনেক জটিলতাও যোগ করে। আমি শুধুমাত্র কন্ট্রাক্টের সাইজ কমানোর জন্য এগুলো যোগ করব না, যদি না কোনো কারণে এটি আপনার একমাত্র বিকল্প হয়।

## মাঝারি প্রভাব {#medium-impact}

### ফাংশনগুলো সরিয়ে ফেলুন {#remove-functions}

এটি স্পষ্ট হওয়া উচিত। ফাংশনগুলো একটি কন্ট্রাক্টের সাইজ বেশ কিছুটা বাড়িয়ে দেয়।

- **External**: অনেক সময় আমরা সুবিধার জন্য অনেক view ফাংশন যোগ করি। সাইজ লিমিটে না পৌঁছানো পর্যন্ত এটি সম্পূর্ণ ঠিক আছে। এরপর আপনি হয়তো শুধুমাত্র অত্যন্ত প্রয়োজনীয় ফাংশনগুলো রেখে বাকি সব সরিয়ে ফেলার কথা গুরুত্ব সহকারে ভাবতে পারেন।
- **Internal**: আপনি internal/private ফাংশনগুলোও সরিয়ে ফেলতে পারেন এবং ফাংশনটি যদি শুধুমাত্র একবার কল করা হয় তবে কোডটি সরাসরি ইনলাইন করতে পারেন।

### অতিরিক্ত ভেরিয়েবল এড়িয়ে চলুন {#avoid-additional-variables}

```solidity
struct MyStruct {
    address addr1;
    address addr2;
}

mapping(uint => MyStruct) myStructs;

function get(uint id) public view returns (address, address) {
    MyStruct memory myStruct = myStructs[id];
    return (myStruct.addr1, myStruct.addr2);
}
```

```solidity
function get(uint id) public view returns (address, address) {
    return (myStructs[id].addr1, myStructs[id].addr2);
}
```

এই নিবন্ধটি লেখার সময় এই ধরনের একটি সাধারণ পরিবর্তন **0.28kb**-এর পার্থক্য তৈরি করেছিল। সঠিক সঞ্চয় আপনার কম্পাইলার সংস্করণ এবং সেটিংসের ওপর নির্ভর করে (Solidity 0.8.37-এর সাথে এটি অপ্টিমাইজার ছাড়া প্রায় 0.1kb এবং এর সাথে অনেক কম), তাই সর্বদা পরিমাপ করুন। সম্ভাবনা রয়েছে যে আপনি আপনার কন্ট্রাক্টগুলোতে এই ধরনের অনেক পরিস্থিতি খুঁজে পেতে পারেন এবং সেগুলো সত্যিই উল্লেখযোগ্য পরিমাণে যোগ হতে পারে।

### এরর বার্তা ছোট করুন {#shorten-error-message}

দীর্ঘ রিভার্ট বার্তা এবং বিশেষ করে অনেকগুলো ভিন্ন ভিন্ন রিভার্ট বার্তা কন্ট্রাক্টের সাইজ বাড়িয়ে দিতে পারে। এর পরিবর্তে ছোট এরর কোড ব্যবহার করুন এবং আপনার কন্ট্রাক্টে সেগুলো ডিকোড করুন। একটি দীর্ঘ বার্তা অনেক ছোট হয়ে যেতে পারে:

```solidity
require(msg.sender == owner, "Only the owner of this contract can call this function");
```

```solidity
require(msg.sender == owner, "OW1");
```

### এরর বার্তার পরিবর্তে কাস্টম এরর ব্যবহার করুন {#use-custom-errors-instead-of-error-messages}

[Solidity 0.8.4](https://blog.soliditylang.org/2021/04/21/custom-errors/)-এ কাস্টম এরর চালু করা হয়েছে। এগুলো আপনার কন্ট্রাক্টের সাইজ কমানোর একটি দুর্দান্ত উপায়, কারণ এগুলো সিলেক্টর হিসেবে ABI-এনকোড করা হয় (ঠিক ফাংশনগুলোর মতো)।

```solidity
error Unauthorized();

function doSomething() public view {
    if (msg.sender != owner) {
        revert Unauthorized();
    }
}
```

### অপ্টিমাইজারে একটি কম রান ভ্যালু বিবেচনা করুন {#consider-a-low-run-value-in-the-optimizer}

আপনি অপ্টিমাইজার সেটিংসও পরিবর্তন করতে পারেন। ডিফল্ট ভ্যালু 200-এর অর্থ হলো এটি বাইটকোডটিকে এমনভাবে অপ্টিমাইজ করার চেষ্টা করছে যেন একটি ফাংশন 200 বার কল করা হয়েছে। আপনি যদি এটিকে 1-এ পরিবর্তন করেন, তবে আপনি মূলত অপ্টিমাইজারকে প্রতিটি ফাংশন শুধুমাত্র একবার চালানোর ক্ষেত্রে অপ্টিমাইজ করতে বলছেন। শুধুমাত্র একবার চালানোর জন্য একটি অপ্টিমাইজ করা ফাংশন মানে এটি ডিপ্লয়মেন্টের জন্যই অপ্টিমাইজ করা হয়েছে। মনে রাখবেন যে **এটি ফাংশনগুলো চালানোর জন্য [গ্যাস খরচ](/developers/docs/gas/) বাড়িয়ে দেয়**, তাই আপনি হয়তো এটি করতে চাইবেন না। আপনি যদি `viaIR` চালু করে কম্পাইল করেন, তবে এটি সহ এবং এটি ছাড়া সাইজ চেক করুন, কারণ IR-ভিত্তিক কোড জেনারেটর লক্ষণীয়ভাবে ভিন্ন বাইটকোড সাইজ তৈরি করতে পারে। বিস্তারিত জানতে [অপ্টিমাইজার অপশনগুলো](https://docs.soliditylang.org/en/latest/using-the-compiler.html#optimizer-options) দেখুন।

## ছোট প্রভাব {#small-impact}

### ফাংশনে স্ট্রাক্ট পাস করা এড়িয়ে চলুন {#avoid-passing-structs-to-functions}

আপনি যদি [ABI coder v2](https://docs.soliditylang.org/en/latest/layout-of-source-files.html#abi-coder-pragma) ব্যবহার করেন (Solidity 0.8.0 থেকে ডিফল্ট), তবে এটি কোনো ফাংশনে স্ট্রাক্ট পাস না করতে সাহায্য করতে পারে। প্যারামিটারটিকে স্ট্রাক্ট হিসেবে পাস করার পরিবর্তে, প্রয়োজনীয় প্যারামিটারগুলো সরাসরি পাস করুন। এই উদাহরণে আমরা আরও **0.1kb** বাঁচিয়েছি।

```solidity
function get(uint id) public view returns (address, address) {
    return _get(myStructs[id]);
}

function _get(MyStruct memory myStruct) private pure returns (address, address) {
    return (myStruct.addr1, myStruct.addr2);
}
```

```solidity
function get(uint id) public view returns (address, address) {
    return _get(myStructs[id].addr1, myStructs[id].addr2);
}

function _get(address addr1, address addr2) private pure returns (address, address) {
    return (addr1, addr2);
}
```

### ফাংশন এবং ভেরিয়েবলের জন্য সঠিক ভিজিবিলিটি ডিক্লেয়ার করুন {#declare-correct-visibility-for-functions-and-variables}

- যে ফাংশন বা ভেরিয়েবলগুলো শুধুমাত্র বাইরে থেকে কল করা হয়? সেগুলোকে `public`-এর পরিবর্তে `external` হিসেবে ডিক্লেয়ার করুন।
- যে ফাংশন বা ভেরিয়েবলগুলো শুধুমাত্র কন্ট্রাক্টের ভেতর থেকে কল করা হয়? সেগুলোকে `public`-এর পরিবর্তে `private` বা `internal` হিসেবে ডিক্লেয়ার করুন।

### মডিফায়ারগুলো সরিয়ে ফেলুন {#remove-modifiers}

মডিফায়ারগুলো, বিশেষ করে যখন ব্যাপকভাবে ব্যবহার করা হয়, তখন কন্ট্রাক্টের সাইজের ওপর উল্লেখযোগ্য প্রভাব ফেলতে পারে। এগুলো সরিয়ে ফেলার কথা বিবেচনা করুন এবং এর পরিবর্তে ফাংশন ব্যবহার করুন।

```solidity
modifier checkStuff() {
    require(msg.sender == owner, "OW1");
    _;
}

function doSomething() public checkStuff {}
```

```solidity
function checkStuff() private view {
    require(msg.sender == owner, "OW1");
}

function doSomething() public view {
    checkStuff();
}
```

এই টিপসগুলো আপনাকে কন্ট্রাক্টের সাইজ উল্লেখযোগ্যভাবে কমাতে সাহায্য করবে। আবারও, আমি যথেষ্ট জোর দিয়ে বলতে পারি না, সবচেয়ে বড় প্রভাবের জন্য সম্ভব হলে সর্বদা কন্ট্রাক্টগুলো ভাগ করার দিকে ফোকাস করুন।
