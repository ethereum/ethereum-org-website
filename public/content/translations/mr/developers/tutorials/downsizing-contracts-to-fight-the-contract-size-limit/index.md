## मर्यादा का आहे? {#why-is-there-a-limit}

[22 नोव्हेंबर 2016](https://blog.ethereum.org/2016/11/18/hard-fork-no-4-spurious-dragon) रोजी Spurious Dragon हार्ड फोर्कने [EIP-170](https://eips.ethereum.org/EIPS/eip-170) सादर केले ज्याने 24,576 बाइट्स (24 KiB) ची स्मार्ट कॉन्ट्रॅक्ट आकार मर्यादा जोडली. एक Solidity डेव्हलपर म्हणून तुमच्यासाठी याचा अर्थ असा आहे की जेव्हा तुम्ही तुमच्या कॉन्ट्रॅक्टमध्ये अधिकाधिक कार्यक्षमता जोडता, तेव्हा एका टप्प्यावर तुम्ही मर्यादेपर्यंत पोहोचाल आणि कंपायलर तुम्हाला चेतावणी देईल:

`Warning: Contract code size is 25000 bytes and exceeds 24576 bytes (a limit introduced in Spurious Dragon). This contract may not be deployable on Mainnet. Consider enabling the optimizer (with a low "runs" value!), turning off revert strings, or using libraries.`

प्रस्थापना कोड (initcode) साठी अशीच एक चेतावणी आहे, ज्याला [EIP-3860](https://eips.ethereum.org/EIPS/eip-3860) ने शांघाय अपग्रेडमध्ये 49,152 बाइट्सपर्यंत मर्यादित केले आहे.

ही मर्यादा कायमस्वरूपी नाही. [EIP-7954](https://eips.ethereum.org/EIPS/eip-7954) ती 65,536 बाइट्स (64 KiB) पर्यंत वाढवते आणि initcode मर्यादा 131,072 बाइट्सपर्यंत वाढवते, आणि ती [ग्लॅमस्टरडॅम अपग्रेड](/roadmap/glamsterdam/) साठी नियोजित आहे. जोपर्यंत ते अपग्रेड तुम्ही प्रस्थापित करत असलेल्या नेटवर्कवर सक्रिय होत नाही, तोपर्यंत तिथे 24,576 बाइट्स ही मर्यादा आहे, आणि त्यानंतरही लहान कॉन्ट्रॅक्ट्स प्रस्थापित करण्यासाठी स्वस्त आणि ऑडिट करण्यासाठी सोपे राहतात.

ही मर्यादा denial-of-service (DOS) हल्ले रोखण्यासाठी आणली गेली. कॉन्ट्रॅक्टला केलेला कोणताही कॉल गॅसच्या दृष्टीने तुलनेने स्वस्त असतो. तथापि, इथेरियम नोड्ससाठी कॉन्ट्रॅक्ट कॉलचा प्रभाव कॉल केलेल्या कॉन्ट्रॅक्ट कोडच्या आकारानुसार विषम प्रमाणात वाढतो (डिस्कवरून कोड वाचणे, कोडवर पूर्व-प्रक्रिया करणे, मर्केल पुराव्यामध्ये डेटा जोडणे). जेव्हा तुमच्याकडे अशी परिस्थिती असते जिथे हल्लेखोराला इतरांसाठी खूप काम निर्माण करण्यासाठी कमी संसाधनांची आवश्यकता असते, तेव्हा तुम्हाला DOS हल्ल्यांची शक्यता मिळते.

सुरुवातीला ही कमी समस्या होती कारण एक नैसर्गिक कॉन्ट्रॅक्ट आकार मर्यादा म्हणजे ब्लॉक गॅस मर्यादा. साहजिकच, कॉन्ट्रॅक्ट अशा व्यवहारामध्ये प्रस्थापित केले जाणे आवश्यक आहे ज्यामध्ये कॉन्ट्रॅक्टचा सर्व बाइटकोड असतो. जर तुम्ही ब्लॉकमध्ये फक्त तो एक व्यवहार समाविष्ट केला, तर तुम्ही तो सर्व गॅस वापरू शकता, परंतु तो अमर्याद नाही. आज ब्लॉक गॅस मर्यादा लाखो गॅस आहे आणि व्हॅलिडेटर्सद्वारे ती अनेक वेळा वाढवली गेली आहे, त्यामुळे ती स्वतःहून खूप मोठ्या कॉन्ट्रॅक्ट्सना अनुमती देईल. [फुसाका अपग्रेड](/roadmap/fusaka/) पासून, एका व्यवहारावर 16,777,216 गॅसची मर्यादा देखील आहे ([EIP-7825](https://eips.ethereum.org/EIPS/eip-7825)), परंतु तरीही ते 24 KiB कॉन्ट्रॅक्ट प्रस्थापित करण्यासाठी लागणाऱ्या खर्चापेक्षा खूप जास्त आहे, म्हणूनच स्पष्ट आकार मर्यादेची आवश्यकता आहे.

पुढील भागात आपण त्यांच्या संभाव्य प्रभावानुसार क्रमवारी लावलेल्या काही पद्धती पाहू. वजन कमी करण्याच्या संदर्भात याचा विचार करा. एखाद्या व्यक्तीने त्यांचे लक्ष्यित वजन (आपल्या बाबतीत 24kb) गाठण्यासाठी सर्वोत्तम रणनीती म्हणजे प्रथम मोठ्या प्रभावाच्या पद्धतींवर लक्ष केंद्रित करणे. बऱ्याच प्रकरणांमध्ये फक्त तुमचा आहार सुधारल्याने तुम्ही तिथे पोहोचाल, परंतु कधीकधी तुम्हाला थोड्या अधिक गोष्टींची आवश्यकता असते. मग तुम्ही काही व्यायाम (मध्यम प्रभाव) किंवा अगदी सप्लिमेंट्स (कमी प्रभाव) जोडू शकता.

## मोठा प्रभाव {#big-impact}

### तुमचे कॉन्ट्रॅक्ट्स वेगळे करा {#separate-your-contracts}

हा नेहमी तुमचा पहिला दृष्टिकोन असावा. तुम्ही कॉन्ट्रॅक्टला अनेक लहान कॉन्ट्रॅक्ट्समध्ये कसे विभागू शकता? हे सामान्यतः तुम्हाला तुमच्या कॉन्ट्रॅक्ट्ससाठी एक चांगले आर्किटेक्चर तयार करण्यास भाग पाडते. कोड वाचनीयतेच्या दृष्टिकोनातून लहान कॉन्ट्रॅक्ट्सना नेहमीच प्राधान्य दिले जाते. कॉन्ट्रॅक्ट्स विभाजित करण्यासाठी, स्वतःला विचारा:

- कोणती फंक्शन्स एकत्र येतात? फंक्शन्सचा प्रत्येक संच त्याच्या स्वतःच्या कॉन्ट्रॅक्टमध्ये सर्वोत्तम असू शकतो.
- कोणत्या फंक्शन्सना कॉन्ट्रॅक्ट स्थिती वाचण्याची आवश्यकता नाही किंवा फक्त स्थितीचा एक विशिष्ट उपसंच आवश्यक आहे?
- तुम्ही स्टोरेज आणि कार्यक्षमता विभाजित करू शकता का?

### लायब्ररी {#libraries}

स्टोरेजपासून कार्यक्षमता कोड दूर हलवण्याचा एक सोपा मार्ग म्हणजे [लायब्ररी](https://docs.soliditylang.org/en/latest/contracts.html#libraries) वापरणे. लायब्ररी फंक्शन्सना internal म्हणून घोषित करू नका कारण ती संकलनादरम्यान (compilation) थेट [कॉन्ट्रॅक्टमध्ये जोडली जातील](https://ethereum.stackexchange.com/questions/12975/are-internal-functions-in-libraries-not-covered-by-linking). परंतु जर तुम्ही public फंक्शन्स वापरत असाल, तर ती प्रत्यक्षात एका वेगळ्या लायब्ररी कॉन्ट्रॅक्टमध्ये असतील. लायब्ररीचा वापर अधिक सोयीस्कर करण्यासाठी [using for](https://docs.soliditylang.org/en/latest/contracts.html#using-for) वापरण्याचा विचार करा.

### प्रॉक्सी (Proxies) {#proxies}

एक अधिक प्रगत रणनीती म्हणजे प्रॉक्सी प्रणाली. लायब्ररी मागे `DELEGATECALL` वापरतात जे फक्त कॉल करणाऱ्या कॉन्ट्रॅक्टच्या स्थितीसह दुसऱ्या कॉन्ट्रॅक्टचे फंक्शन कार्यान्वित करते. प्रॉक्सी प्रणालींबद्दल अधिक जाणून घेण्यासाठी [स्मार्ट कॉन्ट्रॅक्ट्स अपग्रेड करणे](/developers/docs/smart-contracts/upgrading/) तपासा. ते तुम्हाला अधिक कार्यक्षमता देतात, उदा., ते अपग्रेड करण्याची क्षमता सक्षम करतात, परंतु ते खूप गुंतागुंत देखील वाढवतात. जोपर्यंत कोणत्याही कारणास्तव तो तुमचा एकमेव पर्याय नसेल तोपर्यंत मी फक्त कॉन्ट्रॅक्टचा आकार कमी करण्यासाठी ते जोडणार नाही.

## मध्यम प्रभाव {#medium-impact}

### फंक्शन्स काढून टाका {#remove-functions}

हे स्पष्ट असले पाहिजे. फंक्शन्स कॉन्ट्रॅक्टचा आकार बऱ्यापैकी वाढवतात.

- **External**: बऱ्याच वेळा आपण सोयीसाठी अनेक view फंक्शन्स जोडतो. जोपर्यंत तुम्ही आकार मर्यादेपर्यंत पोहोचत नाही तोपर्यंत ते अगदी ठीक आहे. त्यानंतर तुम्हाला अत्यंत आवश्यक असलेली फंक्शन्स वगळता इतर सर्व काढून टाकण्याचा खरोखर विचार करावा लागेल.
- **Internal**: तुम्ही internal/private फंक्शन्स देखील काढून टाकू शकता आणि जोपर्यंत फंक्शन फक्त एकदाच कॉल केले जाते तोपर्यंत कोड इनलाइन करू शकता.

### अतिरिक्त व्हेरिएबल्स टाळा {#avoid-additional-variables}

```solidity
struct MyStruct {
    address addr1;
    address addr2;
}

mapping(uint => MyStruct) myStructs;

function get(uint id) public view returns (address, address) {
    MyStruct memory myStruct = myStructs[id];
    return (myStruct.addr1, myStruct.addr2);
}
```

```solidity
function get(uint id) public view returns (address, address) {
    return (myStructs[id].addr1, myStructs[id].addr2);
}
```

जेव्हा हा लेख लिहिला गेला तेव्हा यासारख्या साध्या बदलामुळे **0.28kb** चा फरक पडला. अचूक बचत तुमच्या कंपायलर आवृत्ती आणि सेटिंग्जवर अवलंबून असते (Solidity 0.8.37 सह ऑप्टिमायझरशिवाय हे सुमारे 0.1kb आहे आणि त्यासह खूप कमी आहे), त्यामुळे नेहमी मोजा. अशी शक्यता आहे की तुम्हाला तुमच्या कॉन्ट्रॅक्ट्समध्ये अशा अनेक समान परिस्थिती सापडतील आणि त्या खरोखरच महत्त्वपूर्ण प्रमाणात भर घालू शकतात.

### त्रुटी संदेश लहान करा {#shorten-error-message}

लांब पूर्ववत करणे (revert) संदेश आणि विशेषतः अनेक भिन्न पूर्ववत करणे संदेश कॉन्ट्रॅक्टचा आकार वाढवू शकतात. त्याऐवजी लहान त्रुटी कोड वापरा आणि त्यांना तुमच्या कॉन्ट्रॅक्टमध्ये डीकोड करा. एक लांब संदेश खूप लहान होऊ शकतो:

```solidity
require(msg.sender == owner, "Only the owner of this contract can call this function");
```

```solidity
require(msg.sender == owner, "OW1");
```

### त्रुटी संदेशांऐवजी कस्टम त्रुटी वापरा {#use-custom-errors-instead-of-error-messages}

कस्टम त्रुटी [Solidity 0.8.4](https://blog.soliditylang.org/2021/04/21/custom-errors/) मध्ये सादर केल्या गेल्या आहेत. तुमच्या कॉन्ट्रॅक्ट्सचा आकार कमी करण्याचा हा एक उत्तम मार्ग आहे, कारण ते सिलेक्टर म्हणून ABI-एनकोड केलेले असतात (जसे फंक्शन्स असतात).

```solidity
error Unauthorized();

function doSomething() public view {
    if (msg.sender != owner) {
        revert Unauthorized();
    }
}
```

### ऑप्टिमायझरमध्ये कमी रन व्हॅल्यूचा विचार करा {#consider-a-low-run-value-in-the-optimizer}

तुम्ही ऑप्टिमायझर सेटिंग्ज देखील बदलू शकता. 200 च्या डीफॉल्ट मूल्याचा अर्थ असा आहे की ते बाइटकोड ऑप्टिमाइझ करण्याचा प्रयत्न करत आहे जणू काही फंक्शन 200 वेळा कॉल केले गेले आहे. जर तुम्ही ते 1 मध्ये बदलले, तर तुम्ही मुळात ऑप्टिमायझरला प्रत्येक फंक्शन फक्त एकदाच चालवण्याच्या प्रकरणासाठी ऑप्टिमाइझ करण्यास सांगता. फक्त एकदाच चालवण्यासाठी ऑप्टिमाइझ केलेले फंक्शन म्हणजे ते प्रस्थापनेसाठीच ऑप्टिमाइझ केलेले आहे. लक्षात ठेवा की **यामुळे फंक्शन्स चालवण्यासाठी [गॅस खर्च](/developers/docs/gas/) वाढतो**, त्यामुळे तुम्हाला कदाचित ते करायचे नसेल. जर तुम्ही `viaIR` सक्षम करून कंपाइल केले, तर त्यासह आणि त्याशिवाय आकार तपासा, कारण IR-आधारित कोड जनरेटर लक्षणीयरीत्या भिन्न बाइटकोड आकार तयार करू शकतो. तपशीलांसाठी [ऑप्टिमायझर पर्याय](https://docs.soliditylang.org/en/latest/using-the-compiler.html#optimizer-options) पहा.

## कमी प्रभाव {#small-impact}

### फंक्शन्सना स्ट्रक्ट्स (structs) पास करणे टाळा {#avoid-passing-structs-to-functions}

जर तुम्ही [ABI coder v2](https://docs.soliditylang.org/en/latest/layout-of-source-files.html#abi-coder-pragma) वापरत असाल (Solidity 0.8.0 पासून डीफॉल्ट), तर फंक्शनला स्ट्रक्ट्स पास न करणे उपयुक्त ठरू शकते. पॅरामीटर स्ट्रक्ट म्हणून पास करण्याऐवजी, आवश्यक पॅरामीटर्स थेट पास करा. या उदाहरणात आपण आणखी **0.1kb** वाचवले.

```solidity
function get(uint id) public view returns (address, address) {
    return _get(myStructs[id]);
}

function _get(MyStruct memory myStruct) private pure returns (address, address) {
    return (myStruct.addr1, myStruct.addr2);
}
```

```solidity
function get(uint id) public view returns (address, address) {
    return _get(myStructs[id].addr1, myStructs[id].addr2);
}

function _get(address addr1, address addr2) private pure returns (address, address) {
    return (addr1, addr2);
}
```

### फंक्शन्स आणि व्हेरिएबल्ससाठी योग्य दृश्यमानता (visibility) घोषित करा {#declare-correct-visibility-for-functions-and-variables}

- फंक्शन्स किंवा व्हेरिएबल्स जे फक्त बाहेरून कॉल केले जातात? त्यांना `public` ऐवजी `external` म्हणून घोषित करा.
- फंक्शन्स किंवा व्हेरिएबल्स जे फक्त कॉन्ट्रॅक्टच्या आतून कॉल केले जातात? त्यांना `public` ऐवजी `private` किंवा `internal` म्हणून घोषित करा.

### मॉडिफायर्स (modifiers) काढून टाका {#remove-modifiers}

मॉडिफायर्स, विशेषतः जेव्हा तीव्रतेने वापरले जातात, तेव्हा कॉन्ट्रॅक्टच्या आकारावर महत्त्वपूर्ण प्रभाव टाकू शकतात. ते काढून टाकण्याचा विचार करा आणि त्याऐवजी फंक्शन्स वापरा.

```solidity
modifier checkStuff() {
    require(msg.sender == owner, "OW1");
    _;
}

function doSomething() public checkStuff {}
```

```solidity
function checkStuff() private view {
    require(msg.sender == owner, "OW1");
}

function doSomething() public view {
    checkStuff();
}
```

या टिप्स तुम्हाला कॉन्ट्रॅक्टचा आकार लक्षणीयरीत्या कमी करण्यास मदत करतील. पुन्हा एकदा, मी पुरेसा जोर देऊ शकत नाही, सर्वात मोठ्या प्रभावासाठी शक्य असल्यास नेहमी कॉन्ट्रॅक्ट्स विभाजित करण्यावर लक्ष केंद्रित करा.
