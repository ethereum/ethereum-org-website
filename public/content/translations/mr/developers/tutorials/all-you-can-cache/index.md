जेव्हा रोलअप्स वापरले जातात, तेव्हा व्यवहाराचा प्रत्येक बाइट L1 वर पोस्ट करावा लागतो. जेव्हा हा लेख लिहिला गेला, तेव्हा त्यामुळे व्यवहारातील एका बाइटची किंमत स्टोरेज स्लॉटच्या किंमतीपेक्षा खूप जास्त महाग झाली होती. त्यामुळे, शक्य तितकी माहिती ऑनचेन कॅशे करणे अर्थपूर्ण होते.

> **टीप:** 2022 मध्ये हा लेख लिहिल्यापासून रोलअप शुल्कामध्ये खूप बदल झाले आहेत. [Ecotone आणि Fjord अपग्रेड्स](https://docs.optimism.io/op-stack/transactions/fees#l1-data-fee) (2024) पासून, OP Stack चेन्स व्यवहार डेटा [ब्लॉब्स](/roadmap/danksharding/) वर पोस्ट करतात, आणि L1 डेटा शुल्क हे व्यवहाराच्या _संकुचित (compressed)_ आकाराच्या अंदाजावर आधारित असते, ज्यामध्ये प्रति व्यवहार किमान 100 बाइट्स असतात ([तपशील पहा](https://specs.optimism.io/protocol/fjord/exec-engine.html)). याचा परिणाम म्हणून:
>
> - शून्य बाइट्स जवळजवळ विनामूल्य आहेत, कारण ते चांगल्या प्रकारे संकुचित होतात.
> - लहान व्यवहार आधीच 100-बाइटच्या किमान मर्यादेवर असतात, त्यामुळे त्यांचा कॉल डेटा आणखी लहान केल्याने त्यांचे शुल्क कमी होत नाही.
> - ब्लॉब स्पेस स्वस्त आहे, त्यामुळे OP Mainnet वर L2 एक्झिक्यूशन गॅस हा अनेकदा L1 डेटा शुल्कापेक्षा शुल्काचा मोठा भाग असतो. कॅशेमध्ये नवीन मूल्य लिहिण्यासाठी (प्रत्येकी 22100 गॅसचे दोन `SSTORE`) ते वाचवणाऱ्या बाइट्सपेक्षा जास्त खर्च येऊ शकतो.
>
> हे तत्त्व अजूनही लागू आहे (कमी संकुचित बाइट्स म्हणजे कमी L1 डेटा शुल्क), परंतु कॅशिंग फायदेशीर ठरते की नाही हे तुमच्या व्यवहारांच्या आकारावर आणि सध्याच्या L1 आणि L2 गॅसच्या किंमतींवर अवलंबून असते. तुम्ही [`GasPriceOracle` predeploy](https://specs.optimism.io/protocol/predeploys.html#gaspriceoracle) वर `getL1Fee` ला कॉल करून विशिष्ट व्यवहाराचे L1 डेटा शुल्क तपासू शकता.

या लेखामध्ये तुम्ही कॅशिंग कॉन्ट्रॅक्ट कसे तयार करावे आणि कसे वापरावे हे शिकाल जेणेकरून अनेक वेळा वापरले जाण्याची शक्यता असलेले कोणतेही पॅरामीटर मूल्य कॅशे केले जाईल आणि (पहिल्या वेळेनंतर) खूप कमी बाइट्ससह वापरण्यासाठी उपलब्ध होईल, आणि या कॅशेचा वापर करणारा साखळीबाह्य कोड कसा लिहावा हे देखील शिकाल.

जर तुम्हाला लेख वगळायचा असेल आणि फक्त सोर्स कोड पाहायचा असेल, तर [तो येथे आहे](https://github.com/qbzzt/20220915-all-you-can-cache). डेव्हलपमेंट स्टॅक [Foundry](https://getfoundry.sh/introduction/installation/) आहे.

## एकूण डिझाइन {#overall-design}

सोपे करण्यासाठी आपण असे गृहीत धरू की सर्व व्यवहार पॅरामीटर्स `uint256`, 32 बाइट्स लांबीचे आहेत. जेव्हा आपल्याला एखादा व्यवहार प्राप्त होतो, तेव्हा आपण प्रत्येक पॅरामीटरचे खालीलप्रमाणे विश्लेषण करू:

1. जर पहिला बाइट `0xFF` असेल, तर पुढील 32 बाइट्स पॅरामीटर मूल्य म्हणून घ्या आणि ते कॅशेमध्ये लिहा.

2. जर पहिला बाइट `0xFE` असेल, तर पुढील 32 बाइट्स पॅरामीटर मूल्य म्हणून घ्या पण ते कॅशेमध्ये _लिहू नका_.

3. इतर कोणत्याही मूल्यासाठी, वरचे चार बिट्स अतिरिक्त बाइट्सची संख्या म्हणून घ्या आणि खालचे चार बिट्स कॅशे कीचे सर्वात महत्त्वपूर्ण बिट्स म्हणून घ्या. येथे काही उदाहरणे आहेत:

   | कॉल डेटामधील बाइट्स | कॅशे की |
   | :---------------- | --------: |
   | 0x0F              |      0x0F |
   | 0x10,0x10         |      0x10 |
   | 0x12,0xAC         |    0x02AC |
   | 0x2D,0xEA, 0xD6   |  0x0DEAD6 |

## कॅशे हाताळणी {#cache-manipulation}

कॅशे [`कॅशे.sol`](https://github.com/qbzzt/20220915-all-you-can-cache/blob/main/src/Cache.sol) मध्ये लागू केले आहे. आपण ते ओळीनुसार पाहूया.

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity ^0.8.13;


contract Cache {

    bytes1 public constant INTO_CACHE = 0xFF;
    bytes1 public constant DONT_CACHE = 0xFE;
```

हे स्थिरांक अशा विशेष प्रकरणांचा अर्थ लावण्यासाठी वापरले जातात जिथे आपण सर्व माहिती प्रदान करतो आणि ती कॅशेमध्ये लिहिली जावी की नाही हे ठरवतो. कॅशेमध्ये लिहिण्यासाठी पूर्वी न वापरलेल्या स्टोरेज स्लॉट्समध्ये दोन [`SSTORE`](https://www.evm.codes/#55) ऑपरेशन्स आवश्यक असतात, ज्यासाठी प्रत्येकी 22100 गॅस खर्च येतो, त्यामुळे आपण ते ऐच्छिक बनवतो.

```solidity

    mapping(uint => uint) public val2key;
```

मूल्ये आणि त्यांच्या कीजमधील एक [मॅपिंग](https://www.geeksforgeeks.org/solidity/solidity-mappings/). तुम्ही व्यवहार पाठवण्यापूर्वी मूल्यांना एन्कोड करण्यासाठी ही माहिती आवश्यक आहे.

```solidity
    // लोकेशन n मध्ये की n+1 चे मूल्य आहे, कारण आपल्याला जतन करणे आवश्यक आहे
    // शून्य "कॅशेमध्ये नाही" म्हणून.
    uint[] public key2val;
```

कीजवरून मूल्यांपर्यंत मॅपिंग करण्यासाठी आपण ॲरे वापरू शकतो कारण आपण कीज नियुक्त करतो आणि सोपे करण्यासाठी आपण ते क्रमाने करतो.

```solidity
    function cacheRead(uint _key) public view returns (uint) {
        require(_key <= key2val.length, "Reading uninitialize cache entry");
        return key2val[_key-1];
    }  // cacheRead
```

कॅशेमधून मूल्य वाचा.

```solidity
    // मूल्य आधीपासून कॅशेमध्ये नसल्यास ते कॅशेमध्ये लिहा
    // केवळ चाचणी कार्य करण्यासाठी सार्वजनिक (public) आहे
    function cacheWrite(uint _value) public returns (uint) {
        // मूल्य आधीपासून कॅशेमध्ये असल्यास, वर्तमान की परत करा
        if (val2key[_value] != 0) {
            return val2key[_value];
        }
```

समान मूल्य कॅशेमध्ये एकापेक्षा जास्त वेळा टाकण्यात काही अर्थ नाही. जर मूल्य आधीपासूनच तिथे असेल, तर फक्त विद्यमान की परत करा.

```solidity
        // 0xFE ही एक विशेष केस असल्याने, कॅशेमध्ये सामावून घेता येणारी सर्वात मोठी की
        // 0x0D आणि त्यानंतर 15 0xFF's आहे. जर कॅशेची लांबी आधीपासूनच तितकी
        // मोठी असेल, तर अयशस्वी (fail) करा.
        //                              1 2 3 4 5 6 7 8 9 A B C D E F
        require(key2val.length+1 < 0x0DFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF,
            "cache overflow");
```

मला वाटत नाही की आपल्याला कधीही इतका मोठा कॅशे मिळेल (अंदाजे 1.8\*10<sup>37</sup> नोंदी, ज्या साठवण्यासाठी सुमारे 10<sup>27</sup> TB लागेल). तथापि, मला ["640kB नेहमीच पुरेसे असेल"](https://quoteinvestigator.com/2011/09/08/640k-enough/) हे आठवण्याइतपत मी जुना आहे. ही चाचणी खूप स्वस्त आहे.

```solidity
        // पुढील की वापरून मूल्य लिहा
        val2key[_value] = key2val.length+1;
```

रिव्हर्स लुकअप जोडा (मूल्यावरून कीकडे).

```solidity
        key2val.push(_value);
```

फॉरवर्ड लुकअप जोडा (कीवरून मूल्याकडे). कारण आपण मूल्ये क्रमाने नियुक्त करतो, आपण ते फक्त शेवटच्या ॲरे मूल्यानंतर जोडू शकतो.

```solidity
        return key2val.length;
    }  // cacheWrite
```

`key2val` ची नवीन लांबी परत करा, जो सेल आहे जिथे नवीन मूल्य साठवले जाते.

```solidity
    function _calldataVal(uint startByte, uint length)
        private pure returns (uint)
```

हे फंक्शन अनियंत्रित लांबीच्या (32 बाइट्सपर्यंत, वर्ड आकार) कॉल डेटामधून मूल्य वाचते.

```solidity
    {
        uint _retVal;

        require(length < 0x21,
            "_calldataVal length limit is 32 bytes");
        require(length + startByte <= msg.data.length,
            "_calldataVal trying to read beyond calldatasize");
```

हे फंक्शन अंतर्गत आहे, त्यामुळे जर उर्वरित कोड योग्यरित्या लिहिला असेल तर या चाचण्या आवश्यक नाहीत. तथापि, त्यांना जास्त खर्च येत नाही त्यामुळे आपण त्या ठेवू शकतो.

```solidity
        assembly {
            _retVal := calldataload(startByte)
        }
```

हा कोड [Yul](https://docs.soliditylang.org/en/v0.8.16/yul.html) मध्ये आहे. तो कॉल डेटामधून 32 बाइट मूल्य वाचतो. कॉल डेटा `startByte+32` च्या आधी थांबला तरीही हे कार्य करते कारण EVM मधील अनिनिशियलाइज्ड जागा शून्य मानली जाते.

```solidity
        _retVal = _retVal >> (256-length*8);
```

आपल्याला 32 बाइट मूल्याची आवश्यकता असेलच असे नाही. हे अतिरिक्त बाइट्स काढून टाकते.

```solidity
        return _retVal;
    } // _calldataVal


    // कॉल डेटा मधून _fromByte पासून सुरू होणारा एकच पॅरामीटर वाचा
    function _readParam(uint _fromByte) internal
        returns (uint _nextByte, uint _parameterValue)
    {
```

कॉल डेटामधून एकच पॅरामीटर वाचा. लक्षात घ्या की आपल्याला फक्त वाचलेले मूल्यच नाही, तर पुढील बाइटचे स्थान देखील परत करणे आवश्यक आहे कारण पॅरामीटर्स 1 बाइट लांबीपासून 33 बाइट्सपर्यंत असू शकतात.

```solidity
        // पहिला बाइट आपल्याला उर्वरित भागाचा अर्थ कसा लावायचा हे सांगतो
        uint8 _firstByte;

        _firstByte = uint8(_calldataVal(_fromByte, 1));
```

Solidity संभाव्य धोकादायक [इम्प्लिसिट टाइप कन्व्हर्जन्स](https://docs.soliditylang.org/en/v0.8.16/types.html#implicit-conversions) ला मनाई करून बग्सची संख्या कमी करण्याचा प्रयत्न करते. डाउनग्रेड, उदाहरणार्थ 256 बिट्सवरून 8 बिट्सपर्यंत, स्पष्ट असणे आवश्यक आहे.

```solidity

        // मूल्य वाचा, परंतु ते कॅशेमध्ये लिहू नका
        if (_firstByte == uint8(DONT_CACHE))
            return(_fromByte+33, _calldataVal(_fromByte+1, 32));

        // मूल्य वाचा, आणि ते कॅशेमध्ये लिहा
        if (_firstByte == uint8(INTO_CACHE)) {
            uint _param = _calldataVal(_fromByte+1, 32);
            cacheWrite(_param);
            return(_fromByte+33, _param);
        }

        // जर आपण येथे पोहोचलो तर याचा अर्थ असा की आपल्याला कॅशेमधून वाचण्याची आवश्यकता आहे

        // वाचण्यासाठी अतिरिक्त बाइट्सची संख्या
        uint8 _extraBytes = _firstByte / 16;
```

खालचे [निबल](https://en.wikipedia.org/wiki/Nibble) घ्या आणि कॅशेमधून मूल्य वाचण्यासाठी ते इतर बाइट्ससह एकत्र करा.

```solidity
        uint _key = (uint256(_firstByte & 0x0F) << (8*_extraBytes)) +
            _calldataVal(_fromByte+1, _extraBytes);

        return (_fromByte+_extraBytes+1, cacheRead(_key));

    }  // _readParam


    // n पॅरामीटर्स वाचा (फंक्शन्सना माहित असते की त्यांना किती पॅरामीटर्स अपेक्षित आहेत)
    function _readParams(uint _paramNum) internal returns (uint[] memory) {
```

आपल्याकडे असलेल्या पॅरामीटर्सची संख्या आपण कॉल डेटामधूनच मिळवू शकतो, परंतु आपल्याला कॉल करणाऱ्या फंक्शन्सना माहित असते की त्यांना किती पॅरामीटर्स अपेक्षित आहेत. त्यांना आपल्याला सांगू देणे सोपे आहे.

```solidity
        // आपण वाचलेले पॅरामीटर्स
        uint[] memory params = new uint[](_paramNum);

        // पॅरामीटर्स बाइट 4 पासून सुरू होतात, त्यापूर्वी फंक्शन सिग्नेचर असते
        uint _atByte = 4;

        for(uint i=0; i<_paramNum; i++) {
            (_atByte, params[i]) = _readParam(_atByte);
        }
```

तुम्हाला आवश्यक असलेली संख्या मिळेपर्यंत पॅरामीटर्स वाचा. जर आपण कॉल डेटाच्या शेवटी गेलो, तर `_readParams` कॉल पूर्ववत करेल.

```solidity

        return(params);
    }   // readParams

    // _readParams ची चाचणी करण्यासाठी, चार पॅरामीटर्स वाचण्याची चाचणी करा
    function fourParam() public
        returns (uint256,uint256,uint256,uint256)
    {
        uint[] memory params;
        params = _readParams(4);
        return (params[0], params[1], params[2], params[3]);
    }    // fourParam
```

Foundry चा एक मोठा फायदा असा आहे की ते Solidity मध्ये चाचण्या लिहिण्याची परवानगी देते ([खाली कॅशेची चाचणी पहा](#testing-the-cache)). यामुळे युनिट चाचण्या खूप सोप्या होतात. हे एक फंक्शन आहे जे चार पॅरामीटर्स वाचते आणि ते परत करते जेणेकरून चाचणी ते योग्य असल्याची पडताळणी करू शकेल.

```solidity
    // मूल्य मिळवा, ते एन्कोड करणारे बाइट्स परत करा (शक्य असल्यास कॅशे वापरून)
    function encodeVal(uint _val) public view returns(bytes memory) {
```

`encodeVal` हे एक फंक्शन आहे ज्याला साखळीबाह्य कोड कॅशे वापरणारा कॉल डेटा तयार करण्यात मदत करण्यासाठी कॉल करतो. ते एकच मूल्य प्राप्त करते आणि ते एन्कोड करणारे बाइट्स परत करते. हे फंक्शन एक `view` आहे, त्यामुळे त्याला व्यवहाराची आवश्यकता नसते आणि बाह्यरित्या कॉल केल्यावर कोणताही गॅस खर्च होत नाही.

```solidity
        uint _key = val2key[_val];

        // मूल्य अद्याप कॅशेमध्ये नाही, ते जोडा
        if (_key == 0)
            return bytes.concat(INTO_CACHE, bytes32(_val));
```

[EVM](/developers/docs/evm/) मध्ये सर्व अनिनिशियलाइज्ड स्टोरेज शून्य असल्याचे गृहीत धरले जाते. त्यामुळे जर आपण तिथे नसलेल्या मूल्यासाठी की शोधली, तर आपल्याला शून्य मिळते. त्या बाबतीत ते एन्कोड करणारे बाइट्स `INTO_CACHE` असतात (जेणेकरून ते पुढच्या वेळी कॅशे केले जाईल), आणि त्यानंतर वास्तविक मूल्य असते.

```solidity
        // जर की <0x10 असेल, तर ती सिंगल बाइट म्हणून परत करा
        if (_key < 0x10)
            return bytes.concat(bytes1(uint8(_key)));
```

सिंगल बाइट्स सर्वात सोपे आहेत. आपण फक्त [`bytes.concat`](https://docs.soliditylang.org/en/v0.8.16/types.html#the-functions-bytes-concat-and-string-concat) वापरून `bytes<n>` प्रकाराला बाइट ॲरेमध्ये बदलतो जो कोणत्याही लांबीचा असू शकतो. नावाकडे दुर्लक्ष करून, जेव्हा फक्त एक आर्ग्युमेंट दिले जाते तेव्हा ते उत्तम प्रकारे कार्य करते.

```solidity
        // दोन बाइट मूल्य, 0x1vvv म्हणून एन्कोड केलेले
        if (_key < 0x1000)
            return bytes.concat(bytes2(uint16(_key) | 0x1000));
```

जेव्हा आपल्याकडे 16<sup>3</sup> पेक्षा कमी की असते, तेव्हा आपण ती दोन बाइट्समध्ये व्यक्त करू शकतो. आपण प्रथम `_key`, जे 256 बिट मूल्य आहे, त्याला 16 बिट मूल्यामध्ये रूपांतरित करतो आणि पहिल्या बाइटमध्ये अतिरिक्त बाइट्सची संख्या जोडण्यासाठी लॉजिकल OR वापरतो. नंतर आपण ते फक्त `bytes2` मूल्यामध्ये टाकतो, ज्याचे `bytes` मध्ये रूपांतर केले जाऊ शकते.

```solidity

        // परंतु हे एक व्ह्यू (view) फंक्शन आहे त्यामुळे मी प्रोग्रामरचा वेळ आणि
        // साधेपणा यासाठी ऑप्टिमाइझ करत आहे.

        if (_key < 16*256**2)
            return bytes.concat(bytes3(uint24(_key) | (0x2 * 16 * 256**2)));
        if (_key < 16*256**3)
            return bytes.concat(bytes4(uint32(_key) | (0x3 * 16 * 256**3)));
             .
             .
             .
        if (_key < 16*256**14)
            return bytes.concat(bytes15(uint120(_key) | (0xE * 16 * 256**14)));
        if (_key < 16*256**15)
            return bytes.concat(bytes16(uint128(_key) | (0xF * 16 * 256**15)));
```

इतर मूल्ये (3 बाइट्स, 4 बाइट्स, इ.) त्याच प्रकारे हाताळली जातात, फक्त वेगवेगळ्या फील्ड आकारांसह.

```solidity

        revert("Error in encodeVal, should not happen");
```

जर आपण येथे पोहोचलो तर याचा अर्थ आपल्याला अशी की मिळाली आहे जी 16\*256<sup>15</sup> पेक्षा कमी नाही. परंतु `cacheWrite` कीज मर्यादित करते त्यामुळे आपण 14\*256<sup>16</sup> पर्यंत देखील पोहोचू शकत नाही (ज्याचा पहिला बाइट 0xFE असेल, त्यामुळे तो `DONT_CACHE` सारखा दिसेल). परंतु भविष्यातील प्रोग्रामरने एखादा बग आणल्यास चाचणी जोडण्यासाठी आपल्याला जास्त खर्च येत नाही.

### कॅशेची चाचणी करणे {#testing-the-cache}

Foundry चा एक फायदा असा आहे की [ते तुम्हाला Solidity मध्ये चाचण्या लिहिण्याची परवानगी देते](https://getfoundry.sh/forge/tests/overview/), ज्यामुळे युनिट चाचण्या लिहिणे सोपे होते. `Cache` क्लाससाठी चाचण्या [येथे](https://github.com/qbzzt/20220915-all-you-can-cache/blob/main/test/Cache.t.sol) आहेत. चाचणी कोड पुनरावृत्ती करणारा असल्यामुळे, जसे की चाचण्या असतात, हा लेख फक्त मनोरंजक भाग स्पष्ट करतो.

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity ^0.8.13;

import "forge-std/Test.sol";


// कन्सोलसाठी `forge test -vv` चालवणे आवश्यक आहे.
import "forge-std/console.sol";
```

हे फक्त बॉयलरप्लेट आहे जे चाचणी पॅकेज आणि `console.log` वापरण्यासाठी आवश्यक आहे.

```solidity
import "src/Cache.sol";
```

आपण ज्या कॉन्ट्रॅक्टची चाचणी करत आहोत ते आपल्याला माहित असणे आवश्यक आहे.

```solidity
contract CacheTest is Test {
    Cache cache;

    function setUp() public {
        cache = new Cache();
    }
```

प्रत्येक चाचणीपूर्वी `setUp` फंक्शनला कॉल केले जाते. या प्रकरणात आपण फक्त एक नवीन कॅशे तयार करतो, जेणेकरून आपल्या चाचण्यांचा एकमेकांवर परिणाम होणार नाही.

```solidity

```

चाचण्या ही अशी फंक्शन्स आहेत ज्यांची नावे `test` ने सुरू होतात. हे फंक्शन मूलभूत कॅशे कार्यक्षमतेची तपासणी करते, मूल्ये लिहिते आणि ती पुन्हा वाचते.

```solidity

            cache.cacheWrite(i*i);

        for(uint i=1; i<5000; i++) {
            assertEq(cache.cacheRead(i), i*i);
```

[`assert...` फंक्शन्स](https://getfoundry.sh/reference/forge-std/std-assertions/) वापरून तुम्ही प्रत्यक्ष चाचणी कशी करता ते येथे आहे. या प्रकरणात, आपण तपासतो की आपण लिहिलेले मूल्य तेच आहे जे आपण वाचले आहे. आपण `cache.cacheWrite` चा परिणाम सोडून देऊ शकतो कारण आपल्याला माहित आहे की कॅशे की रेषीयपणे (linearly) नियुक्त केल्या जातात.

```solidity

    }    // testCaching


    // समान मूल्य अनेक वेळा कॅशे करा, की तशीच राहील याची खात्री करा
    // समान
    function testRepeatCaching() public {
        for(uint i=1; i<100; i++) {
            uint _key1 = cache.cacheWrite(i);
            uint _key2 = cache.cacheWrite(i);

```

प्रथम आपण प्रत्येक मूल्य कॅशेमध्ये दोनदा लिहितो आणि की समान असल्याची खात्री करतो (म्हणजे दुसरे लेखन खरोखर झाले नाही).

```solidity

            uint _key = cache.cacheWrite(i);
            assertEq(_key, i);
        }
    }    // testRepeatCaching
```

सैद्धांतिकदृष्ट्या असा एखादा बग असू शकतो जो सलग कॅशे लेखनावर परिणाम करत नाही. त्यामुळे येथे आपण काही लेखन करतो जे सलग नाहीत आणि पाहतो की मूल्ये अद्याप पुन्हा लिहिली गेली नाहीत.

```solidity
    // मेमरी बफरमधून uint वाचा (आपल्याला तेच पॅरामीटर्स परत मिळतील याची खात्री करण्यासाठी
    // जे आपण पाठवले होते)
    function toUint256(bytes memory _bytes, uint256 _start) internal pure
        returns (uint256)
```

`bytes memory` बफरमधून 256 बिट शब्द वाचा. हे युटिलिटी फंक्शन आपल्याला हे सत्यापित करू देते की जेव्हा आपण कॅशे वापरणारा फंक्शन कॉल चालवतो तेव्हा आपल्याला योग्य परिणाम मिळतात.

```solidity
    {
        require(_bytes.length >= _start + 32, "toUint256_outOfBounds");
        uint256 tempUint;

        assembly {
            tempUint := mload(add(add(_bytes, 0x20), _start))
        }
```

Yul `uint256` च्या पलीकडे डेटा स्ट्रक्चर्सना समर्थन देत नाही, त्यामुळे जेव्हा तुम्ही मेमरी बफर `_bytes` सारख्या अधिक अत्याधुनिक डेटा स्ट्रक्चरचा संदर्भ देता, तेव्हा तुम्हाला त्या स्ट्रक्चरचा पत्ता मिळतो. Solidity `bytes memory` मूल्यांना 32 बाइट शब्द म्हणून संग्रहित करते ज्यामध्ये लांबी असते, त्यानंतर प्रत्यक्ष बाइट्स असतात, त्यामुळे बाइट क्रमांक `_start` मिळवण्यासाठी आपल्याला `_bytes+32+_start` ची गणना करणे आवश्यक आहे.

```solidity

        return tempUint;

    // fourParams() साठी फंक्शन सिग्नेचर, सौजन्याने
    // https://www.4byte.directory/signatures/?bytes4_signature=0x3edc1e6d
    bytes4 constant FOUR_PARAMS = 0x3edc1e6d;
```

चाचणीसाठी आपल्याला आवश्यक असलेले काही स्थिरांक (constants).

कॅशे वापरून फंक्शनला कॉल करण्यासाठी आपण सामान्य ABI यंत्रणा वापरू शकत नाही, त्यामुळे आपल्याला निम्न स्तरावरील (low level) [`<address>.call()`](https://docs.soliditylang.org/en/v0.8.16/types.html#members-of-addresses) यंत्रणा वापरण्याची आवश्यकता आहे. ती यंत्रणा इनपुट म्हणून `bytes memory` घेते, आणि आउटपुट म्हणून ते (तसेच बुलियन मूल्य) परत करते.

एकाच कॉन्ट्रॅक्टसाठी कॅशे केलेली फंक्शन्स (थेट व्यवहारांमधून कॉल करण्यासाठी) आणि कॅशे न केलेली फंक्शन्स (इतर स्मार्ट कॉन्ट्रॅक्ट्समधून कॉल करण्यासाठी) या दोन्हीला समर्थन देणे उपयुक्त आहे. ते करण्यासाठी आपल्याला सर्वकाही [एका `fallback` फंक्शनमध्ये](https://docs.soliditylang.org/en/v0.8.16/contracts.html#fallback-function) ठेवण्याऐवजी योग्य फंक्शनला कॉल करण्यासाठी Solidity यंत्रणेवर अवलंबून राहणे सुरू ठेवणे आवश्यक आहे. असे केल्याने संयोज्यता खूप सोपी होते. बहुतेक प्रकरणांमध्ये फंक्शन ओळखण्यासाठी एकच बाइट पुरेसा असेल, त्यामुळे आपण तीन बाइट्स वाया घालवत आहोत. सध्याच्या OP Stack शुल्क सूत्रानुसार ते तीन बाइट्स सेंटचा एक छोटासा अंश जोडतात (काही असल्यास, लेखाच्या शीर्षस्थानी असलेली टीप पहा), जी सोप्या, कमी बग प्रवण (bug prone) कोडची वाजवी किंमत आहे.


## एक नमुना ॲप्लिकेशन {#a-sample-app}

Solidity मध्ये चाचण्या लिहिणे खूप चांगले आहे, परंतु शेवटी विकेंद्रित ॲप्लिकेशन (dapp) उपयुक्त ठरण्यासाठी त्याला साखळीच्या बाहेरील विनंत्यांवर प्रक्रिया करण्यास सक्षम असणे आवश्यक आहे. हा लेख `WORM` सह dapp मध्ये कॅशिंग कसे वापरावे हे दर्शवितो, ज्याचा अर्थ "एकदा लिहा, अनेकदा वाचा" (Write Once, Read Many) असा होतो. जर एखादी की अद्याप लिहिलेली नसेल, तर तुम्ही त्यावर मूल्य लिहू शकता. जर की आधीच लिहिलेली असेल, तर तुम्हाला रिव्हर्ट (पूर्ववत) मिळते.

### कॉन्ट्रॅक्ट {#the-contract}

[हे कॉन्ट्रॅक्ट आहे](https://github.com/qbzzt/20220915-all-you-can-cache/blob/main/src/WORM.sol). आपण `Cache` आणि `CacheTest` सह जे आधीच केले आहे त्याचीच हे बहुतांशी पुनरावृत्ती करते, त्यामुळे आपण फक्त मनोरंजक भाग कव्हर करतो.

```solidity
import "./Cache.sol";

contract WORM is Cache {
```

`Cache` वापरण्याचा सर्वात सोपा मार्ग म्हणजे ते आपल्या स्वतःच्या कॉन्ट्रॅक्टमध्ये इनहेरिट करणे.

```solidity
    function writeEntryCached() external {
        uint[] memory params = _readParams(2);
        writeEntry(params[0], params[1]);
    }    // writeEntryCached
```

हे फंक्शन वरील `CacheTest` मधील `fourParam` सारखेच आहे. आपण ABI वैशिष्ट्यांचे पालन करत नसल्यामुळे, फंक्शनमध्ये कोणतेही पॅरामीटर्स घोषित न करणे चांगले.

```solidity
    // आम्हाला कॉल करणे सोपे करा
    // writeEntryCached() साठी फंक्शन सिग्नेचर, सौजन्य
    // https://www.4byte.directory/signatures/?bytes4_signature=0xe4e4f2d3
    bytes4 constant public WRITE_ENTRY_CACHED = 0xe4e4f2d3;
```

`writeEntryCached` ला कॉल करणाऱ्या बाह्य कोडला `worm.writeEntryCached` वापरण्याऐवजी मॅन्युअली कॉल डेटा तयार करावा लागेल, कारण आपण ABI वैशिष्ट्यांचे पालन करत नाही. हे स्थिर मूल्य असण्याने ते लिहिणे सोपे होते.

लक्षात घ्या की जरी आपण `WRITE_ENTRY_CACHED` ला स्थिती व्हेरिएबल म्हणून परिभाषित केले असले तरी, ते बाह्यरित्या वाचण्यासाठी त्याचे गेटर फंक्शन, `worm.WRITE_ENTRY_CACHED()` वापरणे आवश्यक आहे.

```solidity
    function readEntry(uint key) public view
        returns (uint _value, address _writtenBy, uint _writtenAtBlock)
```

रीड फंक्शन एक `view` आहे, त्यामुळे त्याला व्यवहाराची आवश्यकता नसते आणि गॅस खर्च होत नाही. परिणामी, पॅरामीटरसाठी कॅशे वापरण्याचा कोणताही फायदा नाही. व्ह्यू फंक्शन्ससह मानक यंत्रणा वापरणे सर्वोत्तम आहे जी सोपी आहे.

### चाचणी कोड {#the-testing-code}

[हा कॉन्ट्रॅक्टसाठी चाचणी कोड आहे](https://github.com/qbzzt/20220915-all-you-can-cache/blob/main/test/WORM.t.sol). पुन्हा, आपण फक्त मनोरंजक गोष्टी पाहूया.

```solidity
    function testWReadWrite() public {
        worm.writeEntry(0xDEAD, 0x60A7);

        vm.expectRevert(bytes("entry already written"));
        worm.writeEntry(0xDEAD, 0xBEEF);
```

[अशा प्रकारे (`vm.expectRevert`)](https://getfoundry.sh/reference/cheatcodes/expect-revert/) आपण Foundry चाचणीमध्ये निर्दिष्ट करतो की पुढील कॉल अयशस्वी झाला पाहिजे, आणि अपयशाचे नोंदवलेले कारण. हे तेव्हा लागू होते जेव्हा आपण कॉल डेटा तयार करण्याऐवजी आणि निम्न स्तरावरील इंटरफेस (`<contract>.call()`, इ.) वापरून कॉन्ट्रॅक्टला कॉल करण्याऐवजी `<contract>.<function name>()` सिंटॅक्स वापरतो.

```solidity
    function testReadWriteCached() public {
        uint cacheGoat = worm.cacheWrite(0x60A7);
```

येथे आपण या वस्तुस्थितीचा वापर करतो की `cacheWrite` कॅशे की परत करते. हे असे काही नाही जे आपण उत्पादनात (production) वापरण्याची अपेक्षा करू, कारण `cacheWrite` स्थिती बदलते, आणि त्यामुळे केवळ व्यवहारादरम्यान कॉल केले जाऊ शकते. व्यवहारांना रिटर्न व्हॅल्यूज नसतात, जर त्यांचे परिणाम असतील तर ते परिणाम घटना म्हणून उत्सर्जित (emitted) केले जावेत. त्यामुळे `cacheWrite` रिटर्न व्हॅल्यू केवळ ऑनचेन कोडमधून प्रवेशयोग्य आहे, आणि ऑनचेन कोडला पॅरामीटर कॅशिंगची आवश्यकता नाही.

```solidity
        (_success,) = address(worm).call(_callInput);
```

अशा प्रकारे आपण Solidity ला सांगतो की `<contract address>.call()` ला दोन रिटर्न व्हॅल्यूज असल्या तरी, आपल्याला फक्त पहिल्याची काळजी आहे.

```solidity
        (_success,) = address(worm).call(_callInput);
        assertEq(_success, false);
```

आपण निम्न स्तरावरील `<address>.call()` फंक्शन वापरत असल्याने, आपण `vm.expectRevert()` वापरू शकत नाही आणि आपल्याला कॉलमधून मिळणाऱ्या बुलियन यश मूल्याकडे पहावे लागेल.

```solidity
    event EntryWritten(uint indexed key, uint indexed value);

        .
        .
        .

        _callInput = bytes.concat(
            worm.WRITE_ENTRY_CACHED(), worm.encodeVal(a), worm.encodeVal(b));
        vm.expectEmit(true, true, false, false);
        emit EntryWritten(a, b);
        (_success,) = address(worm).call(_callInput);
```

अशा प्रकारे आपण Foundry मध्ये कोड [घटना योग्यरित्या उत्सर्जित करतो](https://getfoundry.sh/reference/cheatcodes/expect-emit/) हे सत्यापित करतो.

### क्लायंट {#the-client}

Solidity चाचण्यांसह तुम्हाला न मिळणारी एक गोष्ट म्हणजे JavaScript कोड जो तुम्ही कट करून तुमच्या स्वतःच्या ॲप्लिकेशनमध्ये पेस्ट करू शकता. या ट्यूटोरियलच्या मूळ आवृत्तीने WORM ला Optimism गोर्ली वर प्रस्थापित केले होते, जे तेव्हापासून बंद झाले आहे. नमुना रिपॉझिटरी अजूनही Optimism गोर्ली कडे निर्देश करते, त्यामुळे आज क्लायंट चालवण्यासाठी तुम्हाला स्वतः WORM ला [OP Sepolia](https://docs.optimism.io/op-stack/introduction/op-stack) वर प्रस्थापित करणे आणि क्लायंटला तुमच्या प्रस्थापनेकडे निर्देशित करणे आवश्यक आहे.

[तुम्ही क्लायंटसाठी JavaScript कोड येथे पाहू शकता](https://github.com/qbzzt/20220915-all-you-can-cache/blob/main/javascript/index.js). ते वापरण्यासाठी, तुम्हाला [Foundry](https://getfoundry.sh/introduction/installation/), [Node.js](https://nodejs.org/), आणि काही OP Sepolia ETH असलेले खाते आवश्यक आहे. [Optimism चे फॉसेट डॉक्स](https://docs.optimism.io/app-developers/tools-sdks/faucets) सध्याच्या टेस्टनेट फॉसेट्सची यादी देतात.

1. `forge-std` सबमॉड्यूलसह गिट रिपॉझिटरी क्लोन करा आणि कॉन्ट्रॅक्ट्स तयार करा. क्लायंट `out/WORM.sol/WORM.json` मधून WORM ABI आणि बाइटकोड वाचतो, जे केवळ `forge build` नंतर अस्तित्वात असते.

   ```sh
   git clone --recurse-submodules https://github.com/qbzzt/20220915-all-you-can-cache.git
   cd 20220915-all-you-can-cache
   forge build
   ```

   Forge चेतावणी देते की `foundry.toml` जुने `[default]` विभाग नाव वापरते. तुम्ही या चेतावणीकडे दुर्लक्ष करू शकता, किंवा `forge config --fix` चालवू शकता.

2. तुमच्या निधी असलेल्या खात्याची खाजगी की एन्क्रिप्टेड Foundry कीस्टोअरमध्ये आयात करा, आणि त्याचा वापर OP Sepolia वर [WORM प्रस्थापित करण्यासाठी](https://getfoundry.sh/reference/forge/create) करा.

   ```sh
   cast wallet import op-sepolia-deployer --interactive
   forge create src/WORM.sol:WORM --rpc-url https://sepolia.optimism.io --account op-sepolia-deployer --broadcast
   ```

   `--broadcast` शिवाय, `forge create` केवळ प्रस्थापनेचे अनुकरण करते. आउटपुटच्या `Deployed to:` ओळीवरून पत्ता कॉपी करा.

3. `javascript/index.js` संपादित करा. या ओळीतील जुना Optimism गोर्ली पत्ता तुमच्या प्रस्थापनेच्या पत्त्याने बदला:


   तुम्ही दोन `console.log` ओळींमध्ये `https://goerli-optimism.etherscan.io` च्या जागी `https://sepolia-optimism.etherscan.io` देखील बदलू शकता, जेणेकरून क्लायंट प्रिंट करत असलेल्या लिंक्स काम करतील.

## निष्कर्ष {#conclusion}

या लेखातील कोड एक संकल्पनेचा पुरावा (proof of concept) आहे, ज्याचा उद्देश ही कल्पना समजण्यास सोपी करणे हा आहे. उत्पादन-सज्ज (production-ready) प्रणालीसाठी तुम्हाला काही अतिरिक्त कार्यक्षमता लागू करायची असू शकते:

- `uint256` नसलेली मूल्ये हाताळा. उदाहरणार्थ, स्ट्रिंग्ज.
- जागतिक (global) कॅशेऐवजी, कदाचित वापरकर्ते आणि कॅशे यांच्यात मॅपिंग असावे. भिन्न वापरकर्ते भिन्न मूल्ये वापरतात.
- पत्त्यांसाठी वापरलेली मूल्ये इतर उद्देशांसाठी वापरल्या जाणाऱ्या मूल्यांपेक्षा वेगळी असतात. फक्त पत्त्यांसाठी वेगळी कॅशे असणे अर्थपूर्ण असू शकते.
- सध्या, कॅशे की "प्रथम येणाऱ्यास, सर्वात लहान की" अल्गोरिदमवर आहेत. पहिली सोळा मूल्ये एक बाइट म्हणून पाठविली जाऊ शकतात. पुढील 4080 मूल्ये दोन बाइट्स म्हणून पाठविली जाऊ शकतात. पुढील अंदाजे दशलक्ष मूल्ये तीन बाइट्स आहेत, इ. उत्पादन प्रणालीने कॅशे नोंदींवर वापर काउंटर ठेवले पाहिजेत आणि त्यांची पुनर्रचना केली पाहिजे जेणेकरून सोळा _सर्वाधिक सामान्य_ मूल्ये एक बाइट असतील, पुढील 4080 सर्वाधिक सामान्य मूल्ये दोन बाइट्स असतील, इ.

  तथापि, हे संभाव्यतः धोकादायक ऑपरेशन आहे. खालील घटनांच्या क्रमाची कल्पना करा:

  1. नोम नेव्ह (Noam Naive) ज्या पत्त्यावर टोकन्स पाठवू इच्छितो तो पत्ता एन्कोड करण्यासाठी `encodeVal` ला कॉल करतो. तो पत्ता ॲप्लिकेशनवर वापरल्या गेलेल्या पहिल्या पत्त्यांपैकी एक आहे, त्यामुळे एन्कोड केलेले मूल्य 0x06 आहे. हे एक `view` फंक्शन आहे, व्यवहार नाही, त्यामुळे ते नोम आणि तो वापरत असलेल्या नोडच्या दरम्यान आहे, आणि इतर कोणालाही त्याबद्दल माहिती नाही

  2. ओवेन ओनर (Owen Owner) कॅशे पुनर्रचना ऑपरेशन चालवतो. खूप कमी लोक प्रत्यक्षात तो पत्ता वापरतात, त्यामुळे तो आता 0x201122 म्हणून एन्कोड केला आहे. एक वेगळे मूल्य, 10<sup>18</sup>, ला 0x06 नियुक्त केले आहे.

  3. नोम नेव्ह त्याचे टोकन्स 0x06 वर पाठवतो. ते `0x0000000000000000000000000de0b6b3a7640000` पत्त्यावर जातात, आणि कोणालाही त्या पत्त्याची खाजगी की माहित नसल्यामुळे, ते तिथेच अडकतात. नोम _खूश नाही_.

  ही समस्या सोडवण्याचे मार्ग आहेत, आणि कॅशे पुनर्रचनेदरम्यान मेमपूलमध्ये असलेल्या व्यवहारांची संबंधित समस्या सोडवण्याचे मार्ग आहेत, परंतु तुम्हाला याची जाणीव असणे आवश्यक आहे.
