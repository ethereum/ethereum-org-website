[イーサリアム](/)は、イーサリアムのクライアントソフトウェアを実行するコンピューターで構成されるネットワークです。これらのコンピューターはそれぞれ「ノード」と呼ばれます。クライアントソフトウェアにより、ノードはイーサリアム・ネットワーク上でデータを送受信し、イーサリアムのプロトコルルールに照らしてデータを検証することができます。ノードはディスクストレージに大量の履歴データを保持し、ネットワーク上の他のノードからブロックと呼ばれる新しい情報のパケットを受け取ったときにそれを追加します。これは、ノードがネットワークの他の部分と一貫した情報を持っていることを常に確認するために必要です。つまり、ノードを実行するには大量のディスク容量が必要になる場合があります。一部のノード操作では、大量のRAMも必要になる場合があります。

実行クライアントは、もはやそのすべてのデータを保持する必要はありません。2025年7月以降、実行クライアントは[マージ](/roadmap/merge/)以前のブロックの本体とレシートを破棄できるようになり、イーサリアムのロードマップには、時間の経過とともにチェーンの履歴をさらに破棄することが含まれています。その履歴は、ブロックエクスプローラー、インデクサー、または古いトランザクションを検索するウォレットなど、それを必要とする誰もが引き続き利用できるようにしておく必要があります。

ポータル・ネットワークは、この履歴を小さな断片に分割して多くのノード間で共有することで、利用可能な状態に保ちます。どのノードもすべてを保存する必要はなく、ノードは任意の断片を取得し、送信元のノードを信頼することなく、すでに保持しているデータと照合して確認することができます。

## なぜポータル・ネットワークが必要なのか {#why-do-we-need-portal-network}

イーサリアムのノードは、イーサリアムのブロックチェーンの完全または部分的なコピーを独自に保存します。このローカルコピーは、トランザクションを検証し、ノードが正しいチェーンに従っていることを確認するために使用されます。このローカルに保存されたデータにより、ノードは他のエンティティを信頼することなく、受信したデータが有効で正しいことを独立して検証できます。

このブロックチェーンのローカルコピーと、関連する状態およびレシートのデータは、ノードのハードディスク上で多くのスペースを占有します。たとえば、コンセンサス・クライアントとペアになった[Geth（ゲス）](https://geth.ethereum.org)を使用してノードを実行するには、4TBのSSDが推奨されます。完全なチェーン履歴を持つ場合、Geth（ゲス）は1.8TB以上のディスク容量を占有し（2026年9月現在）、チェーンとともに増え続けています。

つまり、イーサリアムに大量のディスク容量を割り当てる必要があるため、ノードの実行にはコストがかかる可能性があります。[履歴の失効](/roadmap/statelessness/#history-expiry)は、チェーンを追跡するために必要のない古いブロックデータをクライアントが削除できるようにすることで、このコストを削減します。2025年7月の[部分的な履歴の失効](https://blog.ethereum.org/2025/07/08/partial-history-exp)以降、実行クライアントはマージ以前のすべてのブロックの本体とレシートを破棄できるようになりました。[ステート失効](/roadmap/statelessness/#state-expiry)と[ステートレス性](/roadmap/statelessness/)は、現在も研究が続けられているさらなる解決策です。

ノードが古い履歴の保存をやめると、それを他のノードに提供できなくなります。アーカイブ、トレント、プロバイダーはそのコピーを保持します。ポータル・ネットワークはそれを多くのノードに分散させるため、特定のノードに依存することなく利用可能な状態を維持します。

## ポータル・ネットワークはどのように機能するのか？ {#how-does-portal-network-work}

イーサリアムのノードには、互いに通信する方法を定義する厳格なプロトコルがあります。実行クライアントは[devp2p](/developers/docs/networking-layer/#devp2p)として知られるサブプロトコルのセットを使用して通信し、コンセンサス・クライアントは[libp2p](/developers/docs/networking-layer/#libp2p)と呼ばれる別のサブプロトコルスタックを使用します。devp2pを使用すると、ノードはピアにブロック本体とレシートを要求できますが、古い履歴を破棄したピアはそれを提供できません。アプリやウォレットは、[JSON-RPC API](/developers/docs/apis/json-rpc/)を通じてノードからデータを取得することもできますが、それは1つのノードまたはプロバイダーがデータを保存していること、およびそれが誠実であると信頼することに依存しています。

ポータル・ネットワークは、履歴を共有するために構築された独立したピア・ツー・ピア・ネットワークです。これは、コンセンサス・クライアントがピアを見つけるためにも使用するノード・ディスカバリー・プロトコルである[discv5](https://github.com/ethereum/devp2p/blob/master/discv5/discv5.md)上で実行され、BitTorrentと同様に、ノードを[分散ハッシュテーブル（DHT）](https://en.wikipedia.org/wiki/Distributed_hash_table)として編成します。すべてのノードにはノードIDがあり、1つのブロックのレシートなどのすべてのコンテンツには、ブロック番号から派生した同じID空間内のコンテンツIDがあります。各ノードは、自身のIDに最も近いIDを持つコンテンツを、半径と呼ばれる自身が選択した距離まで保存します。コンテンツを取得するために、ノードはコンテンツIDに最も近い、自身が知っているピアに問い合わせます。それを持っていないピアは、さらに近いノードを回答し、リクエストがそれを保存しているノードに到達するまでこれを繰り返します。

ノードは受信したデータを信頼する必要は決してありません。ノードはすべてのブロック・ヘッダーを保持し、各ヘッダーは`transactionsRoot`や`receiptsRoot`などのルートを通じて、そのブロックのトランザクションとレシートにコミットします。ノードは、ブロック本体またはブロックのレシートを使用する前に、それらのルートと照合して確認します。

### ポータル・ネットワーク {#the-portal-networks}

ポータル・ネットワークは当初、軽量なクライアントがフル・ノードを信頼することなくチェーンを追跡できるようにするいくつかのサブネットワークとして設計されました。これには、ビーコン・チェーンのライト・クライアント・ネットワーク、状態ネットワーク、トランザクション・ゴシップ・ネットワーク、履歴ネットワークが含まれます。2025年に、そのうちの1つを除くすべての仕様がレガシーに移行され、現在開発は**履歴ネットワーク**に焦点を当てています。これは、すべてのブロック・ヘッダーを保持しつつ残りの履歴を破棄した実行クライアントのために、過去のブロックの本体とレシートを保存するものです。

## ポータル・ネットワークのクライアント {#client-diversity-as-default}

いくつかのチームがポータル・ネットワークのクライアントを構築しました。

- [ニンバス・ポータル・クライアント](https://fluffy.guide)（旧Fluffy）: Nimで書かれており、現在も活発に開発が続けられています。
- [Trin](https://github.com/ethereum/trin): Rustで書かれており、現在はメンテナンスされていません。
- [Ultralight](https://github.com/ethereumjs/ultralight): TypeScriptで書かれており、2025年中頃から更新されていません。
- [Shisui](https://github.com/zen-eth/shisui): Goで書かれており、2025年中頃から更新されていません。
