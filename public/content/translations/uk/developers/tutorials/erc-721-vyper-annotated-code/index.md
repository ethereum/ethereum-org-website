## Вступ {#introduction}

Стандарт [ERC-721](/developers/docs/standards/tokens/erc-721/) використовується для зберігання права власності на невзаємозамінні токени (NFT).
Токени [ERC-20](/developers/docs/standards/tokens/erc-20/) поводяться як товар, оскільки між окремими токенами немає різниці.
На відміну від них, токени ERC-721 розроблені для активів, які є схожими, але не ідентичними, наприклад, різні [мультяшні коти](https://www.cryptokitties.co/)
або права власності на різні об'єкти нерухомості.

У цій статті ми проаналізуємо [контракт ERC-721 Рюї Накамури](https://github.com/vyperlang/vyper/blob/master/examples/tokens/ERC721.vy).
Цей контракт написаний на [Vyper](https://vyper.readthedocs.io/en/latest/index.html), мові контрактів, подібній до Python, яка розроблена так, щоб писати небезпечний код було складніше, ніж у Solidity.

## Контракт {#contract}

```python
#pragma version >0.3.10
```

Рядок `#pragma version` вказує компілятору, для яких версій Vyper написаний контракт. `>0.3.10` приймає будь-який реліз, новіший за 0.3.10, але насправді цьому контракту потрібен Vyper 0.4.1 або новішої версії: він реєструє події з іменованими аргументами (наприклад, `log IERC721.Transfer(...)`), функція, додана у Vyper 0.4.1, тому він не компілюється на 0.4.0.

```python
# @dev Реалізація стандарту невзаємозамінного токена (NFT) ERC-721.
# @author Ryuya Nakamura (@nrryuya)
# Змінено з: https://github.com/vyperlang/vyper/blob/de74722bf2d8718cca46902be165f9fe0e3641dd/examples/tokens/ERC721.vy
```

Коментарі у Vyper, як і в Python, починаються з хеша (`#`) і продовжуються до кінця рядка. Коментарі, що містять `@<keyword>`, використовуються [NatSpec](https://vyper.readthedocs.io/en/latest/natspec.html) для створення зрозумілої для людини документації.

```python
from ethereum.ercs import IERC165
from ethereum.ercs import IERC721

implements: IERC721
implements: IERC165
```

Інтерфейси ERC-165 та ERC-721 постачаються разом із компілятором Vyper, тому ми імпортуємо їх з `ethereum.ercs`, а не пишемо самостійно. [Ви можете переглянути визначення інтерфейсу ERC-721 тут](https://github.com/vyperlang/vyper/blob/master/vyper/builtins/interfaces/IERC721.vyi).
Рядки `implements:` оголошують, що цей контракт надає обидва інтерфейси, і компілятор перевіряє, чи кожна функція, яку вони вимагають, визначена нижче.

### Інтерфейс ERC721Receiver {#receiver-interface}

```python
# Інтерфейс для контракту, який викликається safeTransferFrom()
interface ERC721Receiver:
    def onERC721Received(
```

ERC-721 підтримує два типи переказу:

- `transferFrom`, який дозволяє відправнику вказати будь-яку адресу призначення та покладає відповідальність за переказ на відправника. Це означає, що ви можете здійснити переказ на недійсну адресу, і в такому випадку NFT буде втрачено назавжди.
- `safeTransferFrom`, який перевіряє, чи є адреса призначення контрактом. Якщо так, контракт ERC-721 запитує контракт-отримувач, чи хоче він отримати NFT.

Щоб відповідати на запити `safeTransferFrom`, контракт-отримувач повинен реалізувати `ERC721Receiver`.

```python
            _operator: address,
            _from: address,
```

Адреса `_from` — це поточний власник токена. Адреса `_operator` — це та, яка надіслала запит на переказ (ці дві адреси можуть не збігатися через дозволи). За домовленістю, більшість параметрів функцій у цьому контракті починаються з підкреслення (`_`).

```python
            _tokenId: uint256,
```

Ідентифікатори токенів ERC-721 мають розмір 256 біт. Зазвичай вони створюються шляхом хешування опису того, що представляє токен.

```python
            _data: Bytes[1024]
```

Запит може містити до 1024 байт даних користувача.

```python
        ) -> bytes4: nonpayable
```

Щоб запобігти випадкам, коли контракт випадково приймає переказ, значення, що повертається, є не логічним (boolean), а конкретним чотирибайтовим значенням — селектором функції `onERC721Received`. Функція є `nonpayable`, оскільки контракт-отримувач може змінити свій власний стан, коли приймає токен.

### Події {#events}

[Події](/developers/docs/smart-contracts/anatomy/#events-and-logs)
генеруються для інформування користувачів та серверів за межами блокчейну про події. Зверніть увагу, що вміст подій недоступний для контрактів у блокчейні. Три події ERC-721 визначені інтерфейсом `IERC721`, який ми імпортували, тому цей контракт не оголошує їх самостійно; він генерує їх за допомогою `log IERC721.<Event>(...)`, як ми побачимо у функціях переказу нижче.

`Transfer` (`sender`, `receiver`, `token_id`) повідомляє про зміну права власності на NFT. Це схоже на подію Transfer в ERC-20, за винятком того, що ми повідомляємо `token_id` замість суми. Ніхто не володіє нульовою адресою, тому за домовленістю ми використовуємо її для повідомлення про створення та знищення токенів. Єдиним винятком є створення контракту, під час якого може бути створено та призначено будь-яку кількість NFT без генерування `Transfer`.

Схвалення (approval) в ERC-721 схоже на дозвіл (allowance) в ERC-20: певній адресі дозволяється переказувати певний токен, і `Approval` (`owner`, `approved`, `token_id`) генерується щоразу, коли ця схвалена адреса встановлюється або підтверджується. Це надає механізм для контрактів реагувати, коли вони приймають токен. Контракти не можуть прослуховувати події, тому якщо ви просто перекажете їм токен, вони про це не «дізнаються». Таким чином, власник спочатку подає схвалення, а потім надсилає запит до контракту: «Я схвалив для вас переказ токена X, будь ласка, зробіть...». Це дизайнерське рішення, щоб зробити стандарт ERC-721 схожим на стандарт ERC-20. Оскільки токени ERC-721 є невзаємозамінними, контракт також може визначити, що він отримав певний токен, подивившись на право власності на токен.

Нарешті, `ApprovalForAll` (`owner`, `operator`, `approved`) генерується, коли _оператор_ вмикається або вимикається для власника. Іноді корисно мати оператора, який може керувати всіма токенами акаунта певного типу (тими, якими керує певний контракт), подібно до довіреності. Наприклад, я можу захотіти надати такі повноваження контракту, який перевіряє, чи не звертався я до нього протягом шести місяців, і якщо так, розподіляє мої активи між моїми спадкоємцями (якщо один із них попросить про це, контракти нічого не можуть зробити без виклику транзакцією). В ERC-20 ми можемо просто надати великий дозвіл контракту на спадкування, але це не працює для ERC-721, оскільки токени не є взаємозамінними. Це є еквівалентом. Значення `approved` вказує нам, чи стосується подія схвалення, чи його відкликання.

### Змінні стану {#state-vars}

Ці змінні містять поточний стан токенів: які з них доступні та кому вони належать. Більшість із них є об'єктами `HashMap`, [односпрямованими відображеннями, що існують між двома типами](https://vyper.readthedocs.io/en/latest/types.html#mappings).

```python
# @dev Відображення ID NFT на адресу, яка ним володіє.
idToOwner: HashMap[uint256, address]

# @dev Відображення ID NFT на схвалену адресу.
idToApprovals: HashMap[uint256, address]
```

Ідентифікатори користувачів та контрактів в Етеріумі представлені 160-бітними адресами. Ці дві змінні відображають ідентифікатори токенів на їхніх власників та тих, кому дозволено їх переказувати (максимум по одному для кожного). В Етеріумі неініціалізовані дані завжди дорівнюють нулю, тому якщо немає власника або схваленого відправника, значення для цього токена дорівнює нулю.

```python
# @dev Відображення адреси власника на кількість його токенів.
ownerToNFTokenCount: HashMap[address, uint256]
```

Ця змінна містить кількість токенів для кожного власника. Немає відображення від власників до токенів, тому єдиний спосіб ідентифікувати токени, якими володіє певний власник, — це зазирнути в історію подій блокчейну та знайти відповідні події `Transfer`. Ми можемо використовувати цю змінну, щоб знати, коли ми знайшли всі NFT і нам не потрібно шукати далі в часі.

Зверніть увагу, що цей алгоритм працює лише для інтерфейсів користувача та зовнішніх серверів. Код, що виконується в самому блокчейні, не може читати минулі події.

```python
# @dev Відображення адреси власника на відображення адрес операторів.
ownerToOperators: HashMap[address, HashMap[address, bool]]
```

Акаунт може мати більше одного оператора. Простого `HashMap` недостатньо для їх відстеження, оскільки кожен ключ веде до одного значення. Замість цього ви можете використовувати `HashMap[address, bool]` як значення. За замовчуванням значення для кожної адреси — `False`, що означає, що вона не є оператором. Ви можете встановлювати значення `True` за потреби.

```python
# @dev Адреса карбувальника, який може карбувати токен
minter: address
```

Нові токени мають якось створюватися. У цьому контракті є лише одна сутність, якій дозволено це робити — `minter`. Цього, ймовірно, буде достатньо, наприклад, для гри. Для інших цілей може знадобитися створити складнішу бізнес-логіку.

```python
# @dev Статичний список підтримуваних ID інтерфейсів ERC-165
SUPPORTED_INTERFACES: constant(bytes4[2]) = [
    # ID інтерфейсу ERC-165 для ERC-165
    0x01ffc9a7,
    # ID інтерфейсу ERC-165 для ERC-721
    0x80ac58cd,
]
```

[ERC-165](https://eips.ethereum.org/EIPS/eip-165) визначає механізм, за допомогою якого контракт може розкривати, як застосунки можуть взаємодіяти з ним, і яким стандартам ERC він відповідає. `SUPPORTED_INTERFACES` — це константний список із двох чотирибайтових ідентифікаторів інтерфейсів, яким відповідає цей контракт: самого ERC-165 та ERC-721.

### Функції {#functions}

Це функції, які фактично реалізують ERC-721.

#### Конструктор {#constructor}

```python
@deploy
def __init__():
```

У Vyper, як і в Python, функція-конструктор називається `__init__`. Вона позначена декоратором `@deploy`, що означає, що вона виконується один раз під час розгортання контракту.

```python
    """
    @dev Конструктор контракту.
    """
```

У Python та у Vyper ви також можете створити коментар, вказавши багаторядковий рядок (який починається і закінчується на `"""`), і ніяк його не використовуючи. Ці коментарі також можуть містити [NatSpec](https://vyper.readthedocs.io/en/latest/natspec.html).

```python
    self.minter = msg.sender
```

Для доступу до змінних стану ви використовуєте `self.<variable name>` (знову ж таки, як і в Python). Конструктор записує акаунт, який розгорнув контракт, як `minter`.

#### Функції перегляду (View) {#views}

Це функції, які не змінюють стан блокчейну, і тому можуть виконуватися безкоштовно, якщо вони викликаються ззовні. Якщо функції перегляду викликаються контрактом, вони все одно повинні виконуватися на кожному вузлі, і тому коштують газ.

```python
@view
@external
```

Ці ключові слова перед визначенням функції, які починаються зі знака «at» (`@`), називаються _декораторами_. Вони визначають обставини, за яких може бути викликана функція.

- `@view` вказує, що ця функція є функцією перегляду (view).
- `@external` вказує, що ця конкретна функція може бути викликана транзакціями та іншими контрактами.

```python
def supportsInterface(interface_id: bytes4) -> bool:
```

На відміну від Python, Vyper є [мовою зі статичною типізацією](https://wikipedia.org/wiki/Type_system#Static_type_checking).
Ви не можете оголосити змінну або параметр функції без визначення [типу даних](https://vyper.readthedocs.io/en/latest/types.html). У цьому випадку вхідним параметром є `bytes4`, чотирибайтове значення, а вихідним — логічне значення.

```python
    """
    @dev Ідентифікація інтерфейсу вказана в ERC-165.
    @param interface_id ID інтерфейсу
    """
    return interface_id in SUPPORTED_INTERFACES
```

Повертає `True`, якщо `interface_id` є одним з ідентифікаторів інтерфейсу у списку `SUPPORTED_INTERFACES`.

```python
### VIEW FUNCTIONS ###
```

Це функції перегляду, які роблять інформацію про токени доступною для користувачів та інших контрактів.

```python
@view
@external
def balanceOf(_owner: address) -> uint256:
    """
    @dev Повертає кількість NFT, якими володіє `_owner`.
         Викликає помилку, якщо `_owner` — нульова адреса. NFT, призначені нульовій адресі, вважаються недійсними.
    @param _owner Адреса, для якої запитується баланс.
    """
    assert _owner != empty(address)
```

Цей рядок [стверджує](https://vyper.readthedocs.io/en/latest/statements.html#assert), що `_owner` не є нульовою адресою, яка записується як `empty(address)`. Якщо це так, виникає помилка, і операція скасовується.

```python
    return self.ownerToNFTokenCount[_owner]

@view
@external
def ownerOf(_tokenId: uint256) -> address:
    """
    @dev Повертає адресу власника NFT.
         Викликає помилку, якщо `_tokenId` не є дійсним NFT.
    @param _tokenId Ідентифікатор NFT.
    """
    owner: address = self.idToOwner[_tokenId]
    # Викликає помилку, якщо `_tokenId` не є дійсним NFT
    assert owner != empty(address)
    return owner
```

У Віртуальній машині Ethereum (EVM) будь-яке сховище, в якому не збережено значення, дорівнює нулю.
Якщо за адресою `_tokenId` немає токена, то значення `self.idToOwner[_tokenId]` дорівнює нулю. У такому випадку функція скасовується.

```python
@view
@external
def getApproved(_tokenId: uint256) -> address:
    """
    @dev Отримати схвалену адресу для одного NFT.
         Викликає помилку, якщо `_tokenId` не є дійсним NFT.
    @param _tokenId ID NFT для запиту схвалення.
    """
    # Викликає помилку, якщо `_tokenId` не є дійсним NFT
    assert self.idToOwner[_tokenId] != empty(address)
    return self.idToApprovals[_tokenId]
```

Зверніть увагу, що `getApproved` _може_ повертати нуль. Якщо токен дійсний, він повертає `self.idToApprovals[_tokenId]`.
Якщо немає того, хто схвалив, це значення дорівнює нулю.

```python
@view
@external
def isApprovedForAll(_owner: address, _operator: address) -> bool:
    """
    @dev Перевіряє, чи є `_operator` схваленим оператором для `_owner`.
    @param _owner Адреса, яка володіє NFT.
    @param _operator Адреса, яка діє від імені власника.
    """
    return (self.ownerToOperators[_owner])[_operator]
```

Ця функція перевіряє, чи дозволено `_operator` керувати всіма токенами `_owner` у цьому контракті.
Оскільки операторів може бути кілька, це дворівнева хеш-таблиця (HashMap).

#### Допоміжні функції переказу {#transfer-helpers}

Ці функції реалізують операції, які є частиною переказу або керування токенами.

```python

### TRANSFER FUNCTION HELPERS ###

@view
@internal
```

Цей декоратор, `@internal`, означає, що функція доступна лише з інших функцій у межах того самого контракту. За домовленістю, імена цих функцій також починаються з підкреслення (`_`).

```python
def _isApprovedOrOwner(_spender: address, _tokenId: uint256) -> bool:
    """
    @dev Повертає, чи може вказаний витрачальник здійснити переказ вказаного ID токена
    @param spender адреса витрачальника для запиту
    @param tokenId uint256 ID токена для переказу
    @return bool чи схвалений msg.sender для вказаного ID токена,
        чи є він оператором власника, або чи є він власником токена
    """
    owner: address = self.idToOwner[_tokenId]
    spenderIsOwner: bool = owner == _spender
    spenderIsApproved: bool = _spender == self.idToApprovals[_tokenId]
    spenderIsApprovedForAll: bool = (self.ownerToOperators[owner])[_spender]
    return (spenderIsOwner or spenderIsApproved) or spenderIsApprovedForAll
```

Існує три способи, за допомогою яких адресі може бути дозволено переказати токен:

1. Адреса є власником токена
2. Адресі дозволено витрачати цей токен
3. Адреса є оператором для власника токена

Наведена вище функція може бути функцією перегляду (view), оскільки вона не змінює стан. Щоб зменшити операційні витрати, будь-яка функція, яка _може_ бути функцією перегляду, _повинна_ нею бути.

```python
@internal
def _addTokenTo(_to: address, _tokenId: uint256):
    """
    @dev Додати NFT до вказаної адреси
         Викликає помилку, якщо `_tokenId` комусь належить.
    """
    # Викликає помилку, якщо `_tokenId` комусь належить
    assert self.idToOwner[_tokenId] == empty(address)
    # Змінити власника
    self.idToOwner[_tokenId] = _to
    # Змінити відстеження кількості
    self.ownerToNFTokenCount[_to] += 1


@internal
def _removeTokenFrom(_from: address, _tokenId: uint256):
    """
    @dev Видалити NFT з вказаної адреси
         Викликає помилку, якщо `_from` не є поточним власником.
    """
    # Викликає помилку, якщо `_from` не є поточним власником
    assert self.idToOwner[_tokenId] == _from
    # Змінити власника
    self.idToOwner[_tokenId] = empty(address)
    # Змінити відстеження кількості
    self.ownerToNFTokenCount[_from] -= 1
```

Коли виникає проблема з переказом, ми скасовуємо виклик.

```python
@internal
def _clearApproval(_owner: address, _tokenId: uint256):
    """
    @dev Очистити схвалення для вказаної адреси
         Викликає помилку, якщо `_owner` не є поточним власником.
    """
    # Викликає помилку, якщо `_owner` не є поточним власником
    assert self.idToOwner[_tokenId] == _owner
    if self.idToApprovals[_tokenId] != empty(address):
        # Скинути схвалення
        self.idToApprovals[_tokenId] = empty(address)
```

Змінюйте значення лише за необхідності. Змінні стану живуть у сховищі. Запис у сховище є однією з найдорожчих операцій, які виконує EVM (Віртуальна машина Ethereum) (з точки зору
[газу](/developers/docs/gas/)). Тому доцільно мінімізувати його, оскільки навіть запис існуючого значення має високу вартість.

```python
@internal
def _transferFrom(_from: address, _to: address, _tokenId: uint256, _sender: address):
    """
    @dev Виконати переказ NFT.
         Викликає помилку, якщо `msg.sender` не є поточним власником, уповноваженим оператором або схваленою
         адресою для цього NFT. (ПРИМІТКА: `msg.sender` не дозволено у приватній функції, тому передайте `_sender`.)
         Викликає помилку, якщо `_to` — нульова адреса.
         Викликає помилку, якщо `_from` не є поточним власником.
         Викликає помилку, якщо `_tokenId` не є дійсним NFT.
    """
```

У нас є ця внутрішня функція, оскільки існує два способи переказу токенів (звичайний і безпечний), але
ми хочемо, щоб у коді було лише одне місце, де ми це робимо, щоб полегшити аудит.

```python
    # Перевірити вимоги
    assert self._isApprovedOrOwner(_sender, _tokenId)
    # Викликає помилку, якщо `_to` — нульова адреса
    assert _to != empty(address)
    # Очистити схвалення. Викликає помилку, якщо `_from` не є поточним власником
    self._clearApproval(_from, _tokenId)
    # Видалити NFT. Викликає помилку, якщо `_tokenId` не є дійсним NFT
    self._removeTokenFrom(_from, _tokenId)
    # Додати NFT
    self._addTokenTo(_to, _tokenId)
    # Залогувати переказ
    log IERC721.Transfer(sender=_from, receiver=_to, token_id=_tokenId)
```

Щоб згенерувати подію у Vyper, ви використовуєте оператор `log` ([докладніше дивіться тут](https://vyper.readthedocs.io/en/latest/event-logging.html#event-logging)).
Оскільки події належать до імпортованого інтерфейсу, ми посилаємося на них як на `IERC721.Transfer` і передаємо їхні поля за ключовими словами.

#### Функції переказу {#transfer-funs}

```python

### TRANSFER FUNCTIONS ###

@external
@payable
def transferFrom(_from: address, _to: address, _tokenId: uint256):
    """
    @dev Викликає помилку, якщо `msg.sender` не є поточним власником, уповноваженим оператором або схваленою
         адресою для цього NFT.
         Викликає помилку, якщо `_from` не є поточним власником.
         Викликає помилку, якщо `_to` — нульова адреса.
         Викликає помилку, якщо `_tokenId` не є дійсним NFT.
    @notice Абонент несе відповідальність за підтвердження того, що `_to` здатна отримувати NFT, інакше
            вони можуть бути назавжди втрачені.
    @param _from Поточний власник NFT.
    @param _to Новий власник.
    @param _tokenId NFT для переказу.
    """
    self._transferFrom(_from, _to, _tokenId, msg.sender)
```

Ця функція дозволяє здійснювати переказ на довільну адресу. Якщо адреса не є користувачем або контрактом, який
знає, як переказувати токени, будь-який переказаний вами токен застрягне на цій адресі і стане марним.

Декоратор `@payable` тут присутній, оскільки інтерфейс `IERC721` оголошує `transferFrom`, `safeTransferFrom` та
`approve` як payable, тому контракт, який реалізує цей інтерфейс, повинен відповідати цим сигнатурам.

```python
@external
@payable
def safeTransferFrom(
        _from: address,
        _to: address,
        _tokenId: uint256,
        _data: Bytes[1024]=b""
    ):
    """
    @dev Переказує право власності на NFT з однієї адреси на іншу адресу.
         Викликає помилку, якщо `msg.sender` не є поточним власником, уповноваженим оператором або
         схваленою адресою для цього NFT.
         Викликає помилку, якщо `_from` не є поточним власником.
         Викликає помилку, якщо `_to` — нульова адреса.
         Викликає помилку, якщо `_tokenId` не є дійсним NFT.
         Якщо `_to` — смарт-контракт, викликає `onERC721Received` на `_to` і викликає помилку, якщо
         значення, що повертається, не дорівнює `bytes4(keccak256("onERC721Received(address,address,uint256,bytes)"))`.
    @param _from Поточний власник NFT.
    @param _to Новий власник.
    @param _tokenId NFT для переказу.
    @param _data Додаткові дані без визначеного формату, надіслані у виклику до `_to`.
    """
    self._transferFrom(_from, _to, _tokenId, msg.sender)
```

Нормально спочатку виконати переказ, тому що якщо виникне проблема, ми все одно скасуємо операцію,
тому все, що було зроблено під час виклику, буде анульовано.

```python
    if _to.is_contract: # перевірити, чи є `_to` адресою контракту
```

Спочатку перевірте, чи є адреса контрактом (чи є в неї код). Якщо ні, припустіть, що це адреса користувача,
і користувач зможе використовувати токен або переказати його. Але не дозволяйте цьому приспати вашу
пильність. Ви можете втратити токени, навіть з `safeTransferFrom`, якщо перекажете
їх на адресу, для якої ніхто не знає приватний ключ.

```python
        returnValue: bytes4 = extcall ERC721Receiver(_to).onERC721Received(msg.sender, _from, _tokenId, _data)
```

Викличте цільовий контракт, щоб перевірити, чи може він отримувати токени ERC-721. Vyper 0.4 вимагає, щоб виклики інших контрактів
були позначені, тому виклик має префікс `extcall`.

```python
        # Викликає помилку, якщо пункт призначення переказу є контрактом, який не реалізує 'onERC721Received'
        assert returnValue == method_id("onERC721Received(address,address,uint256,bytes)", output_type=bytes4)
```

Якщо адреса призначення є контрактом, але таким, що не приймає токени ERC-721 (або який вирішив не приймати цей
конкретний переказ), скасуйте операцію.

```python
@external
@payable
def approve(_approved: address, _tokenId: uint256):
    """
    @dev Встановити або підтвердити схвалену адресу для NFT. Нульова адреса вказує на відсутність схваленої адреси.
         Викликає помилку, якщо `msg.sender` не є поточним власником NFT або уповноваженим оператором поточного власника.
         Викликає помилку, якщо `_tokenId` не є дійсним NFT. (ПРИМІТКА: Це не написано в EIP)
         Викликає помилку, якщо `_approved` є поточним власником. (ПРИМІТКА: Це не написано в EIP)
    @param _approved Адреса, яка має бути схвалена для вказаного ID NFT.
    @param _tokenId ID токена для схвалення.
    """
    owner: address = self.idToOwner[_tokenId]
    # Викликає помилку, якщо `_tokenId` не є дійсним NFT
    assert owner != empty(address)
    # Викликає помилку, якщо `_approved` є поточним власником
    assert _approved != owner
```

За домовленістю, якщо ви не хочете мати того, хто схвалює, ви призначаєте нульову адресу, а не себе.

```python
    # Перевірити вимоги
    senderIsOwner: bool = self.idToOwner[_tokenId] == msg.sender
    senderIsApprovedForAll: bool = (self.ownerToOperators[owner])[msg.sender]
    assert (senderIsOwner or senderIsApprovedForAll)
```

Щоб встановити схвалення, ви можете бути або власником, або оператором, уповноваженим власником.

```python
    # Встановити схвалення
    self.idToApprovals[_tokenId] = _approved
    log IERC721.Approval(owner=owner, approved=_approved, token_id=_tokenId)


@external
def setApprovalForAll(_operator: address, _approved: bool):
    """
    @dev Вмикає або вимикає схвалення для третьої сторони ("оператора") на управління всіма
         активами `msg.sender`. Це також генерує подію ApprovalForAll.
         Викликає помилку, якщо `_operator` є `msg.sender`. (ПРИМІТКА: Це не написано в EIP)
    @notice Це працює, навіть якщо відправник на той момент не володіє жодними токенами.
    @param _operator Адреса для додавання до набору уповноважених операторів.
    @param _approved True, якщо оператор схвалений, false для відкликання схвалення.
    """
    # Викликає помилку, якщо `_operator` є `msg.sender`
    assert _operator != msg.sender
    self.ownerToOperators[msg.sender][_operator] = _approved
    log IERC721.ApprovalForAll(owner=msg.sender, operator=_operator, approved=_approved)
```

Акаунт, який створив контракт, є `minter` — суперкористувачем, який уповноважений карбувати
нові NFT. Однак навіть йому не дозволено спалювати існуючі токени. Це може зробити лише власник або сутність,

Ця функція завжди повертає `True`, оскільки якщо операція не вдається, вона скасовується.

    @dev Функція для карбування токенів
         Викликає помилку, якщо `msg.sender` не є карбувальником.
         Викликає помилку, якщо `_to` — нульова адреса.

    @param _tokenId ID токена для карбування.

Лише карбувальник (акаунт, який створив контракт ERC-721) може карбувати нові токени. Це може стати
проблемою в майбутньому, якщо ми захочемо змінити особу карбувальника. У
робочому контракті ви, ймовірно, захочете мати функцію, яка дозволяє карбувальнику передавати
привілеї карбування комусь іншому.

```python

    assert _to != empty(address)
    # Додати NFT. Викликає помилку, якщо `_tokenId` комусь належить
    self._addTokenTo(_to, _tokenId)
    log IERC721.Transfer(sender=empty(address), receiver=_to, token_id=_tokenId)
    return True
```

За домовленістю, карбування нових токенів вважається переказом з нульової адреси.

```python

@external
def burn(_tokenId: uint256):
    """
    @dev Спалює конкретний токен ERC-721.
         Викликає помилку, якщо `msg.sender` не є поточним власником, уповноваженим оператором або схваленою
         адресою для цього NFT.
         Викликає помилку, якщо `_tokenId` не є дійсним NFT.
    @param _tokenId uint256 ID токена ERC-721 для спалювання.
    """
    # Перевірити вимоги
    assert self._isApprovedOrOwner(msg.sender, _tokenId)
    owner: address = self.idToOwner[_tokenId]
    # Викликає помилку, якщо `_tokenId` не є дійсним NFT
    assert owner != empty(address)
    self._clearApproval(owner, _tokenId)
    self._removeTokenFrom(owner, _tokenId)
    log IERC721.Transfer(sender=owner, receiver=empty(address), token_id=_tokenId)
```

Будь-кому, кому дозволено переказувати токен, дозволено його спалювати. Хоча спалювання здається еквівалентним
переказу на нульову адресу, нульова адреса насправді не отримує токен. Це дозволяє нам
звільнити все сховище, яке використовувалося для токена, що може зменшити вартість газу для транзакції.

## Використання цього контракту {#using-contract}

На відміну від Solidity, Vyper не має успадкування. Це свідоме дизайнерське рішення, щоб зробити
код зрозумілішим і, отже, легшим для захисту. Тому, щоб створити власний контракт ERC-721 на Vyper, ви берете [цей
контракт](https://github.com/vyperlang/vyper/blob/master/examples/tokens/ERC721.vy) і змінюєте його
для реалізації потрібної вам бізнес-логіки.

## Висновок {#conclusion}

Для повторення, ось деякі з найважливіших ідей у цьому контракті:

- Щоб отримувати токени ERC-721 за допомогою безпечного переказу, контракти повинні реалізувати інтерфейс `ERC721Receiver`.
- Навіть якщо ви використовуєте безпечний переказ, токени все одно можуть застрягти, якщо ви надішлете їх на адресу, приватний ключ якої
  невідомий.
- Коли виникає проблема з операцією, доцільно `revert` виклик, а не просто повертати
  значення помилки.
- Токени ERC-721 існують, коли вони мають власника.
- Існує три способи отримати дозвіл на переказ NFT. Ви можете бути власником, бути схваленим для певного токена,
  або бути оператором для всіх токенів власника.
- Минулі події видимі лише за межами блокчейну. Код, що виконується всередині блокчейну, не може їх переглядати.
