## அறிமுகம் {#introduction}

எத்திரியத்தின் சிறந்த விஷயங்களில் ஒன்று, உங்கள் பரிவர்த்தனைகளை மாற்றியமைக்கவோ அல்லது செயல்தவிர்க்கவோ எந்தவொரு மைய அதிகாரமும் இல்லை என்பதாகும். எத்திரியத்தின் பெரிய சிக்கல்களில் ஒன்று, பயனர் தவறுகள் அல்லது சட்டவிரோத பரிவர்த்தனைகளைச் செயல்தவிர்க்கும் அதிகாரம் கொண்ட மைய அதிகாரம் எதுவும் இல்லை என்பதாகும். இந்தக் கட்டுரையில், [ERC-20](/developers/docs/standards/tokens/erc-20/) வில்லைகளுடன் பயனர்கள் செய்யும் சில பொதுவான தவறுகளைப் பற்றியும், அந்தத் தவறுகளைத் தவிர்க்க பயனர்களுக்கு உதவும் அல்லது மைய அதிகாரத்திற்குச் சில அதிகாரங்களை (உதாரணமாகக் கணக்குகளை முடக்குவதற்கு) வழங்கும் ERC-20 ஒப்பந்தங்களை எவ்வாறு உருவாக்குவது என்பது பற்றியும் நீங்கள் அறிந்துகொள்வீர்கள்.

நாம் [OpenZeppelin ERC-20 வில்லை ஒப்பந்தத்தைப்](https://github.com/OpenZeppelin/openzeppelin-contracts/tree/master/contracts/token/ERC20) பயன்படுத்தினாலும், இந்தக் கட்டுரை அதை விரிவாக விளக்கவில்லை என்பதை நினைவில் கொள்ளவும். இந்தத் தகவலை நீங்கள் [இங்கே](/developers/tutorials/erc20-annotated-code) காணலாம்.

முழுமையான மூலக் குறியீட்டை நீங்கள் காண விரும்பினால்:

1. [Remix IDE](https://remix.ethereum.org/)-ஐத் திறக்கவும்.
2. clone github ஐகானைக் கிளிக் செய்யவும் (![clone github icon](icon-clone.png)).
3. `https://github.com/qbzzt/20220815-erc20-safety-rails` என்ற github களஞ்சியத்தை குளோன் (clone) செய்யவும்.
4. **contracts > erc20-safety-rails.sol** என்பதைத் திறக்கவும்.

இந்தக் களஞ்சியம் OpenZeppelin Contracts 4.7.2-க்காக எழுதப்பட்டது என்பதை நினைவில் கொள்ளவும், இதில் இந்தக் கட்டுரை மேலெழுதும் (override) சார்பு `_beforeTokenTransfer` என்று அழைக்கப்படுகிறது. இந்தக் கட்டுரை தற்போதைய OpenZeppelin Contracts 5.x-ஐப் பயன்படுத்துகிறது, இதில் நீங்கள் அதற்குப் பதிலாக `_update`-ஐ மேலெழுதுகிறீர்கள், எனவே இந்தக் கட்டுரையில் உள்ள குறியீடு களஞ்சியத்தில் உள்ள குறியீட்டிலிருந்து சற்று வேறுபடுகிறது.

## ஒரு ERC-20 ஒப்பந்தத்தை உருவாக்குதல் {#creating-an-erc-20-contract}

பாதுகாப்பு வளையச் செயல்பாட்டைச் சேர்ப்பதற்கு முன், நமக்கு ஒரு ERC-20 ஒப்பந்தம் தேவை. இந்தக் கட்டுரையில் நாம் [OpenZeppelin Contracts Wizard](https://docs.openzeppelin.com/contracts/5.x/wizard)-ஐப் பயன்படுத்துவோம். அதை வேறொரு உலாவியில் திறந்து, இந்த வழிமுறைகளைப் பின்பற்றவும்:

1. **ERC20**-ஐத் தேர்ந்தெடுக்கவும்.
2. இந்த அமைப்புகளை உள்ளிடவும்:

   | அளவுரு (Parameter) | மதிப்பு (Value)            |
   | -------------- | ------------------------- |
   | Name           | SafetyRailsToken          |
   | Symbol         | SAFE                      |
   | Premint        | 1000                      |
   | Features       | None (**Permit**-ஐத் தேர்வுநீக்கவும்) |
   | Access Control | Ownable                   |
   | Upgradability  | None                      |

3. மேலே ஸ்க்ரோல் செய்து, **Open in Remix** (Remix-க்கு) என்பதைக் கிளிக் செய்யவும் அல்லது வேறு சூழலைப் பயன்படுத்த **Download** என்பதைக் கிளிக் செய்யவும். நீங்கள் Remix-ஐப் பயன்படுத்துகிறீர்கள் என்று நான் கருதுகிறேன், நீங்கள் வேறு எதையாவது பயன்படுத்தினால் அதற்கேற்ப மாற்றங்களைச் செய்யுங்கள்.
4. இப்போது நம்மிடம் முழுமையாகச் செயல்படும் ERC-20 ஒப்பந்தம் உள்ளது. இறக்குமதி செய்யப்பட்ட குறியீட்டைக் காண நீங்கள் `.deps` > `npm`-ஐ விரிவுபடுத்தலாம்.
5. ஒப்பந்தத்தை தொகுத்து (compile), நிலைநிறுத்தி (deploy), அது ஒரு ERC-20 ஒப்பந்தமாகச் செயல்படுகிறதா என்பதைப் பார்க்க அதனுடன் விளையாடுங்கள். Remix-ஐ எவ்வாறு பயன்படுத்துவது என்பதை நீங்கள் அறிய விரும்பினால், [இந்த வழிகாட்டியைப் பயன்படுத்தவும்](https://remix.ethereum.org/?#activate=udapp,solidity,LearnEth).

## பொதுவான தவறுகள் {#common-mistakes}

### தவறுகள் {#the-mistakes}

பயனர்கள் சில நேரங்களில் தவறான முகவரிக்கு வில்லைகளை அனுப்புகிறார்கள். அவர்கள் என்ன செய்ய நினைத்தார்கள் என்பதை அறிய அவர்களின் மனதை நம்மால் படிக்க முடியாது என்றாலும், அடிக்கடி நிகழும் மற்றும் எளிதில் கண்டறியக்கூடிய இரண்டு வகையான பிழைகள் உள்ளன:

1. ஒப்பந்தத்தின் சொந்த முகவரிக்கே வில்லைகளை அனுப்புவது. உதாரணமாக, [ஆப்டிமிசத்தின் OP வில்லை](https://optimism.mirror.xyz/qvd0WfuLKnePm1Gxb9dpGchPf5uDz5NSMEFdgirDS4c) இரண்டு மாதங்களுக்குள் [120,000-க்கும் மேற்பட்ட](https://optimism.blockscout.com/address/0x4200000000000000000000000000000000000042) OP வில்லைகளைக் குவித்துள்ளது. இது மக்கள் இழந்திருக்கக்கூடிய கணிசமான அளவு செல்வத்தைக் குறிக்கிறது.

2. [வெளிப்புறமாகச் சொந்தமான கணக்கு (externally owned account)](/developers/docs/accounts/#externally-owned-accounts-and-key-pairs) அல்லது [திறன் ஒப்பந்தத்திற்கு](/developers/docs/smart-contracts) தொடர்பில்லாத வெற்று முகவரிக்கு வில்லைகளை அனுப்புவது. இது எவ்வளவு அடிக்கடி நிகழ்கிறது என்பதற்கான புள்ளிவிவரங்கள் என்னிடம் இல்லை என்றாலும், [ஒரு சம்பவத்தில் 20,000,000 வில்லைகள் இழக்கப்பட்டிருக்கலாம்](https://gov.optimism.io/t/message-to-optimism-community-from-wintermute/2595).

### பரிமாற்றங்களைத் தடுத்தல் {#preventing-transfers}

OpenZeppelin ERC-20 ஒப்பந்தத்தில், நிலுவைகளில் ஏற்படும் ஒவ்வொரு மாற்றமும், அது ஒரு பரிமாற்றமாகவோ, அச்சிடுதலாகவோ அல்லது எரிப்பதாகவோ இருந்தாலும், [ஒரு உள் சார்பான `_update`](https://docs.openzeppelin.com/contracts/5.x/api/token/erc20#ERC20-_update-address-address-uint256-) வழியாகச் செல்கிறது. ஏதேனும் சிக்கல் இருந்தால் மீளமைக்கும் (revert) சரிபார்ப்புகள் போன்ற நமது சொந்தச் செயல்பாட்டை அதில் இணைக்க, நாம் அதை மேலெழுதலாம் (override).

அவ்வாறு செய்ய, ஆக்கிக்குப் (constructor) பிறகு இந்தச் சார்பைச் சேர்க்கவும்:

```solidity
    function _update(address from, address to, uint256 value)
        internal virtual
        override(ERC20)
    {
        super._update(from, to, value);
    }
```

நீங்கள் Solidity-ஐப் பற்றி நன்கு அறிந்திருக்கவில்லை என்றால், இந்தச் சார்பின் சில பகுதிகள் புதியதாக இருக்கலாம்:

```solidity
        internal virtual
```

`virtual` என்ற சிறப்புச்சொல் (keyword), நாம் `ERC20`-லிருந்து செயல்பாட்டைப் பெற்று இந்தச் சார்பை மேலெழுதியது போலவே, பிற ஒப்பந்தங்களும் நம்மிடமிருந்து பெற்று இந்தச் சார்பை மேலெழுதலாம் என்பதைக் குறிக்கிறது.

```solidity
        override(ERC20)
```

`_update`-இன் ERC20 வில்லை வரையறையை நாம் [மேலெழுதுகிறோம்](https://docs.soliditylang.org/en/latest/contracts.html#function-overriding) என்பதை வெளிப்படையாகக் குறிப்பிட வேண்டும். பொதுவாக, பாதுகாப்பு கண்ணோட்டத்தில், மறைமுகமான வரையறைகளை விட வெளிப்படையான வரையறைகள் மிகவும் சிறந்தவை - நீங்கள் செய்த ஒன்று உங்கள் கண்முன்னே இருந்தால் அதை உங்களால் மறக்க முடியாது. எந்த சூப்பர்கிளாஸின் (superclass) `_update`-ஐ நாம் மேலெழுதுகிறோம் என்பதைக் குறிப்பிட வேண்டியதற்கும் இதுவே காரணம்.

```solidity
        super._update(from, to, value);
```

இந்த வரி, நாம் பெற்ற ஒப்பந்தம் அல்லது ஒப்பந்தங்களின் `_update` சார்பை அழைக்கிறது. இந்த நிலையில், அது `ERC20` மட்டுமே, `Ownable`-க்கு இந்தச் சார்பு இல்லை. வெற்று ஹூக்கைப் (hook) போலல்லாமல், `ERC20._update` என்பது உண்மையில் வில்லைகளை நகர்த்துகிறது, எனவே அதை அழைப்பது அவசியம். நமது சரிபார்ப்புகள் இந்த அழைப்பிற்கு முன் செல்கின்றன, எனவே நிலுவை மாற்றங்களுக்கு முன்பே அவை மீளமைக்கப்படலாம்.

### தேவைகளைக் குறியீடாக்குதல் {#coding-the-requirements}

இந்தத் தேவைகளை நாம் சார்பில் சேர்க்க விரும்புகிறோம். வில்லைகள் எரிக்கப்படும்போதும் `_update` அழைக்கப்படுவதால், `to` என்பது `address(0)` என அமைக்கப்பட்டிருக்கும் நிலையில், `to` என்பது `address(0)` ஆக இல்லாதபோது மட்டுமே நாம் அதைச் சரிபார்க்கிறோம்:

- `to` முகவரியானது ERC-20 ஒப்பந்தத்தின் முகவரியான `address(this)`-க்குச் சமமாக இருக்க முடியாது.
- `to` முகவரி காலியாக இருக்க முடியாது, அது பின்வருவனவற்றில் ஒன்றாக இருக்க வேண்டும்:
  - ஒரு வெளிப்புறமாக சொந்தமான கணக்கு (EOA). ஒரு முகவரி EOA தானா என்பதை நம்மால் நேரடியாகச் சரிபார்க்க முடியாது, ஆனால் ஒரு முகவரியின் ETH நிலுவையை நாம் சரிபார்க்கலாம். EOA-க்கள் இனி பயன்படுத்தப்படாவிட்டாலும், அவை எப்போதும் ஒரு நிலுவையைக் கொண்டிருக்கும் - அவற்றை கடைசி Wei வரை அழிப்பது கடினம்.
  - ஒரு திறன் ஒப்பந்தம். ஒரு முகவரி திறன் ஒப்பந்தமா என்பதைச் சோதிப்பது சற்று கடினமானது. வெளிப்புறக் குறியீட்டின் நீளத்தைச் சரிபார்க்கும் ஒரு செயல்பாட்டுக் குறியீடு உள்ளது, அது [`EXTCODESIZE`](https://www.evm.codes/#3b) என்று அழைக்கப்படுகிறது. Solidity-இல் நீங்கள் அதை [`<address>.code.length`](https://docs.soliditylang.org/en/latest/units-and-global-variables.html#members-of-address-types) மூலம் பெறலாம், இதைத் தொகுப்பான் (compiler) `EXTCODESIZE` ஆக மாற்றுகிறது. செயல்பாட்டுக் குறியீட்டை நேரடியாக எவ்வாறு அழைப்பது என்பதைக் காட்ட, EVM அசெம்பிளியான [Yul](https://docs.soliditylang.org/en/latest/yul.html)-ஐ இங்கு பயன்படுத்துகிறோம். [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702)-க்குப் பிறகு ஒரு EOA-வும் குறியீட்டைக் கொண்டிருக்கலாம் (ஒரு ஒப்பந்தத்திற்கான பிரதிநிதித்துவம்) என்பதை நினைவில் கொள்ளவும், எனவே இந்தச் சரிபார்ப்பு குறியீட்டைக் கொண்ட கணக்குகளை அடையாளம் காண்கிறதே தவிர, கண்டிப்பாக ஒப்பந்தங்களை அல்ல. நமது நோக்கத்திற்கு, வெற்று முகவரிகளை நிராகரிப்பது என்பது சரியானது.

முழுமையான சார்பு இதோ:

```solidity
    function _update(address from, address to, uint256 value)
        internal virtual
        override(ERC20)
    {
        // எரித்தல் வில்லைகளை முகவரி(0)-க்கு அனுப்புகிறது, அதைத் தடுக்க வேண்டாம்
        if (to != address(0)) {
            require(to != address(this), "Can't send tokens to the contract address");

            bool isToContract;
            assembly {
               isToContract := gt(extcodesize(to), 0)
            }

            require(to.balance != 0 || isToContract, "Can't send tokens to an empty address");
        }

        super._update(from, to, value);
    }
```

புதிய குறியீட்டை வரியாகப் பார்ப்போம்:

```solidity
        require(to != address(this), "Can't send tokens to the contract address");
```

இது முதல் தேவை, `to` மற்றும் `this(address)` ஆகியவை ஒன்றல்ல என்பதைச் சரிபார்க்கவும்.

```solidity
        bool isToContract;
        assembly {
           isToContract := gt(extcodesize(to), 0)
        }
```

ஒரு முகவரி ஒப்பந்தமா என்பதை நாம் இப்படித்தான் சரிபார்க்கிறோம். Yul-லிருந்து நேரடியாக வெளியீட்டைப் பெற முடியாது, எனவே முடிவை வைத்திருக்க ஒரு மாறியை (variable) வரையறுக்கிறோம் (இந்த நிலையில் `isToContract`). Yul செயல்படும் விதம் என்னவென்றால், ஒவ்வொரு செயல்பாட்டுக் குறியீடும் ஒரு சார்பாகக் கருதப்படுகிறது. எனவே முதலில் ஒப்பந்தத்தின் அளவைப் பெற [`EXTCODESIZE`](https://www.evm.codes/#3b)-ஐ அழைக்கிறோம், பின்னர் அது பூஜ்ஜியமாக இல்லை என்பதைச் சரிபார்க்க [`GT`](https://www.evm.codes/#11)-ஐப் பயன்படுத்துகிறோம் (நாம் குறியிடப்படாத முழு எண்களைக் (unsigned integers) கையாளுகிறோம், எனவே நிச்சயமாக அது எதிர்மறையாக இருக்க முடியாது). பின்னர் முடிவை `isToContract`-இல் எழுதுகிறோம்.

```solidity
        require(to.balance != 0 || isToContract, "Can't send tokens to an empty address");
```

இறுதியாக, வெற்று முகவரிகளுக்கான உண்மையான சரிபார்ப்பு நம்மிடம் உள்ளது.

## நிர்வாக அணுகல் {#admin-access}

சில நேரங்களில் தவறுகளை ரத்து செய்யக்கூடிய ஒரு நிர்வாகி இருப்பது பயனுள்ளதாக இருக்கும். தவறாகப் பயன்படுத்துவதற்கான சாத்தியக்கூறுகளைக் குறைக்க, இந்த நிர்வாகி ஒரு [பல்கையெழுத்தாக (multisig)](https://blog.logrocket.com/security-choices-multi-signature-wallets/) இருக்கலாம், எனவே ஒரு செயலுக்குப் பல நபர்கள் ஒப்புக்கொள்ள வேண்டும். இந்தக் கட்டுரையில் நாம் இரண்டு நிர்வாக அம்சங்களைக் கொண்டிருப்போம்:

1. கணக்குகளை முடக்குதல் மற்றும் முடக்கத்தை நீக்குதல். உதாரணமாக, ஒரு கணக்கு சமரசம் செய்யப்பட்டிருக்கலாம் (compromised) என்ற நிலையில் இது பயனுள்ளதாக இருக்கும்.
2. சொத்துச் சுத்திகரிப்பு.

   சில நேரங்களில் மோசடி செய்பவர்கள் சட்டபூர்வமான தன்மையைப் பெற உண்மையான வில்லை ஒப்பந்தத்திற்கு மோசடியான வில்லைகளை அனுப்புகிறார்கள். உதாரணமாக, [இங்கே பார்க்கவும்](https://optimism.blockscout.com/token/0x2348B1a1228DDCd2dB668c3d30207c3E1852fBbe?tab=holders). சட்டபூர்வமான ERC-20 ஒப்பந்தம் [0x4200....0042](https://optimism.blockscout.com/token/0x4200000000000000000000000000000000000042) ஆகும். அதைப் போல நடிக்கும் மோசடி [0x234....bbe](https://optimism.blockscout.com/token/0x2348B1a1228DDCd2dB668c3d30207c3E1852fBbe) ஆகும்.

   மக்கள் தவறுதலாகச் சட்டபூர்வமான ERC-20 வில்லைகளை நமது ஒப்பந்தத்திற்கு அனுப்புவதும் சாத்தியமாகும், அவற்றை வெளியே எடுப்பதற்கான ஒரு வழியைக் கொண்டிருக்க விரும்புவதற்கு இதுவும் ஒரு காரணமாகும்.

நிர்வாக அணுகலைச் செயல்படுத்த ஓப்பன்செப்பெலின் இரண்டு வழிமுறைகளை வழங்குகிறது:

- [`Ownable`](https://docs.openzeppelin.com/contracts/5.x/access-control#ownership-and-ownable) ஒப்பந்தங்கள் ஒரே ஒரு உரிமையாளரைக் கொண்டுள்ளன. `onlyOwner` [மாற்றியைக் (modifier)](https://docs.soliditylang.org/en/latest/contracts.html#function-modifiers) கொண்ட சார்புகளை அந்த உரிமையாளரால் மட்டுமே அழைக்க முடியும். உரிமையாளர்கள் உரிமையை வேறு ஒருவருக்கு மாற்றலாம் அல்லது அதை முழுமையாகத் துறக்கலாம். மற்ற அனைத்துக் கணக்குகளின் உரிமைகளும் பொதுவாக ஒரே மாதிரியானவை.
- [`AccessControl`](https://docs.openzeppelin.com/contracts/5.x/access-control#role-based-access-control) ஒப்பந்தங்கள் [பங்கு அடிப்படையிலான அணுகல் கட்டுப்பாட்டைக் (role based access control - RBAC)](https://en.wikipedia.org/wiki/Role-based_access_control) கொண்டுள்ளன.

எளிமைக்காக, இந்தக் கட்டுரையில் நாம் `Ownable`-ஐப் பயன்படுத்துகிறோம்.

### ஒப்பந்தங்களை முடக்குதல் மற்றும் முடக்கத்தை நீக்குதல் {#freezing-and-thawing-contracts}

ஒப்பந்தங்களை முடக்குவதற்கும் முடக்கத்தை நீக்குவதற்கும் பல மாற்றங்கள் தேவை:

- எந்த முகவரிகள் முடக்கப்பட்டுள்ளன என்பதைக் கண்காணிக்க முகவரிகளிலிருந்து [பூலியன்களுக்கு (booleans)](https://en.wikipedia.org/wiki/Boolean_data_type) ஒரு [மேப்பிங் (mapping)](https://docs.soliditylang.org/en/latest/types.html#mapping-types). அனைத்து மதிப்புகளும் ஆரம்பத்தில் பூஜ்ஜியமாக இருக்கும், இது பூலியன் மதிப்புகளுக்குத் தவறு (false) எனப் பொருள் கொள்ளப்படும். இயல்பாகவே கணக்குகள் முடக்கப்படாததால் இதுவே நமக்குத் தேவை.

  ```solidity
      mapping(address => bool) public frozenAccounts;
  ```

- ஒரு கணக்கு முடக்கப்படும்போது அல்லது முடக்கம் நீக்கப்படும்போது ஆர்வமுள்ள எவருக்கும் தெரிவிக்க [நிகழ்வுகள்](https://docs.soliditylang.org/en/latest/contracts.html#events). தொழில்நுட்ப ரீதியாகப் பார்த்தால் இந்தச் செயல்களுக்கு நிகழ்வுகள் தேவையில்லை, ஆனால் புறச்சங்கிலிக் குறியீடு இந்த நிகழ்வுகளைக் கேட்கவும் என்ன நடக்கிறது என்பதை அறியவும் இது உதவுகிறது. வேறொருவருக்குத் தொடர்புடைய ஏதாவது நடக்கும்போது திறன் ஒப்பந்தம் அவற்றை வெளியிடுவது நல்ல பழக்கமாகக் கருதப்படுகிறது.

  நிகழ்வுகள் அட்டவணைப்படுத்தப்பட்டுள்ளன (indexed), எனவே ஒரு கணக்கு முடக்கப்பட்ட அல்லது முடக்கம் நீக்கப்பட்ட அனைத்து நேரங்களையும் தேட முடியும்.

  ```solidity
    // கணக்குகள் முடக்கப்படும்போது அல்லது விடுவிக்கப்படும்போது
    event AccountFrozen(address indexed _addr);
    event AccountThawed(address indexed _addr);
  ```

- கணக்குகளை முடக்குவதற்கும் முடக்கத்தை நீக்குவதற்குமான சார்புகள். இந்த இரண்டு சார்புகளும் ஏறக்குறைய ஒரே மாதிரியானவை, எனவே நாம் முடக்கும் சார்பை மட்டுமே பார்ப்போம்.

  ```solidity
      function freezeAccount(address addr)
        public
        onlyOwner
  ```

  [`public`](https://docs.soliditylang.org/en/latest/contracts.html#function-visibility) எனக் குறிக்கப்பட்ட சார்புகளைப் பிற திறன் ஒப்பந்தங்களிலிருந்து அல்லது நேரடியாக ஒரு பரிவர்த்தனை மூலம் அழைக்கலாம்.

  ```solidity
    {
        require(!frozenAccounts[addr], "Account already frozen");
        frozenAccounts[addr] = true;
        emit AccountFrozen(addr);
    }  // கணக்கை முடக்கு
  ```

  கணக்கு ஏற்கனவே முடக்கப்பட்டிருந்தால், மீளமைக்கவும். இல்லையெனில், அதை முடக்கி ஒரு நிகழ்வை `emit` செய்யவும்.

- முடக்கப்பட்ட கணக்கிலிருந்து பணம் நகர்த்தப்படுவதைத் தடுக்க `_update`-ஐ மாற்றவும். முடக்கப்பட்ட கணக்கிற்குப் பணத்தை இன்னும் பரிமாற்றம் செய்ய முடியும் என்பதை நினைவில் கொள்ளவும். இந்த வரியைச் சார்பின் தொடக்கத்தில், `if` தொகுதிக்கு வெளியே வைக்கவும், இதனால் முடக்கப்பட்ட கணக்கிலிருந்து வில்லைகளை எரிப்பதையும் இது தடுக்கிறது.

  ```solidity
       require(!frozenAccounts[from], "The account is frozen");
  ```

### சொத்துச் சுத்திகரிப்பு {#asset-cleanup}

இந்த ஒப்பந்தத்தால் வைத்திருக்கப்படும் ERC-20 வில்லைகளை வெளியிட, அவை சொந்தமான வில்லை ஒப்பந்தத்தில் [`transfer`](https://eips.ethereum.org/EIPS/eip-20#transfer) அல்லது [`approve`](https://eips.ethereum.org/EIPS/eip-20#approve) என்ற சார்பை நாம் அழைக்க வேண்டும். இந்த நிலையில் கொடுப்பனவுகளில் (allowances) எரிவாயுவை வீணாக்குவதில் எந்த அர்த்தமும் இல்லை, நாம் நேரடியாகப் பரிமாற்றம் செய்யலாம்.

```solidity
    function cleanupERC20(
        address erc20,
        address dest
    )
        public
        onlyOwner
    {
        IERC20 token = IERC20(erc20);
```

நாம் முகவரியைப் பெறும்போது ஒரு ஒப்பந்தத்திற்கான பொருளை (object) உருவாக்குவதற்கான தொடரியல் (syntax) இதுவாகும். இதைப் பயன்படுத்த, OpenZeppelin ERC-20 ஒப்பந்தத்திற்கான இடைமுகமான (interface) [IERC20-க்கான வரையறை](https://github.com/OpenZeppelin/openzeppelin-contracts/blob/master/contracts/token/ERC20/IERC20.sol) நமக்குத் தேவை. வழிகாட்டியின் (Wizard) `import {ERC20} from ...` வரி `ERC20`-ஐ மட்டுமே கொண்டுவருகிறது, எனவே கோப்பின் மேற்புறத்தில் உள்ள பிற இறக்குமதிகளுக்கு (imports) அடுத்து இந்த வரியைச் சேர்க்கவும்:

```solidity
import {IERC20} from "@openzeppelin/contracts/token/ERC20/IERC20.sol";
```

```solidity
        uint balance = token.balanceOf(address(this));
        token.transfer(dest, balance);
    }
```

இது ஒரு சுத்திகரிப்புச் சார்பாகும், எனவே நாம் எந்த வில்லைகளையும் விட்டுவிட விரும்பவில்லை. பயனரிடமிருந்து நிலுவையை கைமுறையாகப் பெறுவதற்குப் பதிலாக, நாம் செயல்முறையைத் தானியக்கமாக்கலாம்.

## முடிவுரை {#conclusion}

இது ஒரு சரியான தீர்வு அல்ல - "பயனர் தவறு செய்துவிட்டார்" என்ற சிக்கலுக்குச் சரியான தீர்வு எதுவும் இல்லை. இருப்பினும், இந்த வகையான சரிபார்ப்புகளைப் பயன்படுத்துவது குறைந்தபட்சம் சில தவறுகளையாவது தடுக்கலாம். கணக்குகளை முடக்கும் திறன் ஆபத்தானது என்றாலும், திருடப்பட்ட நிதியை ஹேக்கருக்கு மறுப்பதன் மூலம் சில ஹேக்கிங் தாக்குதல்களின் சேதத்தைக் குறைக்க இதைப் பயன்படுத்தலாம்.
