## நிறுவல் {#installation}

எக்கிட்னாவை Docker, Homebrew மூலமாகவோ அல்லது முன்-தொகுக்கப்பட்ட பைனரியைப் பயன்படுத்தியோ நிறுவலாம். இந்த வழிகாட்டியில் உள்ள எடுத்துக்காட்டுகள் எக்கிட்னா 2.3.3 மற்றும் solc 0.8.37 உடன் சோதிக்கப்பட்டன.

### Docker மூலம் எக்கிட்னா {#echidna-through-docker}

```sh
docker pull ghcr.io/crytic/echidna/echidna:latest
docker run --rm -it -v "$PWD":/src ghcr.io/crytic/echidna/echidna:latest
```

_கடைசி கட்டளை உங்கள் தற்போதைய கோப்பகத்திற்கான அணுகலைக் கொண்ட ஒரு Docker-இல் எக்கிட்னா இமேஜை இயக்குகிறது. உங்கள் ஹோஸ்டிலிருந்து கோப்புகளை மாற்றலாம், மேலும் Docker-இலிருந்து கோப்புகளில் கருவிகளை இயக்கலாம். இந்த இமேஜ் [ஸ்லித்தர்](https://github.com/crytic/slither), [crytic-compile](https://github.com/crytic/crytic-compile) மற்றும் [solc-select](https://github.com/crytic/solc-select) ஆகியவற்றுடனும் வருகிறது._

Docker-இன் உள்ளே, இதை இயக்கவும்:

```sh
solc-select install 0.8.37
solc-select use 0.8.37
cd /src
```

### பைனரி {#binary}

உங்கள் தளத்திற்கான சமீபத்திய வெளியீட்டை [https://github.com/crytic/echidna/releases/latest](https://github.com/crytic/echidna/releases/latest) என்பதிலிருந்து பதிவிறக்கவும். macOS அல்லது Linux-இல் நீங்கள் `brew install echidna` என்பதையும் இயக்கலாம், இது ஸ்லித்தர் மற்றும் crytic-compile ஆகியவற்றை அதனுடன் நிறுவுகிறது.

வெளியீட்டு பைனரியைப் பயன்படுத்தும் போது, [ஸ்லித்தர்](https://github.com/crytic/slither) மற்றும் [solc-select](https://github.com/crytic/solc-select) ஆகியவற்றை நீங்களே நிறுவவும் (எடுத்துக்காட்டாக, ஒரு Python மெய்நிகர் சூழலில் `pip3 install slither-analyzer solc-select`) மற்றும் ஒரு கம்பைலர் பதிப்பைத் தேர்ந்தெடுக்கவும்:

```sh
solc-select install 0.8.37
solc-select use 0.8.37
```

எக்கிட்னா ஸ்லித்தர் இல்லாமல் இயங்குகிறது, ஆனால் `require` அறிக்கைகளில் பயன்படுத்தப்படும் மேஜிக் எண்கள் போன்ற மாறிலிகளை ஸ்லித்தர் பிரித்தெடுக்கிறது, மேலும் பிழைகளை விரைவாகக் கண்டறிய கீழே உள்ள பல எடுத்துக்காட்டுகள் இதைச் சார்ந்துள்ளன.

## பண்பு அடிப்படையிலான ஃபஸ்ஸிங் அறிமுகம் {#introduction-to-property-based-fuzzing}

எக்கிட்னா என்பது ஒரு பண்பு அடிப்படையிலான ஃபஸ்ஸர் ஆகும், இதை எங்கள் முந்தைய வலைப்பதிவு இடுகைகளில் விவரித்துள்ளோம் ([1](https://blog.trailofbits.com/2018/03/09/echidna-a-smart-fuzzer-for-ethereum/), [2](https://blog.trailofbits.com/2018/05/03/state-machine-testing-with-echidna/), [3](https://blog.trailofbits.com/2020/03/30/an-echidna-for-all-seasons/)).

### ஃபஸ்ஸிங் {#fuzzing}

பாதுகாப்பு சமூகத்தில் [ஃபஸ்ஸிங்](https://wikipedia.org/wiki/Fuzzing) என்பது நன்கு அறியப்பட்ட ஒரு நுட்பமாகும். நிரலில் உள்ள பிழைகளைக் கண்டறிய ஏறக்குறைய சீரற்ற உள்ளீடுகளை உருவாக்குவது இதில் அடங்கும். பாரம்பரிய மென்பொருளுக்கான ஃபஸ்ஸர்கள் ([AFL](http://lcamtuf.coredump.cx/afl/) அல்லது [LibFuzzer](https://llvm.org/docs/LibFuzzer.html) போன்றவை) பிழைகளைக் கண்டறியும் திறமையான கருவிகளாக அறியப்படுகின்றன.

முற்றிலும் சீரற்ற உள்ளீடுகளை உருவாக்குவதைத் தாண்டி, சிறந்த உள்ளீடுகளை உருவாக்க பல நுட்பங்களும் உத்திகளும் உள்ளன, அவற்றுள்:

- ஒவ்வொரு செயல்பாட்டிலிருந்தும் பின்னூட்டத்தைப் பெற்று, அதைப் பயன்படுத்தி உருவாக்கத்தை வழிநடத்துதல். எடுத்துக்காட்டாக, புதிதாக உருவாக்கப்பட்ட உள்ளீடு ஒரு புதிய பாதையைக் கண்டறிவதற்கு வழிவகுத்தால், அதற்கு நெருக்கமான புதிய உள்ளீடுகளை உருவாக்குவது அர்த்தமுள்ளதாக இருக்கும்.
- கட்டமைப்பு கட்டுப்பாட்டை மதித்து உள்ளீட்டை உருவாக்குதல். எடுத்துக்காட்டாக, உங்கள் உள்ளீட்டில் செக்சம் கொண்ட தலைப்பு இருந்தால், செக்சமைச் சரிபார்க்கும் உள்ளீட்டை ஃபஸ்ஸரை உருவாக்க அனுமதிப்பது அர்த்தமுள்ளதாக இருக்கும்.
- புதிய உள்ளீடுகளை உருவாக்க அறியப்பட்ட உள்ளீடுகளைப் பயன்படுத்துதல்: செல்லுபடியாகும் உள்ளீட்டின் பெரிய தரவுத்தொகுப்பிற்கான அணுகல் உங்களிடம் இருந்தால், உங்கள் ஃபஸ்ஸர் அதன் உருவாக்கத்தை புதிதாகத் தொடங்குவதற்குப் பதிலாக, அவற்றிலிருந்து புதிய உள்ளீடுகளை உருவாக்க முடியும். இவை பொதுவாக _விதைகள் (seeds)_ என்று அழைக்கப்படுகின்றன.

### பண்பு அடிப்படையிலான ஃபஸ்ஸிங் {#property-based-fuzzing}

எக்கிட்னா ஒரு குறிப்பிட்ட ஃபஸ்ஸர் குடும்பத்தைச் சேர்ந்தது: [QuickCheck](https://wikipedia.org/wiki/QuickCheck) மூலம் பெரிதும் ஈர்க்கப்பட்ட பண்பு அடிப்படையிலான ஃபஸ்ஸிங். செயலிழப்புகளைக் கண்டறிய முயற்சிக்கும் கிளாசிக் ஃபஸ்ஸருக்கு மாறாக, பயனர் வரையறுத்த மாறிலிகளை உடைக்க எக்கிட்னா முயற்சிக்கும்.

திறன் ஒப்பந்தங்களில், மாறிலிகள் என்பவை Solidity சார்புகள் ஆகும், அவை ஒப்பந்தம் அடையக்கூடிய எந்தவொரு தவறான அல்லது செல்லாத நிலையையும் குறிக்கலாம், அவற்றுள்:

- தவறான அணுகல் கட்டுப்பாடு: தாக்குபவர் ஒப்பந்தத்தின் உரிமையாளராகிவிட்டார்.
- தவறான நிலை இயந்திரம்: ஒப்பந்தம் இடைநிறுத்தப்பட்டிருக்கும் போது வில்லைகளை மாற்ற முடியும்.
- தவறான எண்கணிதம்: பயனர் தனது இருப்பை அண்டர்ஃப்ளோ செய்து வரம்பற்ற இலவச வில்லைகளைப் பெறலாம்.

### எக்கிட்னா மூலம் ஒரு பண்பைச் சோதித்தல் {#testing-a-property-with-echidna}

எக்கிட்னா மூலம் ஒரு திறன் ஒப்பந்தத்தை எவ்வாறு சோதிப்பது என்று பார்ப்போம். இலக்கு பின்வரும் திறன் ஒப்பந்தம் [`token.sol`](https://github.com/crytic/building-secure-contracts/blob/master/program-analysis/echidna/example/token.sol):

```solidity
// SPDX-License-Identifier: AGPL-3.0
pragma solidity ^0.8.0;

contract Token {
    mapping(address => uint256) public balances;

    function airdrop() public {
        balances[msg.sender] = 1000;
    }

    function consume() public {
        require(balances[msg.sender] > 0);
        balances[msg.sender] -= 1;
    }

    function backdoor() public {
        balances[msg.sender] += 1;
    }
}
```

இந்த வில்லை பின்வரும் பண்புகளைக் கொண்டிருக்க வேண்டும் என்று நாம் கருதுவோம்:

- எவரும் அதிகபட்சமாக 1000 வில்லைகளை வைத்திருக்கலாம்
- வில்லையை மாற்ற முடியாது (இது ஒரு ERC-20 வில்லை அல்ல)

### ஒரு பண்பை எழுதுதல் {#write-a-property}

எக்கிட்னா பண்புகள் Solidity சார்புகள் ஆகும். ஒரு பண்பு:

- எந்த வாதமும் (argument) கொண்டிருக்கக்கூடாது
- அது வெற்றிகரமாக இருந்தால் `true` என்பதை வழங்க வேண்டும்
- அதன் பெயர் `echidna` என்று தொடங்க வேண்டும்

எக்கிட்னா செய்யும் செயல்கள்:

- பண்பைச் சோதிக்க தன்னிச்சையான பரிவர்த்தனைகளைத் தானாகவே உருவாக்கும்.
- ஒரு பண்பு `false` என்பதை வழங்க அல்லது பிழையை எறிய வழிவகுக்கும் எந்தவொரு பரிவர்த்தனைகளையும் புகாரளிக்கும்.
- ஒரு பண்பை அழைக்கும் போது பக்க விளைவுகளை நிராகரிக்கும் (அதாவது, பண்பு ஒரு நிலை மாறியை மாற்றினால், அது சோதனைக்குப் பிறகு நிராகரிக்கப்படும்)

அழைப்பாளர் 1000 வில்லைகளுக்கு மேல் வைத்திருக்கவில்லை என்பதைப் பின்வரும் பண்பு சரிபார்க்கிறது:

```solidity
function echidna_balance_under_1000() public view returns (bool) {
    return balances[msg.sender] <= 1000;
}
```

உங்கள் ஒப்பந்தத்தை உங்கள் பண்புகளிலிருந்து பிரிக்க மரபுரிமையைப் (inheritance) பயன்படுத்தவும்:

```solidity
contract TestToken is Token {
    function echidna_balance_under_1000() public view returns (bool) {
        return balances[msg.sender] <= 1000;
    }
}
```

[`testtoken.sol`](https://github.com/crytic/building-secure-contracts/blob/master/program-analysis/echidna/example/testtoken.sol) பண்பைச் செயல்படுத்துகிறது மற்றும் வில்லையிலிருந்து மரபுரிமையாகப் பெறுகிறது.

### ஒரு ஒப்பந்தத்தைத் தொடங்குதல் {#initiate-a-contract}

எக்கிட்னாவிற்கு வாதம் இல்லாத ஒரு [ஆக்கி](/developers/docs/smart-contracts/anatomy/#constructor-functions) தேவை. உங்கள் ஒப்பந்தத்திற்கு ஒரு குறிப்பிட்ட துவக்கம் தேவைப்பட்டால், நீங்கள் அதை ஆக்கியில் செய்ய வேண்டும்.

எக்கிட்னாவில் சில குறிப்பிட்ட முகவரிகள் உள்ளன:

- `0x30000` இது ஆக்கியை அழைக்கிறது.
- `0x10000`, `0x20000`, மற்றும் `0x30000` ஆகியவை மற்ற சார்புகளைத் தோராயமாக அழைக்கின்றன.
- `0x00a329c0648769A73afAc7F9381E08FB43dBEA72` இங்குதான் சோதனையில் உள்ள ஒப்பந்தம் நிலைநிறுத்தப்படுகிறது.

எங்கள் தற்போதைய எடுத்துக்காட்டில் எங்களுக்கு எந்தவொரு குறிப்பிட்ட துவக்கமும் தேவையில்லை, இதன் விளைவாக எங்கள் ஆக்கி காலியாக உள்ளது.

### எக்கிட்னாவை இயக்குதல் {#run-echidna}

எக்கிட்னா இதனுடன் தொடங்கப்படுகிறது:

```sh
echidna contract.sol
```

contract.sol பல ஒப்பந்தங்களைக் கொண்டிருந்தால், நீங்கள் இலக்கைக் குறிப்பிடலாம்:

```sh
echidna contract.sol --contract MyContract
```

டெர்மினலில் இயங்கும் போது, எக்கிட்னா ஒரு ஊடாடும் UI-ஐக் காட்டுகிறது. கீழே உள்ள எடுத்துக்காட்டுகளைப் போல எளிய உரை வெளியீட்டைப் பெற `--format text` என்பதைச் சேர்க்கவும்.

### சுருக்கம்: ஒரு பண்பைச் சோதித்தல் {#summary-testing-a-property}

எங்கள் எடுத்துக்காட்டில் எக்கிட்னாவின் ஓட்டத்தைப் பின்வருபவை சுருக்கமாகக் கூறுகின்றன:

```solidity
contract TestToken is Token {
    constructor() {}

    function echidna_balance_under_1000() public view returns (bool) {
        return balances[msg.sender] <= 1000;
    }
}
```

```sh
echidna testtoken.sol --contract TestToken
...

echidna_balance_under_1000: failed!💥
  Call sequence:
    TestToken.airdrop()
    TestToken.backdoor()

...
```

`backdoor` அழைக்கப்பட்டால் பண்பு மீறப்படுவதாக எக்கிட்னா கண்டறிந்தது.

## ஃபஸ்ஸிங் பிரச்சாரத்தின் போது அழைக்க வேண்டிய சார்புகளை வடிகட்டுதல் {#filtering-functions-to-call-during-a-fuzzing-campaign}

ஃபஸ் செய்ய வேண்டிய சார்புகளை எவ்வாறு வடிகட்டுவது என்று பார்ப்போம்.
இலக்கு பின்வரும் திறன் ஒப்பந்தம்:

```solidity
// SPDX-License-Identifier: AGPL-3.0
pragma solidity ^0.8.0;

contract C {
    bool state1 = false;
    bool state2 = false;
    bool state3 = false;
    bool state4 = false;

    function f(uint256 x) public {
        require(x == 12);
        state1 = true;
    }

    function g(uint256 x) public {
        require(state1);
        require(x == 8);
        state2 = true;
    }

    function h(uint256 x) public {
        require(state2);
        require(x == 42);
        state3 = true;
    }

    function i() public {
        require(state3);
        state4 = true;
    }

    function reset1() public {
        state1 = false;
        state2 = false;
        state3 = false;
        return;
    }

    function reset2() public {
        state1 = false;
        state2 = false;
        state3 = false;
        return;
    }

    function echidna_state4() public view returns (bool) {
        return (!state4);
    }
}
```

இந்தச் சிறிய எடுத்துக்காட்டு ஒரு நிலை மாறியை மாற்ற ஒரு குறிப்பிட்ட பரிவர்த்தனைகளின் வரிசையைக் கண்டறிய எக்கிட்னாவைக் கட்டாயப்படுத்துகிறது.
இது ஒரு ஃபஸ்ஸருக்குக் கடினமானது.
இதைச் சரிபார்க்க நாம் எக்கிட்னாவை இயக்கலாம்:

```sh
echidna multi.sol
...
echidna_state4: passing
...
```

### சார்புகளை வடிகட்டுதல் {#filtering-functions}

இந்த ஒப்பந்தத்தைச் சோதிக்கச் சரியான வரிசையைக் கண்டறிவதில் எக்கிட்னா சிக்கலைக் கொண்டுள்ளது, ஏனெனில் இரண்டு மீட்டமைப்பு சார்புகளும் (`reset1` மற்றும் `reset2`) அனைத்து நிலை மாறிகளையும் `false` என அமைக்கும்.
இருப்பினும், மீட்டமைப்பு சார்பைக் கறுப்புப்பட்டியலில் சேர்க்க அல்லது `f`, `g`,
`h` மற்றும் `i` சார்புகளை மட்டும் அனுமதிப்பட்டியலில் சேர்க்க ஒரு சிறப்பு எக்கிட்னா அம்சத்தைப் பயன்படுத்தலாம்.

சார்புகளைக் கறுப்புப்பட்டியலில் சேர்க்க, இந்த உள்ளமைவு கோப்பைப் பயன்படுத்தலாம்:

```yaml
filterBlacklist: true
filterFunctions: ["C.reset1()", "C.reset2()"]
```

சார்புகளை வடிகட்டுவதற்கான மற்றொரு அணுகுமுறை அனுமதிப்பட்டியலில் உள்ள சார்புகளைப் பட்டியலிடுவதாகும். அதைச் செய்ய, இந்த உள்ளமைவு கோப்பைப் பயன்படுத்தலாம்:

```yaml
filterBlacklist: false
filterFunctions: ["C.f(uint256)", "C.g(uint256)", "C.h(uint256)", "C.i()"]
```

- `filterBlacklist` இயல்பாகவே `true` ஆக இருக்கும்.
- முழு சார்பு பெயரிலும் வடிகட்டுதல் செய்யப்படுகிறது: ஒப்பந்தத்தின் பெயர், ஒரு `.`, மற்றும் ABI கையொப்பம் (எடுத்துக்காட்டாக `C.f(uint256)`). உங்களிடம் `f()` மற்றும் `f(uint256)` இருந்தால், எதை வடிகட்ட வேண்டும் என்பதை நீங்கள் சரியாகத் தேர்ந்தெடுக்கலாம். `"reset1"` போன்ற வெறும் பெயர் எதனுடனும் பொருந்தாது.

### எக்கிட்னாவை இயக்குதல் {#run-echidna-1}

`blacklist.yaml` உள்ளமைவு கோப்புடன் எக்கிட்னாவை இயக்க:

```sh
echidna multi.sol --config blacklist.yaml
...
echidna_state4: failed!💥
  Call sequence:
    C.f(12)
    C.g(8)
    C.h(42)
    C.i()
```

பண்பைப் பொய்யாக்குவதற்கான பரிவர்த்தனைகளின் வரிசையை எக்கிட்னா உடனடியாகக் கண்டறியும்.

### சுருக்கம்: சார்புகளை வடிகட்டுதல் {#summary-filtering-functions}

ஒரு ஃபஸ்ஸிங் பிரச்சாரத்தின் போது அழைக்க வேண்டிய சார்புகளை எக்கிட்னா கறுப்புப்பட்டியலில் அல்லது அனுமதிப்பட்டியலில் சேர்க்க இதைப் பயன்படுத்தலாம்:

```yaml
filterBlacklist: true
filterFunctions: ["C.f1()", "C.f2()", "C.f3()"]
```

```sh
echidna contract.sol --config config.yaml
...
```

`filterBlacklist` பூலியனின் மதிப்பைப் பொறுத்து, `C.f1()`, `C.f2()` மற்றும் `C.f3()` ஆகியவற்றைக் கறுப்புப்பட்டியலில் சேர்ப்பதன் மூலமாகவோ அல்லது இவற்றை மட்டும் அழைப்பதன் மூலமாகவோ எக்கிட்னா ஒரு ஃபஸ்ஸிங் பிரச்சாரத்தைத் தொடங்குகிறது.

## எக்கிட்னா மூலம் Solidity-இன் உறுதிப்படுத்தலை எவ்வாறு சோதிப்பது {#how-to-test-soliditys-assert-with-echidna}

இந்தச் சிறிய வழிகாட்டியில், ஒப்பந்தங்களில் உறுதிப்படுத்தல் சரிபார்ப்பைச் சோதிக்க எக்கிட்னாவை எவ்வாறு பயன்படுத்துவது என்பதைக் காட்டப் போகிறோம். இது போன்ற ஒரு ஒப்பந்தம் நம்மிடம் இருப்பதாக வைத்துக்கொள்வோம்:

```solidity
// SPDX-License-Identifier: AGPL-3.0
pragma solidity ^0.8.0;

contract Incrementor {
    uint256 private counter = 2 ** 200;

    function inc(uint256 val) public returns (uint256) {
        uint256 tmp = counter;
        unchecked {
            counter += val;
        }
        // tmp <= counter
        return (counter - tmp);
    }
}
```

Solidity 0.8 முதல், எண்கணித அளவுமீறல்கள் இயல்பாகவே மீளமைக்கப்படும். `unchecked` தொகுதி ரேப்பிங் நடத்தையை மீட்டமைக்கிறது, இதனால் `counter` அளவுமீறலாம், இதுவே எக்கிட்னா கண்டறிய வேண்டும் என்று நாம் விரும்பும் பிழையாகும்.

### ஒரு உறுதிப்படுத்தலை எழுதுதல் {#write-an-assertion}

அதன் வித்தியாசத்தை வழங்கிய பிறகு `tmp` என்பது `counter`-ஐ விடக் குறைவாகவோ அல்லது சமமாகவோ இருப்பதை உறுதிசெய்ய விரும்புகிறோம். நாம் ஒரு எக்கிட்னா பண்பை எழுதலாம், ஆனால் `tmp` மதிப்பை எங்காவது சேமிக்க வேண்டும். அதற்குப் பதிலாக, இது போன்ற ஒரு உறுதிப்படுத்தலை நாம் பயன்படுத்தலாம்:

```solidity
// SPDX-License-Identifier: AGPL-3.0
pragma solidity ^0.8.0;

contract Incrementor {
    uint256 private counter = 2 ** 200;

    function inc(uint256 val) public returns (uint256) {
        uint256 tmp = counter;
        unchecked {
            counter += val;
        }
        assert(tmp <= counter);
        return (counter - tmp);
    }
}
```

### எக்கிட்னாவை இயக்குதல் {#run-echidna-2}

உறுதிப்படுத்தல் தோல்வி சோதனையை இயக்க, கட்டளை வரியில் `--test-mode assertion` என்பதை அனுப்பவும் அல்லது ஒரு [எக்கிட்னா உள்ளமைவு கோப்பை](https://secure-contracts.com/program-analysis/echidna/configuration.html) `config.yaml` உருவாக்கவும்:

```yaml
testMode: assertion
```

இந்த ஒப்பந்தத்தை எக்கிட்னாவில் இயக்கும் போது, எதிர்பார்த்த முடிவுகளைப் பெறுகிறோம்:

```sh
echidna assert.sol --config config.yaml
...
inc(uint256): failed!💥
  Call sequence:
    Incrementor.inc(49775183111401053618147883626307284970293609617350871827880350793793149469639)
    Incrementor.inc(5144534562104187441558356530962235826491531939599480973208359850367425338350)
    Incrementor.inc(60872766323599926080006863949466160074900015204811509590967924145028961380449)
...
```

நீங்கள் பார்ப்பது போல், `inc` சார்பில் சில உறுதிப்படுத்தல் தோல்விகளை எக்கிட்னா புகாரளிக்கிறது. ஒரு சார்புக்கு ஒன்றுக்கு மேற்பட்ட உறுதிப்படுத்தல்களைச் சேர்ப்பது சாத்தியமாகும், ஆனால் எந்த உறுதிப்படுத்தல் தோல்வியடைந்தது என்பதை எக்கிட்னாவால் கூற முடியாது.

### உறுதிப்படுத்தல்களை எப்போது, எப்படிப் பயன்படுத்துவது {#when-and-how-use-assertions}

வெளிப்படையான பண்புகளுக்கு மாற்றாக உறுதிப்படுத்தல்களைப் பயன்படுத்தலாம், குறிப்பாகச் சரிபார்க்க வேண்டிய நிபந்தனைகள் சில செயல்பாடுகளின் `f` சரியான பயன்பாட்டுடன் நேரடியாகத் தொடர்புடையதாக இருந்தால். சில குறியீடுகளுக்குப் பிறகு உறுதிப்படுத்தல்களைச் சேர்ப்பது, அது செயல்படுத்தப்பட்ட உடனேயே சரிபார்ப்பு நடக்கும் என்பதைச் செயல்படுத்தும்:

```solidity
function f(..) public {
    // சில சிக்கலான குறியீடு
    ...
    assert (condition);
    ...
}

```

மாறாக, வெளிப்படையான எக்கிட்னா பண்பைப் பயன்படுத்துவது தோராயமாகப் பரிவர்த்தனைகளைச் செயல்படுத்தும், மேலும் அது எப்போது சரிபார்க்கப்படும் என்பதைச் சரியாகச் செயல்படுத்த எளிதான வழி இல்லை. இந்தத் தீர்வைச் செய்வது இன்னும் சாத்தியமாகும்:

```solidity
function echidna_assert_after_f() public returns (bool) {
    f(..);
    return(condition);
}
```

இருப்பினும், சில சிக்கல்கள் உள்ளன:

- `f` என்பது `internal` அல்லது `external` என அறிவிக்கப்பட்டால் அது தோல்வியடையும்.
- `f`-ஐ அழைக்க எந்த வாதங்களைப் பயன்படுத்த வேண்டும் என்பது தெளிவாக இல்லை.
- `f` மீளமைக்கப்பட்டால், பண்பு தோல்வியடையும்.

பொதுவாக, உறுதிப்படுத்தல்களை எவ்வாறு பயன்படுத்துவது என்பது குறித்து [ஜான் ரெகரின் பரிந்துரையைப்](https://blog.regehr.org/archives/1091) பின்பற்றப் பரிந்துரைக்கிறோம்:

- உறுதிப்படுத்தல் சரிபார்ப்பின் போது எந்தப் பக்க விளைவையும் கட்டாயப்படுத்த வேண்டாம். எடுத்துக்காட்டாக: `assert(ChangeStateAndReturn() == 1)`
- வெளிப்படையான அறிக்கைகளை உறுதிப்படுத்த வேண்டாம். எடுத்துக்காட்டாக `assert(var >= 0)` இதில் `var` என்பது `uint` என அறிவிக்கப்பட்டுள்ளது.

இறுதியாக, தயவுசெய்து `assert` என்பதற்குப் பதிலாக `require` என்பதைப் **பயன்படுத்த வேண்டாம்**, ஏனெனில் எக்கிட்னாவால் அதைக் கண்டறிய முடியாது (ஆனால் ஒப்பந்தம் எப்படியும் மீளமைக்கப்படும்).

### சுருக்கம்: உறுதிப்படுத்தல் சரிபார்ப்பு {#summary-assertion-checking}

எங்கள் எடுத்துக்காட்டில் எக்கிட்னாவின் ஓட்டத்தைப் பின்வருபவை சுருக்கமாகக் கூறுகின்றன:

```solidity
contract Incrementor {
    uint256 private counter = 2 ** 200;

    function inc(uint256 val) public returns (uint256) {
        uint256 tmp = counter;
        unchecked {
            counter += val;
        }
        assert(tmp <= counter);
        return (counter - tmp);
    }
}
```

```sh
echidna assert.sol --test-mode assertion
...
inc(uint256): failed!💥
  Call sequence:
    Incrementor.inc(49775183111401053618147883626307284970293609617350871827880350793793149469639)
    Incrementor.inc(5144534562104187441558356530962235826491531939599480973208359850367425338350)
    Incrementor.inc(60872766323599926080006863949466160074900015204811509590967924145028961380449)
...
```

இந்தச் சார்பு பெரிய வாதங்களுடன் பல முறை அழைக்கப்பட்டால் `inc`-இல் உள்ள உறுதிப்படுத்தல் தோல்வியடையக்கூடும் என்று எக்கிட்னா கண்டறிந்தது.

## எக்கிட்னா கார்பஸைச் சேகரித்தல் மற்றும் மாற்றுதல் {#collecting-and-modifying-an-echidna-corpus}

எக்கிட்னாவுடன் பரிவர்த்தனைகளின் கார்பஸை எவ்வாறு சேகரிப்பது மற்றும் பயன்படுத்துவது என்று பார்ப்போம். இலக்கு பின்வரும் திறன் ஒப்பந்தம் [`magic.sol`](https://github.com/crytic/building-secure-contracts/blob/master/program-analysis/echidna/example/magic.sol):

```solidity
// SPDX-License-Identifier: AGPL-3.0
pragma solidity ^0.8.0;

contract C {
    bool value_found = false;

    function magic(uint256 magic_1, uint256 magic_2, uint256 magic_3, uint256 magic_4) public {
        require(magic_1 == 42);
        require(magic_2 == 129);
        require(magic_3 == magic_4 + 333);
        value_found = true;
        return;
    }

    function echidna_magic_values() public view returns (bool) {
        return !value_found;
    }
}
```

இந்தச் சிறிய எடுத்துக்காட்டு ஒரு நிலை மாறியை மாற்றக் குறிப்பிட்ட மதிப்புகளைக் கண்டறிய எக்கிட்னாவைக் கட்டாயப்படுத்துகிறது. இது ஒரு ஃபஸ்ஸருக்குக் கடினமானது.
இதைச் சரிபார்க்க நாம் எக்கிட்னாவை இயக்கலாம்:

```sh
echidna magic.sol
...

echidna_magic_values: passing
...
```

இருப்பினும், இந்த ஃபஸ்ஸிங் பிரச்சாரத்தை இயக்கும் போது கார்பஸைச் சேகரிக்க நாம் இன்னும் எக்கிட்னாவைப் பயன்படுத்தலாம்.

### கார்பஸைச் சேகரித்தல் {#collecting-a-corpus}

கார்பஸ் சேகரிப்பை இயக்க, ஒரு கார்பஸ் கோப்பகத்தை உருவாக்கவும்:

```sh
mkdir corpus-magic
```

மற்றும் ஒரு [எக்கிட்னா உள்ளமைவு கோப்பு](https://secure-contracts.com/program-analysis/echidna/configuration.html) `config.yaml`:

```yaml
corpusDir: "corpus-magic"
```

இப்போது நாம் நமது கருவியை இயக்கலாம் மற்றும் சேகரிக்கப்பட்ட கார்பஸைச் சரிபார்க்கலாம்:

```sh
echidna magic.sol --config config.yaml
```

எக்கிட்னாவால் இன்னும் சரியான மேஜிக் மதிப்புகளைக் கண்டறிய முடியவில்லை. அது எங்குச் சிக்கிக்கொள்கிறது என்பதைப் பார்க்க, `corpus-magic/covered.*.txt` கவரேஜ் அறிக்கையைப் பார்க்கவும்:

```text
7 | *   |     function magic(uint256 magic_1, uint256 magic_2, uint256 magic_3, uint256 magic_4) public {
  8 | *r  |         require(magic_1 == 42);
  9 | *r  |         require(magic_2 == 129);
 10 | *r  |         require(magic_3 == magic_4 + 333);
 11 |     |         value_found = true;
 12 |     |         return;
```

`r` லேபிள் என்பது எக்கிட்னா வரியை அடைந்தது, ஆனால் செயல்படுத்தல் அங்கு மீளமைக்கப்பட்டது, மேலும் கடைசி `require`-க்குப் பிந்தைய வரிகள் ஒருபோதும் செயல்படுத்தப்படவில்லை என்பதாகும்.

எக்கிட்னா சேகரித்த பரிவர்த்தனை வரிசைகள் `corpus-magic/coverage/`-இல் JSON கோப்புகளாகச் சேமிக்கப்படுகின்றன. எடுத்துக்காட்டாக, இந்தக் கோப்புகளில் ஒன்றின் முதல் பரிவர்த்தனை:

### கார்பஸை விதைத்தல் {#seeding-a-corpus}

`magic` சார்பைக் கையாள எக்கிட்னாவிற்குச் சில உதவிகள் தேவை. அதற்கான பொருத்தமான அளவுருக்களைப் பயன்படுத்த உள்ளீட்டை நகலெடுத்து மாற்றப் போகிறோம் (கோப்பு பெயர்கள் சீரற்றவை, எனவே உங்கள் சொந்த `corpus-magic/coverage/` கோப்பகத்திலிருந்து ஒன்றைப் பயன்படுத்தவும்):

```sh
cp corpus-magic/coverage/249425678654647553.txt corpus-magic/coverage/new.txt
```

`magic(42,129,333,0)`-ஐ அழைக்கும் ஒற்றைப் பரிவர்த்தனையைக் கொண்டிருக்கும் வகையில் `new.txt`-ஐ மாற்றுவோம். இப்போது, நாம் எக்கிட்னாவை மீண்டும் இயக்கலாம்:

```sh
echidna magic.sol --config config.yaml
...
echidna_magic_values: failed!💥
  Call sequence:
    C.magic(42,129,333,0)

...
```

இந்த முறை, பண்பு உடனடியாக மீறப்படுவதை அது கண்டறிந்தது.

## அதிக எரிவாயு நுகர்வு கொண்ட பரிவர்த்தனைகளைக் கண்டறிதல் {#finding-transactions-with-high-gas-consumption}

எக்கிட்னா மூலம் அதிக எரிவாயு நுகர்வு கொண்ட பரிவர்த்தனைகளை எவ்வாறு கண்டறிவது என்று பார்ப்போம். எக்கிட்னாவின் பழைய பதிப்புகளில் இதற்கான `estimateGas` விருப்பம் இருந்தது; இது எக்கிட்னா 2.3.0-இல் அகற்றப்பட்டது. அதற்குப் பதிலாக, `gasleft()` மூலம் எரிவாயுவை அளவிடுகிறோம் மற்றும் எக்கிட்னாவின் [உகப்பாக்கப் பயன்முறை (optimization mode)](https://secure-contracts.com/program-analysis/echidna/advanced/optimization_mode.html) அதை அதிகரிக்க அனுமதிக்கிறோம். இலக்கு பின்வரும் திறன் ஒப்பந்தம்:

```solidity
// SPDX-License-Identifier: AGPL-3.0
pragma solidity ^0.8.0;

contract C {
    uint256 state;

    function expensive(uint8 times) internal {
        for (uint8 i = 0; i < times; i++) {
            state = state + i;
        }
    }

    function f(uint256 x, uint256 y, uint8 times) public {
        if (x == 42 && y == 123) {
            expensive(times);
        } else {
            state = 0;
        }
    }
}
```

இங்கு `expensive` அதிக எரிவாயு நுகர்வைக் கொண்டிருக்கலாம்.

### எரிவாயு நுகர்வை அளவிடுதல் {#measuring-gas-consumption}

உகப்பாக்கப் பயன்முறையில், எக்கிட்னா எந்த வாதமும் இல்லாமல் `int256`-ஐ வழங்கும் `echidna_` என்று தொடங்கும் சார்புகளைத் தேடுகிறது, மேலும் வழங்கப்பட்ட மதிப்பை அதிகரிக்கும் பரிவர்த்தனைகளின் வரிசையைக் கண்டறிய முயற்சிக்கிறது. `f`-ஐ அழைக்கும், அது பயன்படுத்திய எரிவாயுவைப் பதிவுசெய்யும் மற்றும் அதிகபட்சத்தை வெளிப்படுத்தும் ஒரு சோதனை ஒப்பந்தத்தைச் சேர்க்கிறோம் (இரண்டு ஒப்பந்தங்களையும் `gas.sol`-இல் சேமிக்கவும்):

```solidity
contract TestGas is C {
    int256 maxGasUsed;

    function measureF(uint256 x, uint256 y, uint8 times) public {
        uint256 start = gasleft();
        f(x, y, times);
        int256 used = int256(start - gasleft());
        if (used > maxGasUsed) {
            maxGasUsed = used;
        }
    }

    function echidna_opt_gas_f() public view returns (int256) {
        return maxGasUsed;
    }
}
```

உகப்பாக்கப் பயன்முறையை இயக்க, ஒரு உள்ளமைவு கோப்பை `config.yaml` உருவாக்கவும். இந்த எடுத்துக்காட்டில், முடிவுகளைப் புரிந்துகொள்வதை எளிதாக்கப் பரிவர்த்தனை வரிசையின் அளவையும் குறைப்போம்:

```yaml
testMode: optimization
seqLen: 2
```

### எக்கிட்னாவை இயக்குதல் {#run-echidna-3}

உள்ளமைவு கோப்பை உருவாக்கியதும், நாம் எக்கிட்னாவை இப்படி இயக்கலாம்:

```sh
echidna gas.sol --contract TestGas --config config.yaml
...
echidna_opt_gas_f: max value: 127128

  Call sequence:
    TestGas.measureF(42,123,223)

...
```

- காட்டப்படும் எரிவாயு எக்கிட்னா இயங்கும் EVM செயலாக்கமான [hevm](https://github.com/argotorg/hevm) மூலம் அளவிடப்படுகிறது, மேலும் இது `measureF`-இலிருந்து உள் அழைப்பின் மேல்நிலையை (overhead) உள்ளடக்கியது.
- அதிகபட்சம் தனித்துவமானது அல்ல: ஒவ்வொரு பிரச்சாரமும் சீரற்றது, மேலும் நீண்ட பிரச்சாரங்கள் (எடுத்துக்காட்டாக `--test-limit 200000`) பெரிய மதிப்புகளைக் கண்டறிய முனைகின்றன.

### எரிவாயுவைக் குறைக்கும் அழைப்புகளை வடிகட்டுதல் {#filtering-out-gas-reducing-calls}

மேலே உள்ள **ஃபஸ்ஸிங் பிரச்சாரத்தின் போது அழைக்க வேண்டிய சார்புகளை வடிகட்டுதல்** குறித்த வழிகாட்டி உங்கள் சோதனையிலிருந்து சில சார்புகளை எவ்வாறு அகற்றுவது என்பதைக் காட்டுகிறது.  
துல்லியமான எரிவாயு மதிப்பீட்டைப் பெறுவதற்கு இது முக்கியமானதாக இருக்கலாம்.
பின்வரும் எடுத்துக்காட்டைக் கவனியுங்கள்:

```solidity
// SPDX-License-Identifier: AGPL-3.0
pragma solidity ^0.8.0;

contract C {
    address[] addrs;

    function push(address a) public {
        addrs.push(a);
    }

    function pop() public {
        addrs.pop();
    }

    function clear() public {
        delete addrs;
    }

    function check() public {
        for (uint256 i = 0; i < addrs.length; i++)
            for (uint256 j = i + 1; j < addrs.length; j++)
                if (addrs[i] == addrs[j]) addrs[j] = address(0x0);
    }

    function echidna_opt_gas_check() public returns (int256) {
        uint256 start = gasleft();
        check();
        return int256(start - gasleft());
    }
}
```

`echidna_opt_gas_check` `check`-ஐ அழைக்கிறது மற்றும் அதன் எரிவாயு செலவை வழங்குகிறது. ஒவ்வொரு எக்கிட்னா சோதனைச் சார்பைப் போலவே, அதன் நிலை மாற்றங்களும் பின்னர் நிராகரிக்கப்படும்.

எக்கிட்னாவால் அனைத்துச் சார்புகளையும் அழைக்க முடிந்தால், அதிக எரிவாயு செலவு கொண்ட பரிவர்த்தனைகளை அது எளிதில் கண்டறியாது:

```sh
echidna pushpop.sol --test-mode optimization
...
echidna_opt_gas_check: max value: 265706
...
```

ஏனெனில் செலவு `addrs`-இன் அளவைப் பொறுத்தது மற்றும் சீரற்ற அழைப்புகள் வரிசையை (array) கிட்டத்தட்டக் காலியாக விட முனைகின்றன.
இருப்பினும், `pop` மற்றும் `clear` ஆகியவற்றைக் கறுப்புப்பட்டியலில் சேர்ப்பது எங்களுக்குச் சிறந்த முடிவுகளைத் தருகிறது:

```yaml
testMode: optimization
filterBlacklist: true
filterFunctions: ["C.pop()", "C.clear()"]
```

```sh
echidna pushpop.sol --config config.yaml
...
echidna_opt_gas_check: max value: 2446228
...
```

இந்த முடிவுக்கான அழைப்பு வரிசையைச் சுருக்குவதற்குப் பல நிமிடங்கள் ஆகும், ஏனெனில் ஒவ்வொரு மறுஇயக்கமும் விலையுயர்ந்த `check` சார்பை அழைக்கிறது.

### சுருக்கம்: அதிக எரிவாயு நுகர்வு கொண்ட பரிவர்த்தனைகளைக் கண்டறிதல் {#summary-finding-transactions-with-high-gas-consumption}

`int256`-ஐ வழங்கும் `echidna_` சார்பில் `gasleft()` மூலம் எரிவாயுவை அளவிடுவதன் மூலமும், உகப்பாக்கப் பயன்முறையில் இயங்குவதன் மூலமும் அதிக எரிவாயு நுகர்வு கொண்ட பரிவர்த்தனைகளை எக்கிட்னா கண்டறிய முடியும்:

```yaml
testMode: optimization
```

```sh
echidna contract.sol --config config.yaml
...
```

ஃபஸ்ஸிங் பிரச்சாரம் முடிந்ததும், கண்டறியப்பட்ட அதிகபட்ச மதிப்பையும் அதை உருவாக்கிய பரிவர்த்தனைகளின் வரிசையையும் எக்கிட்னா புகாரளிக்கும்.
