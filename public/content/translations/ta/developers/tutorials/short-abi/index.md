## அறிமுகம் {#introduction}

இந்தக் கட்டுரையில், நீங்கள் [ஆப்டிமிஸ்டிக் ரோலப்கள் (optimistic rollups)](/developers/docs/scaling/optimistic-rollups), அவற்றில் பரிவர்த்தனைகளுக்கான செலவு மற்றும் அந்த மாறுபட்ட செலவு அமைப்பு எத்தேரியம் முதன்மை வலைப்பின்னலில் (Ethereum Mainnet) உள்ளதை விட வெவ்வேறு விஷயங்களுக்கு எவ்வாறு உகப்பாக்கக் கோருகிறது என்பதைப் பற்றி அறிந்துகொள்வீர்கள்.
இந்த உகப்பாக்கத்தை எவ்வாறு செயல்படுத்துவது என்பதையும் நீங்கள் அறிந்துகொள்வீர்கள்.

### முழு வெளிப்படுத்தல் {#full-disclosure}

நான் ஒரு முழுநேர [ஆப்டிமிசம்](https://www.optimism.io/) ஊழியர், எனவே இந்தக் கட்டுரையில் உள்ள எடுத்துக்காட்டுகள் ஆப்டிமிசத்தில் இயங்கும்.
இருப்பினும், இங்கு விளக்கப்பட்டுள்ள நுட்பம் மற்ற ரோலப்களுக்கும் (rollups) அதேபோன்று சிறப்பாகச் செயல்பட வேண்டும்.

### கலைச்சொற்கள் {#terminology}

ரோலப்களைப் பற்றி விவாதிக்கும்போது, 'அடுக்கு 1 (L1)' என்ற சொல் தயாரிப்பு எத்திரியம் பிணையமான முதன்மை வலைப்பின்னலுக்குப் பயன்படுத்தப்படுகிறது.
'அடுக்கு 2 (L2)' என்ற சொல் ரோலப் அல்லது பாதுகாப்பிற்காக L1-ஐச் சார்ந்திருக்கும் ஆனால் அதன் பெரும்பாலான செயலாக்கத்தைப் புறச்சங்கிலியில் (offchain) செய்யும் வேறு எந்த அமைப்புக்கும் பயன்படுத்தப்படுகிறது.

## L2 பரிவர்த்தனைகளின் செலவை நாம் எவ்வாறு மேலும் குறைக்கலாம்? {#how-can-we-further-reduce-the-cost-of-l2-transactions}

[Optimistic ரோலப்கள்](/developers/docs/scaling/optimistic-rollups) ஒவ்வொரு வரலாற்றுப் பரிவர்த்தனையின் பதிவையும் பாதுகாக்க வேண்டும், இதனால் எவரும் அவற்றைச் சரிபார்த்து தற்போதைய நிலை (state) சரியானது என்பதை உறுதிப்படுத்த முடியும்.
இந்தக் கட்டுரை எழுதப்பட்டபோது, எத்தேரியம் முதன்மை வலைப்பின்னலில் தரவைப் பெறுவதற்கான மலிவான வழி அதை அழைப்புத் தரவாக (calldata) எழுதுவதாகும்.
இந்தத் தீர்வு [Optimism](https://docs.optimism.io/op-stack/protocol/overview) மற்றும் [Arbitrum](https://docs.arbitrum.io/welcome/arbitrum-gentle-introduction) ஆகிய இரண்டாலும் தேர்ந்தெடுக்கப்பட்டது.
டென்குன் மேம்படுத்தலுக்குப் பிறகு (மார்ச் 2024), ரோலப்கள் இந்தத் தரவை [தரவுத் திரளைகளில் (blobs)](/roadmap/danksharding/) இடுகையிடலாம், இவை மிகவும் மலிவானவை.

### L2 பரிவர்த்தனைகளின் செலவு {#cost-of-l2-transactions}

L2 பரிவர்த்தனைகளின் செலவு இரண்டு கூறுகளைக் கொண்டுள்ளது:

1. L2 செயலாக்கம், இது பொதுவாக மிகவும் மலிவானது
2. L1 சேமிப்பகம், இது முதன்மை வலைப்பின்னல் எரிவாயு செலவுகளுடன் இணைக்கப்பட்டுள்ளது

2022 இல் நான் இந்தக் கட்டுரையை எழுதியபோது, Optimism-இல் L2 எரிவாயுவின் செலவு 0.001 [Gwei](/developers/docs/gas/#what-is-gas) ஆக இருந்தது.
மறுபுறம், L1 எரிவாயுவின் செலவு தோராயமாக 40 Gwei ஆக இருந்தது.

ஒரு பைட் அழைப்புத் தரவின் செலவு 4 எரிவாயு (அது பூஜ்ஜியமாக இருந்தால்) அல்லது 16 எரிவாயு (அது வேறு எந்த மதிப்பாக இருந்தாலும்) ஆகும்.
EVM-இல் மிகவும் விலையுயர்ந்த செயல்பாடுகளில் ஒன்று சேமிப்பகத்தில் எழுதுவதாகும்.
L2-இல் சேமிப்பகத்தில் 32-பைட் சொல்லை எழுதுவதற்கான அதிகபட்ச செலவு 22100 எரிவாயு ஆகும். அந்த நேரத்தில், இது 22.1 Gwei ஆக இருந்தது.
எனவே நாம் அழைப்புத் தரவின் ஒரு பூஜ்ஜிய பைட்டைச் சேமிக்க முடிந்தால், நாம் சேமிப்பகத்தில் சுமார் 200 பைட்டுகளை எழுத முடியும், மேலும் லாபகரமாக இருக்க முடியும்.

#### 2024 இல் L2 செலவுகள் எவ்வாறு மாறின {#how-l2-costs-changed-in-2024}

இந்தக் கட்டுரை எழுதப்பட்டதிலிருந்து OP Stack [L1 தரவுக் கட்டணச்](https://docs.optimism.io/op-stack/transactions/fees#l1-data-fee) சூத்திரம் இரண்டு முறை மாறியுள்ளது:

- [Ecotone மேம்படுத்தலுடன்](https://docs.optimism.io/op-stack/transactions/fees#ecotone) (மார்ச் 2024), OP Stack சங்கிலிகள் பரிவர்த்தனைத் தரவைத் தரவுத் திரளைகளில் இடுகையிடத் தொடங்கின, இவை தனி (மற்றும் பொதுவாக மிகவும் குறைவான) தரவுத் திரளை அடிப்படை கட்டணத்தால் மதிப்பிடப்படுகின்றன.
- [Fjord மேம்படுத்தலுடன்](https://docs.optimism.io/op-stack/transactions/fees#fjord) (ஜூலை 2024), L1 தரவுக் கட்டணமானது [FastLZ](https://github.com/ariya/FastLZ) சுருக்கத்திற்குப் பிறகு பரிவர்த்தனையின் அளவின் மதிப்பீட்டை அடிப்படையாகக் கொண்டது, ஒரு பரிவர்த்தனைக்குக் குறைந்தபட்சம் 100 பைட்டுகள் இருக்கும் ([விவரக்குறிப்பைப் பார்க்கவும்](https://specs.optimism.io/protocol/fjord/exec-engine.html)).

இது இந்தக் கட்டுரையின் மீதமுள்ள பகுப்பாய்வை மூன்று வழிகளில் மாற்றுகிறது:

1. பூஜ்ஜிய பைட்டுகள் நன்றாகச் சுருக்கப்படுகின்றன, எனவே அவை கிட்டத்தட்ட இலவசம்.
   கீழே உள்ள ஒரு பைட்டுக்கு 4 மற்றும் 16 எரிவாயு புள்ளிவிவரங்கள் L1 அழைப்புத் தரவின் செலவாகும், இன்று OP Stack சங்கிலியில் பரிவர்த்தனைத் தரவிற்காக நீங்கள் செலுத்துவது அல்ல.
2. குறைந்தபட்சம் 100-பைட்டுக்குக் கீழே, குறுகிய அழைப்புத் தரவு எதையும் சேமிக்காது.
   எடுத்துக்காட்டாக, அக்டோபர் 2026 இல் OP முதன்மை வலைப்பின்னலில் ஒரு நிலையான ERC-20 `transfer` (68 பைட்டுகள் அழைப்புத் தரவு) மற்றும் இந்தக் கட்டுரையில் உள்ள 23-பைட் குறுகிய பதிப்பு ஆகியவை சரியாக அதே L1 தரவுக் கட்டணத்தை, குறைந்தபட்சமாக, சுமார் 1 Gwei (10<sup>-9</sup> ETH) செலுத்தியிருக்கும்.
3. தரவுத் திரளை இடம் மலிவானது என்பதால், L2 செயலாக்கக் கட்டணம் இப்போது பெரும்பாலும் L1 தரவுக் கட்டணத்தை விட அதிகமாக உள்ளது.
   0.001 Gwei என்ற L2 எரிவாயு விலையில், 1000 எரிவாயுவின் செலவு 1 Gwei ஆகும், இது முழு L1 தரவுக் கட்டணத்திற்கும் சமம், எனவே ஒரு பதிலி ஒப்பந்தத்தின் மூலம் செல்வதற்கான கூடுதல் செயலாக்க எரிவாயு அது சேமிக்கும் பைட்டுகளை விட அதிக செலவாகும்.

கொள்கை இன்னும் பொருந்தும்: குறைவான சுருக்கப்பட்ட பைட்டுகள் என்றால் குறைந்த L1 தரவுக் கட்டணம்.
நன்றாகச் சுருக்கப்படாத நிறையத் தரவுகளைக் கொண்ட பரிவர்த்தனைகளுக்கும், சங்கிலிகளிலும் அல்லது L1 தரவு விலை உயர்ந்ததாக இருக்கும் நேரங்களிலும் குறுகிய ABI-கள் மிகவும் அர்த்தமுள்ளதாக இருக்கும்.
ஒரு குறிப்பிட்ட பரிவர்த்தனை என்ன செலுத்தும் என்பதைப் பார்க்க, கையொப்பமிடப்படாத பரிவர்த்தனையுடன் [`GasPriceOracle` முன்-வரிசைப்படுத்தலில் (predeploy)](https://specs.optimism.io/protocol/predeploys.html#gaspriceoracle) `getL1Fee`-ஐ அழைக்கவும்.
எடுத்துக்காட்டாக, [Foundry](https://getfoundry.sh/introduction/installation/)-இன் `cast`-ஐப் பயன்படுத்துதல்:

```sh
TX=$(cast mktx --raw-unsigned --from <your address> --chain 10 --nonce 0 --gas-limit 100000 \
  --priority-gas-price 1000000 --gas-price 1000000 <destination address> <calldata>)
cast call 0x420000000000000000000000000000000000000F "getL1Fee(bytes)(uint256)" $TX --rpc-url https://mainnet.optimism.io
```

முடிவு Wei-இல் உள்ளது.

### ABI {#the-abi}

பெரும்பாலான பரிவர்த்தனைகள் வெளிப்புறமாக சொந்தமான கணக்கிலிருந்து (EOA) ஒரு ஒப்பந்தத்தை அணுகுகின்றன.
பெரும்பாலான ஒப்பந்தங்கள் Solidity-இல் எழுதப்பட்டுள்ளன, மேலும் அவற்றின் தரவுப் புலத்தை [பயன்பாட்டு இரும இடைமுகத்தின் (ABI)](https://docs.soliditylang.org/en/latest/abi-spec.html#formal-specification-of-the-encoding) படி விளக்குகின்றன.

இருப்பினும், ABI ஆனது L1-க்காக வடிவமைக்கப்பட்டது, அங்கு ஒரு பைட் அழைப்புத் தரவின் செலவு தோராயமாக நான்கு எண்கணிதச் செயல்பாடுகளுக்குச் சமமாக இருக்கும், L2-க்காக அல்ல, அங்கு (2022 விலைகளில்) ஒரு பைட் அழைப்புத் தரவின் செலவு ஆயிரத்திற்கும் மேற்பட்ட எண்கணிதச் செயல்பாடுகளை விட அதிகமாக இருக்கும்.
அழைப்புத் தரவு இவ்வாறு பிரிக்கப்பட்டுள்ளது:

| பிரிவு | நீளம் | பைட்டுகள் | வீணான பைட்டுகள் | வீணான எரிவாயு | தேவையான பைட்டுகள் | தேவையான எரிவாயு |
| ------------------- | -----: | ----: | -----------: | ---------: | --------------: | ------------: |
| செயல்பாட்டுத் தேர்வி (Function selector) |      4 |   0-3 |            3 |         48 |               1 |            16 |
| பூஜ்ஜியங்கள் |     12 |  4-15 |           12 |         48 |               0 |             0 |
| இலக்கு முகவரி |     20 | 16-35 |            0 |          0 |              20 |           320 |
| தொகை |     32 | 36-67 |           17 |         68 |              15 |           240 |
| மொத்தம் |     68 |       |              |        164 |                 |           576 |

விளக்கம்:

- **செயல்பாட்டுத் தேர்வி**: ஒப்பந்தத்தில் 256-க்கும் குறைவான செயல்பாடுகள் உள்ளன, எனவே அவற்றை ஒரு பைட்டைக் கொண்டு வேறுபடுத்தலாம்.
  இந்த பைட்டுகள் பொதுவாகப் பூஜ்ஜியமற்றவை, எனவே [பதினாறு எரிவாயு செலவாகும்](https://eips.ethereum.org/EIPS/eip-2028).
- **பூஜ்ஜியங்கள்**: இந்த பைட்டுகள் எப்போதும் பூஜ்ஜியமாக இருக்கும், ஏனெனில் இருபது-பைட் முகவரியை வைத்திருக்க முப்பத்திரண்டு-பைட் சொல் தேவையில்லை.
  பூஜ்ஜியத்தைக் கொண்டிருக்கும் பைட்டுகளுக்கு நான்கு எரிவாயு செலவாகும் ([மஞ்சள் அறிக்கையைப் பார்க்கவும்](https://ethereum.github.io/yellowpaper/paper.pdf), பிற்சேர்க்கை G,
  பக்கம் 27, `G`<sub>`txdatazero`</sub>-க்கான மதிப்பு).
- **தொகை**: இந்த ஒப்பந்தத்தில் `decimals` பதினெட்டு (சாதாரண மதிப்பு) என்றும், நாம் பரிமாற்றம் செய்யும் வில்லைகளின் அதிகபட்சத் தொகை 10<sup>18</sup> ஆக இருக்கும் என்றும் கருதினால், நமக்கு அதிகபட்சத் தொகையாக 10<sup>36</sup> கிடைக்கும்.
  256<sup>15</sup> &gt; 10<sup>36</sup>, எனவே பதினைந்து பைட்டுகள் போதுமானவை.

L1-இல் 164 எரிவாயு வீணாவது பொதுவாகப் புறக்கணிக்கத்தக்கது. ஒரு பரிவர்த்தனைக்குக் குறைந்தது [21,000 எரிவாயு](https://yakkomajuri.medium.com/blockchain-definition-of-the-week-ethereum-gas-2f976af774ed) செலவாகும், எனவே கூடுதல் 0.8% ஒரு பொருட்டல்ல.
இருப்பினும், 2022 இல் L2-இல், நிலைமை வேறுபட்டது. பரிவர்த்தனையின் கிட்டத்தட்ட முழுச் செலவும் அதை L1-இல் எழுதுவதாகவே இருந்தது.
பரிவர்த்தனை அழைப்புத் தரவுக்குக் கூடுதலாக, 109 பைட்டுகள் பரிவர்த்தனைத் தலைப்பு (இலக்கு முகவரி, கையொப்பம் போன்றவை) உள்ளன.
எனவே மொத்தச் செலவு `109*16+576+164=2484` ஆகும், மேலும் அதில் சுமார் 6.6%-ஐ நாம் வீணாக்குகிறோம்.

## இலக்கைக் கட்டுப்படுத்தாதபோது செலவுகளைக் குறைத்தல் {#reducing-costs-when-you-dont-control-the-destination}

இலக்கு ஒப்பந்தத்தின் மீது உங்களுக்குக் கட்டுப்பாடு இல்லை என்று வைத்துக்கொண்டால், [இதைப் போன்ற](https://github.com/qbzzt/ethereum.org-20220330-shortABI) ஒரு தீர்வை நீங்கள் இன்னும் பயன்படுத்தலாம்.

அதை இயக்க, உங்களுக்கு [Node.js](https://nodejs.org/) மற்றும் git தேவை:

```sh
git clone https://github.com/qbzzt/ethereum.org-20220330-shortABI.git
cd ethereum.org-20220330-shortABI
npm install
npx hardhat test
```

சோதனையானது Hardhat-இன் உள்ளமைக்கப்பட்ட உள்ளூர் பிணையத்தில் ஒப்பந்தங்களைப் பயன்படுத்துகிறது, எனவே உங்களுக்கு எந்த ETH-உம் தேவையில்லை.
களஞ்சியம் Hardhat 2.9-ஐப் பயன்படுத்துகிறது, எனவே Node.js-இன் தற்போதைய பதிப்புகளில் உங்கள் Node.js பதிப்பு ஆதரிக்கப்படவில்லை என்று அது எச்சரிக்கிறது, ஆனால் சோதனை இன்னும் தேர்ச்சி பெறுகிறது.

### Token.sol {#token-sol}

[இதுதான் இலக்கு ஒப்பந்தம்](https://github.com/qbzzt/ethereum.org-20220330-shortABI/blob/master/contracts/Token.sol).
இது ஒரு கூடுதல் அம்சத்தைக் கொண்ட நிலையான ERC-20 ஒப்பந்தமாகும்.
இந்த `faucet` செயல்பாடு எந்தவொரு பயனரும் பயன்படுத்துவதற்குச் சில வில்லைகளைப் பெற அனுமதிக்கிறது.
இது ஒரு தயாரிப்பு ERC-20 ஒப்பந்தத்தைப் பயனற்றதாக்கும், ஆனால் சோதனையை எளிதாக்குவதற்கு மட்டுமே ERC-20 இருக்கும்போது இது வேலையை எளிதாக்குகிறது.

```solidity
    /**
     * @dev அழைப்பாளருக்கு விளையாடுவதற்கு 1000 வில்லைகளை வழங்குகிறது
     */
    function faucet() external {
        _mint(msg.sender, 1000);
    }   // function faucet
```

### CalldataInterpreter.sol {#calldatainterpreter-sol}

[குறுகிய அழைப்புத் தரவுடன் பரிவர்த்தனைகள் அழைக்க வேண்டிய ஒப்பந்தம் இதுவாகும்](https://github.com/qbzzt/ethereum.org-20220330-shortABI/blob/master/contracts/CalldataInterpreter.sol).
அதை வரியாகப் பார்ப்போம்.

```solidity
//SPDX-License-Identifier: Unlicense
pragma solidity ^0.8.0;


import { OrisUselessToken } from "./Token.sol";
```

அதை எவ்வாறு அழைப்பது என்பதை அறிய நமக்கு வில்லைச் செயல்பாடு தேவை.

```solidity
contract CalldataInterpreter {

    OrisUselessToken public immutable token;
```

நாம் பதிலியாக இருக்கும் வில்லையின் முகவரி.

```solidity

    /**
     * @dev வில்லை முகவரியைக் குறிப்பிடவும்
     * @param tokenAddr_ ERC-20 ஒப்பந்த முகவரி
     */
    constructor(
        address tokenAddr_
    )  {
        token = OrisUselessToken(tokenAddr_);
    }   // ஆக்கி
```

நாம் குறிப்பிட வேண்டிய ஒரே அளவுரு வில்லை முகவரி மட்டுமே.

```solidity
    function calldataVal(uint startByte, uint length)
        private pure returns (uint) {
```

அழைப்புத் தரவிலிருந்து ஒரு மதிப்பைப் படிக்கவும்.

```solidity
        uint _retVal;

        require(length < 0x21,
            "calldataVal length limit is 32 bytes");

        require(length + startByte <= msg.data.length,
            "calldataVal trying to read beyond calldatasize");
```

நாம் ஒரு 32-பைட் (256-பிட்) சொல்லை நினைவகத்தில் ஏற்றி, நமக்குத் தேவையான புலத்தின் பகுதியாக இல்லாத பைட்டுகளை அகற்றப் போகிறோம்.
இந்த வழிமுறை 32 பைட்டுகளுக்கு மேல் உள்ள மதிப்புகளுக்கு வேலை செய்யாது, மேலும் நிச்சயமாக அழைப்புத் தரவின் முடிவைத் தாண்டி நம்மால் படிக்க முடியாது.
L1-இல் எரிவாயுவைச் சேமிக்க இந்தச் சோதனைகளைத் தவிர்க்க வேண்டியிருக்கலாம், ஆனால் L2-இல் எரிவாயு மிகவும் மலிவானது, இது நாம் நினைக்கும் எந்தவொரு சரிபார்ப்புகளையும் செயல்படுத்துகிறது.

```solidity
        assembly {
            _retVal := calldataload(startByte)
        }
```

அழைப்பிலிருந்து தரவை `fallback()`-க்கு நகலெடுத்திருக்கலாம் (கீழே காண்க), ஆனால் EVM-இன் அசெம்பிளி மொழியான [Yul](https://docs.soliditylang.org/en/v0.8.12/yul.html)-ஐப் பயன்படுத்துவது எளிதானது.

இங்கே நாம் `startByte` முதல் `startByte+31` வரையிலான பைட்டுகளை அடுக்கில் படிக்க [CALLDATALOAD செயல்பாட்டுக் குறியீட்டைப்](https://www.evm.codes/#35) பயன்படுத்துகிறோம்.
பொதுவாக, Yul-இல் ஒரு செயல்பாட்டுக் குறியீட்டின் தொடரியல் `<opcode name>(<first stack value, if any>,<second stack value, if any>...)` ஆகும்.

```solidity

        _retVal = _retVal >> (256-length*8);
```

மிக முக்கியமான `length` பைட்டுகள் மட்டுமே புலத்தின் ஒரு பகுதியாகும், எனவே மற்ற மதிப்புகளை அகற்ற நாம் [வலது-நகர்வு (right-shift)](https://en.wikipedia.org/wiki/Logical_shift) செய்கிறோம்.
இது மதிப்பைப் புலத்தின் வலதுபுறத்திற்கு நகர்த்துவதன் கூடுதல் நன்மையைக் கொண்டுள்ளது, எனவே இது மதிப்பு பெருக்கல் 256<sup>ஏதோவொன்று</sup> என்பதை விட மதிப்பு மட்டுமே ஆகும்.

```solidity

        return _retVal;
    }


    fallback() external {
```

Solidity ஒப்பந்தத்திற்கான அழைப்பு எந்தவொரு செயல்பாட்டுக் கையொப்பங்களுடனும் பொருந்தாதபோது, அது [`fallback()` செயல்பாட்டை](https://docs.soliditylang.org/en/v0.8.12/contracts.html#fallback-function) அழைக்கிறது (ஒன்று இருப்பதாகக் கருதி).
`CalldataInterpreter`-ஐப் பொறுத்தவரை, வேறு எந்த `external` அல்லது `public` செயல்பாடுகளும் இல்லாததால் _எந்தவொரு_ அழைப்பும் இங்கு வருகிறது.

```solidity
        uint _func;

        _func = calldataVal(0, 1);
```

அழைப்புத் தரவின் முதல் பைட்டைப் படிக்கவும், இது செயல்பாட்டை நமக்குக் கூறுகிறது.
ஒரு செயல்பாடு இங்கு கிடைக்காமல் இருப்பதற்கு இரண்டு காரணங்கள் உள்ளன:

1. `pure` அல்லது `view` ஆக இருக்கும் செயல்பாடுகள் நிலையை மாற்றாது மற்றும் எரிவாயு செலவாகாது (புறச்சங்கிலியில் அழைக்கப்படும்போது).
   அவற்றின் எரிவாயு செலவைக் குறைக்க முயற்சிப்பதில் எந்த அர்த்தமும் இல்லை.
2. [`msg.sender`](https://docs.soliditylang.org/en/v0.8.12/units-and-global-variables.html#block-and-transaction-properties)-ஐச் சார்ந்திருக்கும் செயல்பாடுகள்.
   `msg.sender`-இன் மதிப்பு அழைப்பாளராக இல்லாமல், `CalldataInterpreter`-இன் முகவரியாக இருக்கும்.

துரதிர்ஷ்டவசமாக, [ERC-20 விவரக்குறிப்புகளைப் பார்க்கும்போது](https://eips.ethereum.org/EIPS/eip-20), இது `transfer` என்ற ஒரு நிலையான செயல்பாட்டை மட்டுமே விட்டுவிடுகிறது (ஏனெனில் நாம் `transferFrom`-ஐ அழைக்கலாம்).
நமது சோதனை வில்லையில் `faucet`-உம் உள்ளது, இதை நாம் ஆதரிக்க முடியும், ஏனெனில் நம்மை அழைத்தவருக்கு வில்லைகளைத் திரும்பப் பரிமாற்றம் செய்ய முடியும்.

```solidity

        // வில்லையின் நிலையை மாற்றும் முறைகளை அழைக்கவும், இதைப் பயன்படுத்தி
        // அழைப்புத் தரவிலிருந்து தகவல்

        // பாசெட்
        if (_func == 1) {
```

அளவுருக்கள் இல்லாத `faucet()`-க்கான அழைப்பு.

```solidity
            token.faucet();
            token.transfer(msg.sender,
                token.balanceOf(address(this)));
        }
```

நாம் `token.faucet()`-ஐ அழைத்த பிறகு நமக்கு வில்லைகள் கிடைக்கும். இருப்பினும், பதிலி ஒப்பந்தமாக, நமக்கு வில்லைகள் **தேவை** இல்லை.
நம்மை அழைத்த EOA (வெளிப்புறமாக சொந்தமான கணக்கு) அல்லது ஒப்பந்தத்திற்குத் தேவை.
எனவே நம்மை அழைத்தவருக்கு நமது வில்லைகள் அனைத்தையும் பரிமாற்றம் செய்கிறோம்.

```solidity
        // பரிமாற்றம் (அதற்கான அனுமதித்தொகை நம்மிடம் உள்ளது என வைத்துக்கொள்வோம்)
        if (_func == 2) {
```

வில்லைகளைப் பரிமாற்றம் செய்வதற்கு இரண்டு அளவுருக்கள் தேவை: இலக்கு முகவரி மற்றும் தொகை.

```solidity
            token.transferFrom(
```

## இலக்கு ஒப்பந்தத்தை நீங்கள் கட்டுப்படுத்தும்போது செலவைக் குறைத்தல் {#reducing-the-cost-when-you-do-control-the-destination-contract}

இலக்கு ஒப்பந்தத்தின் மீது உங்களுக்குக் கட்டுப்பாடு இருந்தால், `msg.sender` சரிபார்ப்புகளைத் தவிர்க்கும் செயல்பாடுகளை நீங்கள் உருவாக்கலாம், ஏனெனில் அவை அழைப்புத் தரவு மொழிபெயர்ப்பாளரை நம்புகின்றன.
[இது எவ்வாறு செயல்படுகிறது என்பதற்கான எடுத்துக்காட்டை இங்கே, `control-contract` கிளையில் நீங்கள் காணலாம்](https://github.com/qbzzt/ethereum.org-20220330-shortABI/tree/control-contract).
அதை இயக்க, நீங்கள் முன்பு குளோன் செய்த களஞ்சியத்தில் உள்ள அந்தக் கிளைக்கு மாறி, சோதனையை மீண்டும் இயக்கவும்:

```sh
git checkout control-contract
npx hardhat test
```

ஒப்பந்தம் வெளிப்புறப் பரிவர்த்தனைகளுக்கு மட்டுமே பதிலளிப்பதாக இருந்தால், நாம் ஒரு ஒப்பந்தத்தை மட்டுமே வைத்திருப்பதன் மூலம் சமாளிக்க முடியும்.
இருப்பினும், அது [ஒருங்கிணைக்கக்கூடிய தன்மையை (composability)](/developers/docs/smart-contracts/composability/) உடைக்கும்.
சாதாரண ERC-20 அழைப்புகளுக்குப் பதிலளிக்கும் ஒரு ஒப்பந்தத்தையும், குறுகிய அழைப்புத் தரவுடன் பரிவர்த்தனைகளுக்குப் பதிலளிக்கும் மற்றொரு ஒப்பந்தத்தையும் வைத்திருப்பது மிகவும் சிறந்தது.

### Token.sol {#token-sol-2}

இந்த எடுத்துக்காட்டில் நாம் `Token.sol`-ஐ மாற்றலாம்.
பதிலி மட்டுமே அழைக்கக்கூடிய பல செயல்பாடுகளை வைத்திருக்க இது நம்மை அனுமதிக்கிறது.
புதிய பகுதிகள் இங்கே:

```solidity
    // CalldataInterpreter முகவரியைக் குறிப்பிட அனுமதிக்கப்பட்ட ஒரே முகவரி
    address owner;

    // CalldataInterpreter முகவரி
    address proxy = address(0);
```

அங்கீகரிக்கப்பட்ட பதிலியின் அடையாளத்தை ERC-20 ஒப்பந்தம் அறிய வேண்டும்.
இருப்பினும், இந்த மாறியை ஆக்கியில் (constructor) அமைக்க முடியாது, ஏனெனில் அதன் மதிப்பு நமக்கு இன்னும் தெரியாது.
பதிலி அதன் ஆக்கியில் வில்லையின் முகவரியை எதிர்பார்ப்பதால் இந்த ஒப்பந்தம் முதலில் தொடங்கப்படுகிறது.

```solidity
    /**
     * @dev ERC20 ஆக்கியை அழைக்கிறது.
     */
    constructor(
    ) ERC20("Oris useless token-2", "OUT-2") {
        owner = msg.sender;
    }
```

உருவாக்கியவரின் முகவரி (`owner` என அழைக்கப்படுகிறது) இங்கே சேமிக்கப்படுகிறது, ஏனெனில் பதிலியை அமைக்க அனுமதிக்கப்பட்ட ஒரே முகவரி அதுதான்.

```solidity
    /**
     * @dev பதிலாளுக்கான (CalldataInterpreter) முகவரியை அமைக்கவும்.
     * உரிமையாளரால் ஒரு முறை மட்டுமே அழைக்கப்பட முடியும்
     */
    function setProxy(address _proxy) external {
        require(msg.sender == owner, "Can only be called by owner");
        require(proxy == address(0), "Proxy is already set");

        proxy = _proxy;
    }    // function setProxy
```

பதிலிக்குச் சிறப்புரிமை அணுகல் உள்ளது, ஏனெனில் அது பாதுகாப்புச் சரிபார்ப்புகளைத் தவிர்க்க முடியும்.
பதிலியை நாம் நம்பலாம் என்பதை உறுதிப்படுத்த, `owner`-ஐ மட்டுமே இந்தச் செயல்பாட்டை அழைக்க அனுமதிக்கிறோம், அதுவும் ஒரு முறை மட்டுமே.
ஒருமுறை `proxy` உண்மையான மதிப்பைப் (பூஜ்ஜியம் அல்ல) பெற்றவுடன், அந்த மதிப்பை மாற்ற முடியாது, எனவே உரிமையாளர் மோசடி செய்ய முடிவு செய்தாலும் அல்லது அதற்கான நினைவூட்டி (mnemonic) வெளிப்படுத்தப்பட்டாலும், நாம் இன்னும் பாதுகாப்பாகவே இருக்கிறோம்.

```solidity
    /**
     * @dev சில செயற்கூறுகள் பதிலாளால் மட்டுமே அழைக்கப்படலாம்.
     */
    modifier onlyProxy {
```

```solidity

```

இல்லையெனில், `revert`.

```solidity

    }
```

```solidity

    function transferProxy(address from, address to, uint256 amount)

    function approveProxy(address from, address spender, uint256 amount)

    function transferFromProxy(
```

இவை பொதுவாக வில்லைகளைப் பரிமாற்றம் செய்யும் அல்லது அனுமதித்தொகையை அங்கீகரிக்கும் நிறுவனத்திடமிருந்து நேரடியாகச் செய்தி (message) வர வேண்டிய மூன்று செயல்பாடுகளாகும்.
இங்கே இந்தச் செயல்பாடுகளின் பதிலிப் பதிப்பு நம்மிடம் உள்ளது, இது:

1. `onlyProxy()` மூலம் மாற்றியமைக்கப்பட்டுள்ளது, எனவே வேறு எவரும் அவற்றைக் கட்டுப்படுத்த அனுமதிக்கப்பட மாட்டார்கள்.
2. பொதுவாக `msg.sender` ஆக இருக்கும் முகவரியைக் கூடுதல் அளவுருவாகப் பெறுகிறது.

### CalldataInterpreter.sol {#calldatainterpreter-sol-2}

பதிலிச் செயல்பாடுகள் `msg.sender` அளவுருவைப் பெறுகின்றன மற்றும் `transfer`-க்கு அனுமதித்தொகை தேவையில்லை என்பதைத் தவிர, அழைப்புத் தரவு மொழிபெயர்ப்பாளர் மேலே உள்ளதைப் போலவே இருக்கும்.

```solidity
        // பரிமாற்றம் (அனுமதித்தொகை தேவையில்லை)
        if (_func == 2) {
            token.transferProxy(
                msg.sender,
                address(uint160(calldataVal(1, 20))),
                calldataVal(21, 2)
            );
        }

        // approve
        if (_func == 3) {
            token.approveProxy(
                msg.sender,
                address(uint160(calldataVal(1, 20))),
                calldataVal(21, 2)
            );
        }

        // transferFrom
        if (_func == 4) {
            token.transferFromProxy(
                msg.sender,
                address(uint160(calldataVal( 1, 20))),
                address(uint160(calldataVal(21, 20))),
                calldataVal(41, 2)
            );
        }
```

### Test.js {#test-js-2}

முந்தைய சோதனைக் குறியீட்டிற்கும் இதற்கும் இடையே சில மாற்றங்கள் உள்ளன.

```js
const Cdi = await ethers.getContractFactory("CalldataInterpreter")
const cdi = await Cdi.deploy(token.address)
await cdi.deployed()
await token.setProxy(cdi.address)
```

எந்தப் பதிலியை நம்ப வேண்டும் என்பதை ERC-20 ஒப்பந்தத்திற்கு நாம் கூற வேண்டும்

```js
console.log("CalldataInterpreter addr:", cdi.address)

// அனுமதித்தொகைகளைச் சரிபார்க்க இரண்டு கையொப்பமிடுபவர்கள் தேவை
const signers = await ethers.getSigners()
const signer = signers[0]
const poorSigner = signers[1]
```

`approve()` மற்றும் `transferFrom()`-ஐச் சரிபார்க்க நமக்கு இரண்டாவது கையொப்பமிடுபவர் தேவை.
இது நமது வில்லைகள் எதையும் பெறாததால் (நிச்சயமாக இதற்கு ETH தேவை) இதை `poorSigner` என்று அழைக்கிறோம்.

```js
// வில்லைகளைப் பரிமாற்றவும்
const destAddr = "0xf5a6ead936fb47f342bb63e676479bddf26ebe1d"
const transferTx = {
  to: cdi.address,
  data: "0x02" + destAddr.slice(2, 42) + "0100",
}
await (await signer.sendTransaction(transferTx)).wait()
```

ERC-20 ஒப்பந்தம் பதிலியை நம்புவதால் (`cdi`), பரிமாற்றங்களைச் செய்ய நமக்கு அனுமதித்தொகை தேவையில்லை.

```js
// ஒப்புதல் மற்றும் transferFrom
const approveTx = {
  to: cdi.address,
  data: "0x03" + poorSigner.address.slice(2, 42) + "00FF",
}
await (await signer.sendTransaction(approveTx)).wait()

const destAddr2 = "0xE1165C689C0c3e9642cA7606F5287e708d846206"

const transferFromTx = {
  to: cdi.address,
  data: "0x04" + signer.address.slice(2, 42) + destAddr2.slice(2, 42) + "00FF",
}
await (await poorSigner.sendTransaction(transferFromTx)).wait()

// approve / transferFrom இணைப்பு சரியாகச் செய்யப்பட்டதா எனச் சரிபார்க்கவும்
expect(await token.balanceOf(destAddr2)).to.equal(255)
```

இரண்டு புதிய செயல்பாடுகளைச் சோதிக்கவும்.
`transferFromTx`-க்கு இரண்டு முகவரி அளவுருக்கள் தேவை என்பதை நினைவில் கொள்ளவும்: அனுமதித்தொகையை வழங்குபவர் மற்றும் பெறுபவர்.
