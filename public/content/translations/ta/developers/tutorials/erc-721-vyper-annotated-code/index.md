## அறிமுகம் {#introduction}

[ERC-721](/developers/docs/standards/tokens/erc-721/) தரநிலையானது பதிலீடு செய்ய முடியாத டோக்கன்களின் (NFT) உரிமையைக் கொண்டிருக்கப் பயன்படுகிறது.
[ERC-20](/developers/docs/standards/tokens/erc-20/) வில்லைகள் ஒரு பண்டமாகச் செயல்படுகின்றன, ஏனெனில் தனிப்பட்ட வில்லைகளுக்கு இடையே எந்த வித்தியாசமும் இல்லை.
அதற்கு மாறாக, ERC-721 வில்லைகள் ஒரே மாதிரியான ஆனால் முற்றிலும் ஒன்றல்லாத சொத்துகளுக்காக வடிவமைக்கப்பட்டுள்ளன, எடுத்துக்காட்டாக வெவ்வேறு [பூனை கார்ட்டூன்கள்](https://www.cryptokitties.co/)
அல்லது வெவ்வேறு ரியல் எஸ்டேட் சொத்துகளின் பத்திரங்கள்.

இந்தக் கட்டுரையில் நாம் [ரியுயா நகமுராவின் ERC-721 ஒப்பந்தத்தை](https://github.com/vyperlang/vyper/blob/master/examples/tokens/ERC721.vy) பகுப்பாய்வு செய்வோம்.
இந்த ஒப்பந்தம் [Vyper](https://vyper.readthedocs.io/en/latest/index.html)-இல் எழுதப்பட்டுள்ளது, இது Solidity-ஐ விட பாதுகாப்பற்ற குறியீட்டை எழுதுவதைக் கடினமாக்கும் வகையில் வடிவமைக்கப்பட்ட Python போன்ற ஒப்பந்த மொழியாகும்.

## ஒப்பந்தம் {#contract}

```python
#pragma version >0.3.10
```

`#pragma version` வரியானது, ஒப்பந்தம் எந்த Vyper பதிப்புகளுக்காக எழுதப்பட்டுள்ளது என்பதை கம்பைலருக்குத் தெரிவிக்கிறது. `>0.3.10` ஆனது 0.3.10-ஐ விடப் புதிய எந்த வெளியீட்டையும் ஏற்கும், ஆனால் இந்த ஒப்பந்தத்திற்கு உண்மையில் Vyper 0.4.1 அல்லது அதற்குப் பிந்தைய பதிப்பு தேவை: இது முக்கியச்சொல் வாதங்களுடன் (keyword arguments) நிகழ்வுகளைப் பதிவு செய்கிறது (எடுத்துக்காட்டாக `log IERC721.Transfer(...)`), இது Vyper 0.4.1-இல் சேர்க்கப்பட்ட அம்சமாகும், எனவே இது 0.4.0-இல் கம்பைல் ஆகாது.

```python
# @dev ERC-721 பதிலீடு செய்ய முடியாத டோக்கன் (NFT) தரநிலையின் செயலாக்கம்.
# @author Ryuya Nakamura (@nrryuya)
# இதிலிருந்து மாற்றியமைக்கப்பட்டது: https://github.com/vyperlang/vyper/blob/de74722bf2d8718cca46902be165f9fe0e3641dd/examples/tokens/ERC721.vy
```

Vyper-இல் உள்ள குறிப்புகள், Python-ஐப் போலவே, ஒரு ஹாஷ் (`#`) குறியீட்டுடன் தொடங்கி வரியின் இறுதி வரை தொடரும். `@<keyword>` உள்ள குறிப்புகள் மனிதர்கள் படிக்கக்கூடிய ஆவணங்களை உருவாக்க [NatSpec](https://vyper.readthedocs.io/en/latest/natspec.html)-ஆல் பயன்படுத்தப்படுகின்றன.

```python
from ethereum.ercs import IERC165
from ethereum.ercs import IERC721

implements: IERC721
implements: IERC165
```

ERC-165 மற்றும் ERC-721 இடைமுகங்கள் Vyper கம்பைலருடன் வருகின்றன, எனவே அவற்றை நாமே எழுதுவதற்குப் பதிலாக `ethereum.ercs` என்பதிலிருந்து இறக்குமதி செய்கிறோம். [ERC-721 இடைமுக வரையறையை நீங்கள் இங்கே காணலாம்](https://github.com/vyperlang/vyper/blob/master/vyper/builtins/interfaces/IERC721.vyi).
`implements:` வரிகள் இந்த ஒப்பந்தம் இரண்டு இடைமுகங்களையும் வழங்குகிறது என்று அறிவிக்கின்றன, மேலும் அவற்றுக்குத் தேவையான ஒவ்வொரு சார்பும் (function) கீழே வரையறுக்கப்பட்டுள்ளதா என்பதை கம்பைலர் சரிபார்க்கிறது.

### ERC721Receiver இடைமுகம் {#receiver-interface}

```python
# safeTransferFrom() ஆல் அழைக்கப்படும் ஒப்பந்தம் இடைமுகம்
interface ERC721Receiver:
    def onERC721Received(
```

ERC-721 இரண்டு வகையான பரிமாற்றங்களை ஆதரிக்கிறது:

- `transferFrom`, இது அனுப்புநரை எந்தவொரு இலக்கு முகவரியையும் குறிப்பிட அனுமதிக்கிறது மற்றும் பரிமாற்றத்திற்கான பொறுப்பை அனுப்புநரிடமே வைக்கிறது. இதன் பொருள் நீங்கள் செல்லுபடியாகாத முகவரிக்கு பரிமாற்றம் செய்யலாம், அவ்வாறு செய்தால் NFT நிரந்தரமாக இழக்கப்படும்.
- `safeTransferFrom`, இது இலக்கு முகவரி ஒரு ஒப்பந்தமா என்பதைச் சரிபார்க்கிறது. அப்படியானால், ERC-721 ஒப்பந்தம் பெறும் ஒப்பந்தத்திடம் NFT-ஐப் பெற விரும்புகிறதா என்று கேட்கும்.

`safeTransferFrom` கோரிக்கைகளுக்குப் பதிலளிக்க, பெறும் ஒப்பந்தம் `ERC721Receiver`-ஐச் செயல்படுத்த வேண்டும்.

```python
            _operator: address,
            _from: address,
```

`_from` முகவரி என்பது வில்லையின் தற்போதைய உரிமையாளர். `_operator` முகவரி என்பது பரிமாற்றத்தைக் கோரியவர் (அனுமதித்தொகைகள் காரணமாக, இவை இரண்டும் ஒன்றாக இருக்க வேண்டியதில்லை). வழக்கப்படி, இந்த ஒப்பந்தத்தில் உள்ள பெரும்பாலான சார்பு அளவுருக்கள் (function parameters) அடிக்கோட்டுடன் (`_`) தொடங்குகின்றன.

```python
            _tokenId: uint256,
```

ERC-721 வில்லை ID-கள் 256 பிட்கள் கொண்டவை. பொதுவாக அவை வில்லை எதைக் குறிக்கிறதோ அதன் விளக்கத்தை ஹாஷ் செய்வதன் மூலம் உருவாக்கப்படுகின்றன.

```python
            _data: Bytes[1024]
```

கோரிக்கையானது 1024 பைட்டுகள் வரையிலான பயனர் தரவைக் கொண்டிருக்கலாம்.

```python
        ) -> bytes4: nonpayable
```

ஒரு ஒப்பந்தம் தற்செயலாக ஒரு பரிமாற்றத்தை ஏற்கும் நிகழ்வுகளைத் தடுக்க, திரும்பப் பெறும் மதிப்பு ஒரு பூலியன் அல்ல, மாறாக ஒரு குறிப்பிட்ட நான்கு-பைட் மதிப்பு, அதாவது `onERC721Received`-இன் சார்புத் தேர்வி (function selector). ஒரு பெறும் ஒப்பந்தம் ஒரு வில்லையை ஏற்கும் போது அதன் சொந்த நிலையை மாற்றக்கூடும் என்பதால், இந்தச் சார்பு `nonpayable` ஆக உள்ளது.

### நிகழ்வுகள் {#events}

தொகுதிச்சங்கிலிக்கு வெளியே உள்ள பயனர்களுக்கும் சேவையகங்களுக்கும் நிகழ்வுகளைத் தெரிவிக்க [நிகழ்வுகள்](/developers/docs/smart-contracts/anatomy/#events-and-logs)
வெளியிடப்படுகின்றன. நிகழ்வுகளின் உள்ளடக்கம் தொகுதிச்சங்கிலியில் உள்ள ஒப்பந்தங்களுக்குக் கிடைக்காது என்பதைக் கவனத்தில் கொள்க. மூன்று ERC-721 நிகழ்வுகள் நாம் இறக்குமதி செய்த `IERC721` இடைமுகத்தால் வரையறுக்கப்பட்டுள்ளன, எனவே இந்த ஒப்பந்தம் அவற்றை தானாகவே அறிவிக்காது; கீழே உள்ள பரிமாற்றச் சார்புகளில் நாம் காணப்போவது போல, இது அவற்றை `log IERC721.<Event>(...)` மூலம் வெளியிடுகிறது.

`Transfer` (`sender`, `receiver`, `token_id`) ஒரு NFT-இன் உரிமையில் ஏற்படும் மாற்றத்தைப் புகாரளிக்கிறது. இது
ERC-20 பரிமாற்ற நிகழ்வைப் போன்றது, ஆனால் நாம் ஒரு தொகைக்குப் பதிலாக `token_id`-ஐப் புகாரளிக்கிறோம். சுழி முகவரி யாருக்கும் சொந்தமானதல்ல, எனவே வழக்கப்படி வில்லைகளின் உருவாக்கம் மற்றும் அழிவைப் புகாரளிக்க அதைப் பயன்படுத்துகிறோம். இதற்கு ஒரு விதிவிலக்கு ஒப்பந்த உருவாக்கம் ஆகும், இதன் போது எந்த எண்ணிக்கையிலான NFT-களையும் `Transfer`-ஐ வெளியிடாமலேயே உருவாக்கி ஒதுக்கலாம்.

ஒரு ERC-721 ஒப்புதல் என்பது ERC-20 அனுமதித்தொகையைப் போன்றது: ஒரு குறிப்பிட்ட முகவரி ஒரு குறிப்பிட்ட வில்லையைப் பரிமாற்றம் செய்ய அனுமதிக்கப்படுகிறது,
மேலும் அந்த அங்கீகரிக்கப்பட்ட முகவரி அமைக்கப்படும்போதோ அல்லது மீண்டும் உறுதிப்படுத்தப்படும்போதோ `Approval` (`owner`, `approved`, `token_id`) வெளியிடப்படுகிறது.
இது ஒப்பந்தங்கள் ஒரு வில்லையை ஏற்கும் போது பதிலளிப்பதற்கான ஒரு வழிமுறையை வழங்குகிறது. ஒப்பந்தங்களால் நிகழ்வுகளைக் கேட்க முடியாது, எனவே
நீங்கள் வில்லையை அவற்றுக்கு மாற்றினால் மட்டுமே அவற்றுக்கு அது "தெரியாது". இந்த வழியில் உரிமையாளர் முதலில் ஒரு ஒப்புதலைச் சமர்ப்பித்து
பின்னர் ஒப்பந்தத்திற்கு ஒரு கோரிக்கையை அனுப்புகிறார்: "வில்லை X-ஐப் பரிமாற்றம் செய்ய நான் உங்களுக்கு ஒப்புதல் அளித்துள்ளேன், தயவுசெய்து ... செய்யுங்கள்". இது
ERC-721 தரநிலையை ERC-20 தரநிலைக்கு ஒத்ததாக மாற்றுவதற்கான ஒரு வடிவமைப்புத் தேர்வாகும். ERC-721 வில்லைகள் பதிலீடு செய்ய முடியாதவை என்பதால், ஒரு
ஒப்பந்தம் வில்லையின் உரிமையைப் பார்ப்பதன் மூலம் ஒரு குறிப்பிட்ட வில்லையைப் பெற்றுள்ளது என்பதையும் அடையாளம் காண முடியும்.

இறுதியாக, ஒரு உரிமையாளருக்கு ஒரு _ஆபரேட்டர்_ (operator) செயல்படுத்தப்படும்போது அல்லது முடக்கப்படும்போது `ApprovalForAll` (`owner`, `operator`, `approved`) வெளியிடப்படுகிறது.
ஒரு கணக்கின் குறிப்பிட்ட வகையைச் சேர்ந்த அனைத்து வில்லைகளையும் (ஒரு குறிப்பிட்ட ஒப்பந்தத்தால் நிர்வகிக்கப்படுபவை) நிர்வகிக்கக்கூடிய ஒரு ஆபரேட்டரைக் கொண்டிருப்பது சில நேரங்களில் பயனுள்ளதாக இருக்கும், இது பவர் ஆஃப் அட்டர்னி (power of attorney) போன்றது. எடுத்துக்காட்டாக, நான் ஆறு மாதங்களாகத் தொடர்புகொள்ளவில்லையா என்பதைச் சரிபார்த்து, அவ்வாறு இருந்தால் எனது சொத்துகளை எனது வாரிசுகளுக்குப் பகிர்ந்தளிக்கும் ஒரு ஒப்பந்தத்திற்கு அத்தகைய அதிகாரத்தை வழங்க நான் விரும்பலாம் (அவர்களில் ஒருவர் அதைக் கேட்டால் மட்டுமே, ஒரு பரிவர்த்தனையால் அழைக்கப்படாமல் ஒப்பந்தங்களால் எதையும் செய்ய முடியாது). ERC-20-இல்
நாம் ஒரு வாரிசு ஒப்பந்தத்திற்கு அதிக அனுமதித்தொகையை வழங்கலாம், ஆனால் ERC-721-க்கு அது வேலை செய்யாது, ஏனெனில் வில்லைகள்
பதிலீடு செய்ய முடியாதவை. இது அதற்குச் சமமானதாகும். `approved` மதிப்பானது, நிகழ்வு ஒரு ஒப்புதலுக்கானதா அல்லது
ஒப்புதலைத் திரும்பப் பெறுவதற்கானதா என்பதை நமக்குத் தெரிவிக்கிறது.

### நிலை மாறிகள் {#state-vars}

இந்த மாறிகள் வில்லைகளின் தற்போதைய நிலையைக் கொண்டுள்ளன: எவை கிடைக்கின்றன மற்றும் அவற்றை யார் வைத்திருக்கிறார்கள். இவற்றில் பெரும்பாலானவை
`HashMap` பொருள்கள், அதாவது [இரண்டு வகைகளுக்கு இடையே இருக்கும் ஒருவழி மேப்பிங்குகள் (unidirectional mappings)](https://vyper.readthedocs.io/en/latest/types.html#mappings).

```python
# @dev NFT ID-யிலிருந்து அதைச் சொந்தமாகக் கொண்ட முகவரிக்கு மேப்பிங் செய்தல்.
idToOwner: HashMap[uint256, address]

# @dev NFT ID-யிலிருந்து அங்கீகரிக்கப்பட்ட முகவரிக்கு மேப்பிங் செய்தல்.
idToApprovals: HashMap[uint256, address]
```

எத்திரியத்தில் பயனர் மற்றும் ஒப்பந்த அடையாளங்கள் 160-பிட் முகவரிகளால் குறிக்கப்படுகின்றன. இந்த இரண்டு மாறிகளும்
வில்லை ID-களிலிருந்து அவற்றின் உரிமையாளர்களுக்கும் அவற்றைப் பரிமாற்றம் செய்ய அங்கீகரிக்கப்பட்டவர்களுக்கும் (ஒவ்வொன்றுக்கும் அதிகபட்சம் ஒன்று) மேப் செய்கின்றன. எத்திரியத்தில்,
துவக்கப்படாத தரவு எப்போதும் சுழியாகவே இருக்கும், எனவே உரிமையாளர் அல்லது அங்கீகரிக்கப்பட்ட பரிமாற்றுநர் இல்லை என்றால் அந்த வில்லைக்கான மதிப்பு
சுழியாகும்.

```python
# @dev உரிமையாளர் முகவரியிலிருந்து அவரது வில்லைகளின் எண்ணிக்கைக்கு மேப்பிங் செய்தல்.
ownerToNFTokenCount: HashMap[address, uint256]
```

இந்த மாறி ஒவ்வொரு உரிமையாளருக்குமான வில்லைகளின் எண்ணிக்கையைக் கொண்டுள்ளது. உரிமையாளர்களிடமிருந்து வில்லைகளுக்கு எந்த மேப்பிங்கும் இல்லை, எனவே
ஒரு குறிப்பிட்ட உரிமையாளர் வைத்திருக்கும் வில்லைகளை அடையாளம் காண ஒரே வழி, தொகுதிச்சங்கிலியின் நிகழ்வு வரலாற்றைத் திரும்பிப் பார்த்து
பொருத்தமான `Transfer` நிகழ்வுகளைக் காண்பதுதான். நம்மிடம் அனைத்து NFT-களும் எப்போது உள்ளன என்பதையும், மேலும் பின்னோக்கிப் பார்க்கத் தேவையில்லை என்பதையும் அறிய இந்த மாறியைப் பயன்படுத்தலாம்.

இந்த அல்காரிதம் பயனர் இடைமுகங்கள் மற்றும் வெளிப்புற சேவையகங்களுக்கு மட்டுமே வேலை செய்யும் என்பதைக் கவனத்தில் கொள்க. தொகுதிச்சங்கிலியிலேயே இயங்கும் குறியீட்டால்
கடந்த கால நிகழ்வுகளைப் படிக்க முடியாது.

```python
# @dev உரிமையாளர் முகவரியிலிருந்து ஆபரேட்டர் முகவரிகளின் மேப்பிங்கிற்கு மேப்பிங் செய்தல்.
ownerToOperators: HashMap[address, HashMap[address, bool]]
```

ஒரு கணக்கு ஒன்றுக்கு மேற்பட்ட ஆபரேட்டர்களைக் கொண்டிருக்கலாம். அவற்றைக் கண்காணிக்க ஒரு எளிய `HashMap` போதுமானதல்ல,
ஏனெனில் ஒவ்வொரு திறவுகோலும் ஒரு ஒற்றை மதிப்புக்கு வழிவகுக்கிறது. அதற்குப் பதிலாக, நீங்கள்
`HashMap[address, bool]`-ஐ மதிப்பாகப் பயன்படுத்தலாம். இயல்பாக ஒவ்வொரு முகவரிக்கான மதிப்பும் `False` ஆகும், அதாவது அது
ஒரு ஆபரேட்டர் அல்ல. தேவைக்கேற்ப நீங்கள் மதிப்புகளை `True` என அமைக்கலாம்.

```python
# @dev ஒரு வில்லை அச்சிடக்கூடிய அச்சிடுபவரின் முகவரி
minter: address
```

புதிய வில்லைகள் எப்படியாவது உருவாக்கப்பட வேண்டும். இந்த ஒப்பந்தத்தில் அவ்வாறு செய்ய அனுமதிக்கப்பட்ட ஒரே ஒரு நிறுவனம் உள்ளது, அது
`minter`. எடுத்துக்காட்டாக, ஒரு விளையாட்டுக்கு இது போதுமானதாக இருக்கலாம். பிற நோக்கங்களுக்காக,
மிகவும் சிக்கலான வணிக தர்க்கத்தை (business logic) உருவாக்குவது அவசியமாக இருக்கலாம்.

```python
# @dev ஆதரிக்கப்படும் ERC165 இடைமுக ஐடிகளின் நிலையான பட்டியல்
SUPPORTED_INTERFACES: constant(bytes4[2]) = [
    # ERC165 இன் ERC165 இடைமுக ஐடி
    0x01ffc9a7,
    # ERC721 இன் ERC165 இடைமுக ஐடி
    0x80ac58cd,
]
```

[ERC-165](https://eips.ethereum.org/EIPS/eip-165) ஆனது, பயன்பாடுகள் தன்னுடன் எவ்வாறு தொடர்பு கொள்ளலாம் என்பதையும், அது எந்த ERC-களுக்கு இணங்குகிறது என்பதையும் ஒரு ஒப்பந்தம் வெளிப்படுத்துவதற்கான ஒரு வழிமுறையைக் குறிப்பிடுகிறது. `SUPPORTED_INTERFACES` என்பது இந்த ஒப்பந்தம் இணங்கும் இரண்டு நான்கு-பைட்
இடைமுக ID-களின் நிலையான பட்டியலாகும்: ERC-165 மற்றும் ERC-721.

### சார்புகள் {#functions}

இவைதான் உண்மையில் ERC-721-ஐச் செயல்படுத்தும் சார்புகள்.

#### ஆக்கி {#constructor}

```python
@deploy
def __init__():
```

Vyper-இல், Python-ஐப் போலவே, ஆக்கிச் சார்பு (constructor function) `__init__` என்று அழைக்கப்படுகிறது. இது `@deploy`
அலங்காரத்துடன் (decoration) குறிக்கப்பட்டுள்ளது, அதாவது ஒப்பந்தம் நிலைநிறுத்தப்படும்போது (deployed) இது ஒரு முறை இயங்கும்.

```python
    """
    @dev ஒப்பந்தம் ஆக்கி.
    """
```

Python மற்றும் Vyper-இல், பல வரி சரத்தைக் (multi-line string) குறிப்பிடுவதன் மூலமும் (இது `"""` உடன் தொடங்கி முடிவடையும்),
அதை எந்த வகையிலும் பயன்படுத்தாமலும் நீங்கள் ஒரு குறிப்பை உருவாக்கலாம். இந்தக் குறிப்புகளில்
[NatSpec](https://vyper.readthedocs.io/en/latest/natspec.html)-உம் அடங்கலாம்.

```python
    self.minter = msg.sender
```

நிலை மாறிகளை அணுக நீங்கள் `self.<variable name>`-ஐப் பயன்படுத்துகிறீர்கள் (மீண்டும், Python-இல் உள்ளதைப் போலவே). ஆக்கியானது
ஒப்பந்தத்தை நிலைநிறுத்திய கணக்கை `minter` ஆகப் பதிவு செய்கிறது.

#### காட்சிச் சார்புகள் {#views}

இவை தொகுதிச்சங்கிலியின் நிலையை மாற்றாத சார்புகள், எனவே அவை வெளிப்புறமாக அழைக்கப்பட்டால்
இலவசமாக இயக்கப்படலாம். காட்சிச் சார்புகள் (view functions) ஒரு ஒப்பந்தத்தால் அழைக்கப்பட்டால், அவை இன்னும் ஒவ்வொரு கணுவிலும் (node) இயக்கப்பட வேண்டும், எனவே எரிவாயு செலவாகும்.

```python
@view
@external
```

ஒரு சார்பு வரையறைக்கு முன்னதாக அட் குறியீட்டுடன் (`@`) தொடங்கும் இந்த முக்கியச்சொற்கள் _அலங்காரங்கள்_ (decorations) என்று அழைக்கப்படுகின்றன.
ஒரு சார்பை எந்தச் சூழ்நிலைகளில் அழைக்கலாம் என்பதை அவை குறிப்பிடுகின்றன.

- `@view` இந்தச் சார்பு ஒரு காட்சி (view) என்பதைக் குறிப்பிடுகிறது.
- `@external` இந்தக் குறிப்பிட்ட சார்பை பரிவர்த்தனைகள் மற்றும் பிற ஒப்பந்தங்களால் அழைக்கலாம் என்பதைக் குறிப்பிடுகிறது.

```python
def supportsInterface(interface_id: bytes4) -> bool:
```

Python-க்கு மாறாக, Vyper ஒரு [நிலையான வகை மொழி (static typed language)](https://wikipedia.org/wiki/Type_system#Static_type_checking) ஆகும்.
[தரவு வகையை (data type)](https://vyper.readthedocs.io/en/latest/types.html) அடையாளம் காணாமல் நீங்கள் ஒரு மாறியையோ அல்லது சார்பு அளவுருவையோ அறிவிக்க முடியாது. இந்த நிலையில் உள்ளீட்டு அளவுரு `bytes4` ஆகும், இது ஒரு நான்கு-பைட் மதிப்பு, மற்றும் வெளியீடு ஒரு பூலியன்
மதிப்பாகும்.

```python
    """
    @dev இடைமுக அடையாளம் ERC-165 இல் குறிப்பிடப்பட்டுள்ளது.
    @param interface_id இடைமுகத்தின் ஐடி
    """
    return interface_id in SUPPORTED_INTERFACES
```

`interface_id` ஆனது `SUPPORTED_INTERFACES` பட்டியலில் உள்ள இடைமுக ID-களில் ஒன்றாக இருந்தால் `True`-ஐத் திரும்பப் பெறவும்.

```python
### பார்வை செயல்பாடுகள் ###
```

எத்தேரியம் மெய்நிகர் இயந்திரத்தில் (EVM) மதிப்பு சேமிக்கப்படாத எந்தவொரு சேமிப்பகமும் சுழியாகும்.
`_tokenId`-இல் எந்த வில்லையும் இல்லை என்றால், `self.idToOwner[_tokenId]`-இன் மதிப்பு சுழியாகும். அந்த
நிலையில் சார்பு மீளமைக்கப்படும்.

`getApproved` சுழியைத் திரும்பப் பெற _முடியும்_ என்பதைக் கவனத்தில் கொள்க. வில்லை செல்லுபடியாகும் என்றால் அது `self.idToApprovals[_tokenId]`-ஐத் திரும்பப் பெறும்.
ஒப்புதல் அளிப்பவர் இல்லை என்றால் அந்த மதிப்பு சுழியாகும்.

```python
@view
@external
def isApprovedForAll(_owner: address, _operator: address) -> bool:
    """
    @dev `_owner` க்கு `_operator` அங்கீகரிக்கப்பட்ட ஆபரேட்டரா என்பதைச் சரிபார்க்கும்.
    @param _owner NFTகளைச் சொந்தமாகக் கொண்ட முகவரி.
    @param _operator உரிமையாளரின் சார்பாகச் செயல்படும் முகவரி.
    """
    return (self.ownerToOperators[_owner])[_operator]
```

இந்த ஒப்பந்தத்தில் உள்ள `_owner`-இன் அனைத்து வில்லைகளையும் நிர்வகிக்க `_operator` அனுமதிக்கப்பட்டுள்ளதா என்பதை இந்தச் சார்பு சரிபார்க்கிறது.
பல ஆபரேட்டர்கள் இருக்க முடியும் என்பதால், இது ஒரு இரண்டு நிலை HashMap ஆகும்.

இந்த அலங்காரம், `@internal`, சார்பை அதே ஒப்பந்தத்திற்குள் உள்ள பிற சார்புகளிலிருந்து மட்டுமே அணுக முடியும் என்பதைக் குறிக்கிறது. வழக்கப்படி, இந்தச் சார்புப் பெயர்களும் அடிக்கோட்டுடன் (`_`) தொடங்குகின்றன.

```python
def _isApprovedOrOwner(_spender: address, _tokenId: uint256) -> bool:
    """
    @dev கொடுக்கப்பட்ட செலவிடுபவர் கொடுக்கப்பட்ட வில்லை ஐடியை பரிமாற்றம் செய்ய முடியுமா என்பதை வழங்கும்
    @param spender வினவ வேண்டிய செலவிடுபவரின் முகவரி
    @param tokenId பரிமாற்றம் செய்யப்பட வேண்டிய வில்லையின் uint256 ஐடி
    @return bool msg.sender கொடுக்கப்பட்ட வில்லை ஐடிக்கு அங்கீகரிக்கப்பட்டுள்ளாரா,
        உரிமையாளரின் ஆபரேட்டரா அல்லது வில்லையின் உரிமையாளரா என்பது
    """
    owner: address = self.idToOwner[_tokenId]
    spenderIsOwner: bool = owner == _spender
    spenderIsApproved: bool = _spender == self.idToApprovals[_tokenId]
    spenderIsApprovedForAll: bool = (self.ownerToOperators[owner])[_spender]
    return (spenderIsOwner or spenderIsApproved) or spenderIsApprovedForAll
```

ஒரு முகவரி ஒரு வில்லையைப் பரிமாற்றம் செய்ய அனுமதிக்கப்பட மூன்று வழிகள் உள்ளன:

1. முகவரி வில்லையின் உரிமையாளராக இருப்பது
2. அந்த வில்லையைச் செலவிட முகவரி அங்கீகரிக்கப்பட்டிருப்பது
3. முகவரி வில்லையின் உரிமையாளருக்கான ஆபரேட்டராக இருப்பது

மேலே உள்ள சார்பு நிலையை மாற்றாததால் அது ஒரு காட்சியாக (view) இருக்கலாம். இயக்கச் செலவுகளைக் குறைக்க, ஒரு
காட்சியாக இருக்க _முடியும்_ எந்தவொரு சார்பும் ஒரு காட்சியாக இருக்க _வேண்டும்_.

```python
@internal
def _addTokenTo(_to: address, _tokenId: uint256):
    """
    @dev கொடுக்கப்பட்ட முகவரிக்கு ஒரு NFTயைச் சேர்க்கவும்
         `_tokenId` யாருக்காவது சொந்தமானது எனில் பிழையை எறியும்.
    """
    # `_tokenId` யாருக்காவது சொந்தமானது எனில் பிழையை எறியும்
    assert self.idToOwner[_tokenId] == empty(address)
    # உரிமையாளரை மாற்றவும்
    self.idToOwner[_tokenId] = _to
    # எண்ணிக்கை கண்காணிப்பை மாற்றவும்
    self.ownerToNFTokenCount[_to] += 1


@internal
def _removeTokenFrom(_from: address, _tokenId: uint256):
    """
    @dev கொடுக்கப்பட்ட முகவரியிலிருந்து ஒரு NFTயை அகற்றவும்
         `_from` தற்போதைய உரிமையாளர் இல்லை எனில் பிழையை எறியும்.
    """
    # `_from` தற்போதைய உரிமையாளர் இல்லை எனில் பிழையை எறியும்
    assert self.idToOwner[_tokenId] == _from
    # உரிமையாளரை மாற்றவும்
    self.idToOwner[_tokenId] = empty(address)
    # எண்ணிக்கை கண்காணிப்பை மாற்றவும்
    self.ownerToNFTokenCount[_from] -= 1
```

```python
@internal
def _clearApproval(_owner: address, _tokenId: uint256):
    """
    @dev கொடுக்கப்பட்ட முகவரியின் அங்கீகாரத்தை அழிக்கவும்

    """
    # `_owner` தற்போதைய உரிமையாளர் இல்லை எனில் பிழையை எறியும்
```

தேவைப்பட்டால் மட்டுமே மதிப்பை மாற்றவும். நிலை மாறிகள் சேமிப்பகத்தில் வாழ்கின்றன. சேமிப்பகத்தில் எழுதுவது
EVM (எத்தேரியம் மெய்நிகர் இயந்திரம்) செய்யும் மிகவும் விலையுயர்ந்த செயல்பாடுகளில் ஒன்றாகும் ([எரிவாயு](/developers/docs/gas/) அடிப்படையில்). எனவே, அதைக் குறைப்பது நல்லது, ஏற்கனவே உள்ள
மதிப்பை எழுதுவது கூட அதிக செலவைக் கொண்டுள்ளது.

```python

         `_to` சுழி முகவரி எனில் பிழையை எறியும்.
         `_from` தற்போதைய உரிமையாளர் இல்லை எனில் பிழையை எறியும்.
         `_tokenId` செல்லுபடியாகும் NFT இல்லை எனில் பிழையை எறியும்.
    """
```

வில்லைகளைப் பரிமாற்றம் செய்ய இரண்டு வழிகள் (வழக்கமான மற்றும் பாதுகாப்பான) இருப்பதால் இந்த உள் சார்பை நாங்கள் கொண்டுள்ளோம், ஆனால்
தணிக்கையை எளிதாக்க குறியீட்டில் அதைச் செய்யும் ஒரே ஒரு இடம் மட்டுமே எங்களுக்குத் தேவை.

```python
    # தேவைகளைச் சரிபார்க்கவும்
    assert self._isApprovedOrOwner(_sender, _tokenId)
    # `_to` சுழி முகவரி எனில் பிழையை எறியும்
    assert _to != empty(address)
    # அங்கீகாரத்தை அழிக்கவும். `_from` தற்போதைய உரிமையாளர் இல்லை எனில் பிழையை எறியும்
    self._clearApproval(_from, _tokenId)
    # NFTயை அகற்றவும். `_tokenId` செல்லுபடியாகும் NFT இல்லை எனில் பிழையை எறியும்
    self._removeTokenFrom(_from, _tokenId)
    # NFTயைச் சேர்க்கவும்
    self._addTokenTo(_to, _tokenId)
    # பரிமாற்றம் நிகழ்வைப் பதிவு செய்யவும்
    log IERC721.Transfer(sender=_from, receiver=_to, token_id=_tokenId)
```

முக்கியச்சொல் மூலம் அனுப்புகிறோம்.

```python
    @dev `msg.sender` தற்போதைய உரிமையாளர், அங்கீகரிக்கப்பட்ட ஆபரேட்டர் அல்லது இந்த NFTக்கான அங்கீகரிக்கப்பட்ட
         முகவரியாக இல்லாவிட்டால் பிழையை எறியும்.
         `_from` தற்போதைய உரிமையாளர் இல்லை எனில் பிழையை எறியும்.
         `_to` சுழி முகவரி எனில் பிழையை எறியும்.
         `_tokenId` செல்லுபடியாகும் NFT இல்லை எனில் பிழையை எறியும்.
    @notice `_to` ஆனது NFTகளைப் பெறும் திறன் கொண்டது என்பதை உறுதிப்படுத்துவது அழைப்பாளரின் பொறுப்பாகும், இல்லையெனில்
            அவை நிரந்தரமாக இழக்கப்படலாம்.
    @param _from NFT இன் தற்போதைய உரிமையாளர்.
    @param _to புதிய உரிமையாளர்.
    @param _tokenId பரிமாற்றம் செய்ய வேண்டிய NFT.
    """
    self._transferFrom(_from, _to, _tokenId, msg.sender)
```

இந்தச் சார்பு உங்களை ஒரு தன்னிச்சையான முகவரிக்குப் பரிமாற்றம் செய்ய அனுமதிக்கிறது. முகவரி ஒரு பயனராகவோ அல்லது
வில்லைகளை எவ்வாறு பரிமாற்றம் செய்வது என்று தெரிந்த ஒரு ஒப்பந்தமாகவோ இல்லாவிட்டால், நீங்கள் பரிமாற்றம் செய்யும் எந்த வில்லையும் அந்த முகவரியில் சிக்கிக்கொண்டு பயனற்றதாகிவிடும்.

`IERC721` இடைமுகம் `transferFrom`, `safeTransferFrom` மற்றும்
`approve` ஆகியவற்றைச் செலுத்தக்கூடியதாக (payable) அறிவிப்பதால் `@payable` அலங்காரம் இங்கே உள்ளது, எனவே இடைமுகத்தைச் செயல்படுத்தும் ஒரு ஒப்பந்தம் அந்த கையொப்பங்களுடன் (signatures) பொருந்த வேண்டும்.

முகவரி என்றும் பயனர் வில்லையைப் பயன்படுத்தவோ அல்லது பரிமாற்றம் செய்யவோ முடியும் என்றும் கருதுங்கள். ஆனால் இது உங்களை
ஒரு தவறான பாதுகாப்பு உணர்வுக்குள் தள்ள அனுமதிக்காதீர்கள். யாருக்கும் தனிப்பட்ட திறவுகோல் தெரியாத ஒரு முகவரிக்கு நீங்கள் வில்லைகளைப் பரிமாற்றம் செய்தால், `safeTransferFrom` உடன் கூட நீங்கள் வில்லைகளை இழக்க நேரிடலாம்.

```python
@external
@payable
def approve(_approved: address, _tokenId: uint256):
    """
    @dev ஒரு NFTக்கான அங்கீகரிக்கப்பட்ட முகவரியை அமைக்கவும் அல்லது மீண்டும் உறுதிப்படுத்தவும். சுழி முகவரி அங்கீகரிக்கப்பட்ட முகவரி இல்லை என்பதைக் குறிக்கிறது.
         `msg.sender` தற்போதைய NFT உரிமையாளர் அல்லது தற்போதைய உரிமையாளரின் அங்கீகரிக்கப்பட்ட ஆபரேட்டராக இல்லாவிட்டால் பிழையை எறியும்.
         `_tokenId` செல்லுபடியாகும் NFT இல்லை எனில் பிழையை எறியும். (குறிப்பு: இது EIP இல் எழுதப்படவில்லை)
         `_approved` தற்போதைய உரிமையாளர் எனில் பிழையை எறியும். (குறிப்பு: இது EIP இல் எழுதப்படவில்லை)
    @param _approved கொடுக்கப்பட்ட NFT ஐடிக்கு அங்கீகரிக்கப்பட வேண்டிய முகவரி.
    @param _tokenId அங்கீகரிக்கப்பட வேண்டிய வில்லையின் ஐடி.
    """
    owner: address = self.idToOwner[_tokenId]
    # `_tokenId` செல்லுபடியாகும் NFT இல்லை எனில் பிழையை எறியும்
    assert owner != empty(address)
    # `_approved` தற்போதைய உரிமையாளர் எனில் பிழையை எறியும்
    assert _approved != owner
```

வழக்கப்படி நீங்கள் ஒரு ஒப்புதல் அளிப்பவரைக் கொண்டிருக்க விரும்பவில்லை என்றால், உங்களை அல்ல, சுழி முகவரியை நியமிக்கிறீர்கள்.

```python

    senderIsOwner: bool = self.idToOwner[_tokenId] == msg.sender
    senderIsApprovedForAll: bool = (self.ownerToOperators[owner])[msg.sender]
    assert (senderIsOwner or senderIsApprovedForAll)
```

ஒரு ஒப்புதலை அமைக்க நீங்கள் உரிமையாளராகவோ அல்லது உரிமையாளரால் அங்கீகரிக்கப்பட்ட ஒரு ஆபரேட்டராகவோ இருக்கலாம்.

```python
    @param _approved ஆபரேட்டர்கள் அங்கீகரிக்கப்பட்டால் True, அங்கீகாரத்தை ரத்து செய்ய False.
```

#### புதிய வில்லைகளை அச்சிடுதல் மற்றும் ஏற்கனவே உள்ளவற்றை அழித்தல் {#mint-burn}

ஒப்பந்தத்தை உருவாக்கிய கணக்கு `minter` ஆகும், இது புதிய NFT-களை அச்சிட அங்கீகரிக்கப்பட்ட
சூப்பர் யூசர் (super user) ஆகும். இருப்பினும், ஏற்கனவே உள்ள வில்லைகளை எரிக்க அது கூட அனுமதிக்கப்படவில்லை. உரிமையாளர் அல்லது
உரிமையாளரால் அங்கீகரிக்கப்பட்ட ஒரு நிறுவனம் மட்டுமே அதைச் செய்ய முடியும்.


அச்சிடுபவர் (ERC-721 ஒப்பந்தத்தை உருவாக்கிய கணக்கு) மட்டுமே புதிய வில்லைகளை அச்சிட முடியும். எதிர்காலத்தில் அச்சிடுபவரின் அடையாளத்தை மாற்ற விரும்பினால் இது ஒரு
சிக்கலாக இருக்கலாம். ஒரு தயாரிப்பு ஒப்பந்தத்தில் (production contract), அச்சிடுபவர் தனது அச்சிடும்
சலுகைகளை வேறொருவருக்குப் பரிமாற்றம் செய்ய அனுமதிக்கும் ஒரு சார்பை நீங்கள் கொண்டிருக்க விரும்புவீர்கள்.

```python
    # `_to` சுழி முகவரி எனில் பிழையை எறியும்
    assert _to != empty(address)
    # NFTயைச் சேர்க்கவும். `_tokenId` யாருக்காவது சொந்தமானது எனில் பிழையை எறியும்
    self._addTokenTo(_to, _tokenId)
    log IERC721.Transfer(sender=empty(address), receiver=_to, token_id=_tokenId)
    return True
```

வழக்கப்படி, புதிய வில்லைகளை அச்சிடுதல் என்பது சுழி முகவரியிலிருந்து ஒரு பரிமாற்றமாகக் கணக்கிடப்படுகிறது.

```python

@external
def burn(_tokenId: uint256):
    """
    @dev ஒரு குறிப்பிட்ட ERC721 வில்லையை எரி செய்யும்.
         `msg.sender` தற்போதைய உரிமையாளர், அங்கீகரிக்கப்பட்ட ஆபரேட்டர் அல்லது இந்த NFTக்கான அங்கீகரிக்கப்பட்ட
         முகவரியாக இல்லாவிட்டால் பிழையை எறியும்.
         `_tokenId` செல்லுபடியாகும் NFT இல்லை எனில் பிழையை எறியும்.
    @param _tokenId எரி செய்யப்பட வேண்டிய ERC721 வில்லையின் uint256 ஐடி.
    """
    # தேவைகளைச் சரிபார்க்கவும்
    assert self._isApprovedOrOwner(msg.sender, _tokenId)
    owner: address = self.idToOwner[_tokenId]
    # `_tokenId` செல்லுபடியாகும் NFT இல்லை எனில் பிழையை எறியும்
    assert owner != empty(address)
    self._clearApproval(owner, _tokenId)
    self._removeTokenFrom(owner, _tokenId)
    log IERC721.Transfer(sender=owner, receiver=empty(address), token_id=_tokenId)
```

ஒரு வில்லையைப் பரிமாற்றம் செய்ய அனுமதிக்கப்பட்ட எவரும் அதை எரிக்கவும் அனுமதிக்கப்படுகிறார்கள். எரிப்பது
சுழி முகவரிக்கு மாற்றுவதற்குச் சமமானதாகத் தோன்றினாலும், சுழி முகவரி உண்மையில் வில்லையைப் பெறுவதில்லை. இது
வில்லைக்காகப் பயன்படுத்தப்பட்ட அனைத்துச் சேமிப்பகத்தையும் விடுவிக்க அனுமதிக்கிறது, இது பரிவர்த்தனையின் எரிவாயு செலவைக் குறைக்கலாம்.

## இந்த ஒப்பந்தத்தைப் பயன்படுத்துதல் {#using-contract}

Solidity-க்கு மாறாக, Vyper-இல் மரபுரிமை (inheritance) இல்லை. இது குறியீட்டைத் தெளிவாக்குவதற்கும், எனவே பாதுகாப்பதை எளிதாக்குவதற்கும் செய்யப்பட்ட ஒரு வேண்டுமென்றே வடிவமைப்புத் தேர்வாகும். எனவே உங்கள் சொந்த Vyper ERC-721 ஒப்பந்தத்தை உருவாக்க, நீங்கள் [இந்த ஒப்பந்தத்தை](https://github.com/vyperlang/vyper/blob/master/examples/tokens/ERC721.vy) எடுத்து, நீங்கள் விரும்பும் வணிக தர்க்கத்தைச் செயல்படுத்த அதை மாற்றியமைக்கிறீர்கள்.

## முடிவுரை {#conclusion}

மதிப்பாய்வுக்காக, இந்த ஒப்பந்தத்தில் உள்ள சில மிக முக்கியமான யோசனைகள் இங்கே:

- பாதுகாப்பான பரிமாற்றத்துடன் ERC-721 வில்லைகளைப் பெற, ஒப்பந்தங்கள் `ERC721Receiver` இடைமுகத்தைச் செயல்படுத்த வேண்டும்.
- நீங்கள் பாதுகாப்பான பரிமாற்றத்தைப் பயன்படுத்தினாலும், தனிப்பட்ட திறவுகோல் தெரியாத ஒரு முகவரிக்கு வில்லைகளை அனுப்பினால் அவை இன்னும் சிக்கிக்கொள்ளலாம்.
- ஒரு செயல்பாட்டில் சிக்கல் ஏற்படும்போது, வெறும் தோல்வி மதிப்பைத் திரும்பப் பெறுவதை விட, அழைப்பை `revert` செய்வது (மீளமைப்பது) நல்லது.
- ERC-721 வில்லைகள் ஒரு உரிமையாளரைக் கொண்டிருக்கும்போது மட்டுமே உள்ளன.
- ஒரு NFT-ஐப் பரிமாற்றம் செய்ய அங்கீகரிக்கப்பட மூன்று வழிகள் உள்ளன. நீங்கள் உரிமையாளராக இருக்கலாம், ஒரு குறிப்பிட்ட வில்லைக்கு அங்கீகரிக்கப்பட்டிருக்கலாம் அல்லது உரிமையாளரின் அனைத்து வில்லைகளுக்கும் ஒரு ஆபரேட்டராக இருக்கலாம்.
- கடந்த கால நிகழ்வுகள் தொகுதிச்சங்கிலிக்கு வெளியே மட்டுமே தெரியும். தொகுதிச்சங்கிலிக்குள் இயங்கும் குறியீட்டால் அவற்றைப் பார்க்க முடியாது.
