# Accounts and verified progress

Optional accounts on top of browser progress. Lessons stay open to everyone, signed in or not. Course Mastery needs an account, because it is the one thing an attestation vouches for.

## What the server can and can't vouch for

The repo is public, so lesson answers can't be secret, and the protection doesn't rely on them. It relies on what the server controls:

| Measure                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | Where                                |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| Course Mastery is graded by the server. The questions and options are public; which option is right is not (an encrypted key, see below).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | `src/lib/courses/server/exams.ts`    |
| Answers are saved without a verdict, in the server's shuffled order (going back to change one is allowed), at least `MIN_ANSWER_MS` (3s) apart. The whole check is graded at the end. A pass shows which were right, with each question's explanation and source, never the right options; a fail gives the score only, since naming the misses would hand the next attempt the answers by elimination.                                                                                                                                                                                                                                                                                                                | same                                 |
| `EXAM_ATTEMPTS_PER_DAY` (2) per course per calendar day in the learner's time zone (the browser sends it on every request; the account keeps the last one, `user.time_zone`), and no more than `EXAM_ATTEMPTS_PER_24H` (4) in any 24 hours, so switching zones can't stack days. Starting counts, so walking away mid-check buys no free look; an unfinished attempt resumes. Starting is atomic (an advisory lock per learner and course), so parallel starts can't add attempts. An attempt expires after `EXAM_ATTEMPT_TTL_MS` (2 hours): it still counts for its day but can't be answered, resumed or graded. A key that doesn't cover every question makes Course Mastery unavailable before an attempt is used. | same                                 |
| A lesson counts as verified only with the token from its own start, within a day (`LESSON_TOKEN_TTL_MS`), after `MIN_STEP_MS` per step. Completing deletes the token, and each start sweeps expired ones. Widget answers run in the browser and aren't checked.                                                                                                                                                                                                                                                                                                                                                                                                                                                        | `src/lib/courses/server/lessons.ts`  |
| Browser progress synced to the account is stored `verified: false`. It shows in the UI and never counts toward XP rankings or completion records.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | `src/lib/courses/server/progress.ts` |
| A proof-of-work challenge (ALTCHA PBKDF2, self-hosted, under a second of compute) before any sign-in that can create an account. Each solution is used once: consuming it inserts a row keyed on its signature, so a parallel replay conflicts. Auth requests have generous per-address limits (a school shares one address) in `auth_rate_limit`, keyed by HMAC and swept once a window ends.                                                                                                                                                                                                                                                                                                                         | `src/lib/auth/challenge.ts`          |
| Completion records (planned, below) carry no economic value and live offchain. Anything claimable gets farmed by scripts, whatever the quiz design.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | (planned)                            |

What it can't stop: someone looking answers up (roughly an open-book exam), sharing them, or running several accounts to learn the key. The aim is to make the trophy mean "completed the course and passed its check while signed in", not a proctored exam. The UI says "Completed", never "Certified".

## The answer key

`ExamStep` has no `correct`: the key is `{ [courseId]: { [questionId]: optionIds[] } }`, committed encrypted in `src/data/courses/exam-key.ts` (AES-256-GCM over gzipped JSON), so it ships in the same PR and deploy as the questions it answers. The server decrypts it with `LEARNER_EXAM_KEY_SECRET` (Functions scope, the same value in every context; also in each maintainer's `.env.local`). Without the secret, or with an empty key, Course Mastery shows as unavailable. Locally the plain JSON is `.learner-exam-key.json`, which is gitignored; anyone with the secret can recreate it with `decrypt`.

```bash
pnpm courses:exam-key check [file]    # key vs questions: every question answered, ids valid
pnpm courses:exam-key encrypt [file]  # JSON -> src/data/courses/exam-key.ts (commit it)
pnpm courses:exam-key decrypt         # committed key -> JSON on stdout
```

Adding or changing a mastery question means updating the key file, then `check` and `encrypt`, and committing `exam-key.ts` with the question change. The `strings.spec` key test runs wherever the secret or the key file exists. A leaked secret means a new one: re-encrypt and replace the env var. Answers committed in plain text before the key was encrypted are in git history; that's accepted (the explanations state the answers anyway).

## Accounts

Better Auth (MIT) with the SIWE and passkey plugins, Drizzle and postgres.js. Site-wide, not courses-only: `src/lib/auth/`, `src/lib/db/`, `app/api/auth/`, and the UI in `src/components/Account/` (strings in `component-account.json`). Another feature (quizzes, say) adds its own `quiz_*` tables referencing `user.id` and reuses the sign-in dialog.

- **Sign-in methods**: passkeys and wallets. A passkey can start an account (`registration.requireSession: false`). SIWE signs in by wallet and creates an account for a new one, so adding a backup wallet to a signed-in account is a custom endpoint (`/api/auth/wallet/link`, `wallet-linking.ts`). Backup passkeys use the plugin as-is. Removing the last method is refused (methods count as passkeys plus distinct addresses). Wallets are mainnet only: SIWE messages must be for chain 1, one row per address. The unique indexes on the wallet address and passkey credential id are hand-added to the generated `auth-schema.ts`; keep them when regenerating.
- **Sessions**: rolling, 60 days (`updateAge` a day), so a learner who keeps coming back stays signed in. Deleting the account, adding or removing a passkey or wallet, and signing out other sessions (Better Auth's `/revoke-*`) need a sign-in within Better Auth's `freshAge` (a day); otherwise "Confirm it's you" (`confirm-identity.tsx`) asks for one of the account's own passkeys or wallets, swaps in the fresh session and retries. A session that ends shows as signed out at the next API call or tab focus. The profile lists the account's live sessions from `/sessions/list` (a plugin in `server.ts`: ids and sign-in dates only, since sessions keep no IP address or user agent; Better Auth's own `/list-sessions` returns every session's token, hence its fresh sign-in) and can sign out the others.
- **Privacy**: no email or password; users get placeholder emails (`...@siwe.placeholder.invalid`, `...@passkey.placeholder.invalid`). Sessions store no IP address or user agent. Better Auth telemetry is off. Plain wallets are verified locally; smart accounts (ERC-1271) need an RPC call and only mainnet ones work.
- **Display names** (`user.name`, `src/lib/auth/display-name.ts`): editable on the profile and shown in the course header. Defaults: a wallet account's address (stored whole, shown truncated), a passkey account's random short tag. 2-24 characters of letters, marks, numbers and `. _ ' -` in any script; nothing that reads as a link or email (in case names are ever shown to others); nothing that passes for ethereum.org or its team. The server re-checks on `/update-user` and adds the `obscenity` word filter (English only), also on the name with spaces removed. A refusal's message is the problem code, which the client words.
- **Sign-in dialog**: one screen for signing in or up, with two choices: passkey, then wallet. A new wallet gets an account, since SIWE can't tell the two apart. A passkey sign-in that fails offers to create a passkey, because browsers report "no passkey here" the same as a cancel.
- **Progress sync** (`account-sync.ts`, `src/lib/courses/progress.ts`): besides the lesson and trophy rows, the account keeps the browser's whole progress record (`course_progress_state`: XP, streak, answer history), so a new browser starts where the last one stopped. Sync merges both ways with `mergeProgress`, on the server and in the browser alike: records join keeping the better or later of each, streak runs that overlap or touch join (never "latest wins"), and XP is the higher total plus whatever only the other copy has, so merging twice changes nothing. A signed-in account's streak is worked out on the server from `course_streak_day` (`src/lib/courses/streak.ts`): verified days from lesson and Course Mastery finishes in the learner's time zone, plus the days browsers upload (unverified), so no device can lose or double-count a day. Every signed-in page syncs on load, lessons and Course Mastery included; after a lesson or exam the new record uploads. A failed upload stays marked (`ethereum-org-course-sync-pending`) and retries with backoff, when the browser is back online, when the tab returns and on the next load.
- **Whose progress**: synced progress is tagged with its account. Signing out uploads first and then clears it from the browser (it lives in the account); if the upload fails, the learner picks Try again or Sign out anyway, and unsaved progress stays on the device; deleting the account keeps it as plain browser progress. Signing in to a different account replaces tagged progress instead of merging it, so one browser can't copy an account's progress into another. Untagged progress (from before signing in) joins whichever account signs in.
- **Profile**: shown with progress or an account, so a new account has a profile before its first lesson. `ethereum-org-course-account` in localStorage marks a signed-in browser for the pre-paint check, which can't read the session cookie. Signing out (or resetting with nothing left) goes to the hub.
- **Static pages**: course pages never read the session on the server. The browser reads it through `/api/auth/*`; a 404 there means the deploy has no database, and account UI hides.

## Planned: completion records

Not built; the profile shows "Coming soon". The idea: a downloadable, signed record for each course mastered while signed in, which anyone can verify without trusting the site. A draft (EIP-712 typed data `CourseCompletion { learner, course, score, passedAt }`, signed by a key used for nothing else, verified with any EIP-712 library such as viem's `verifyTypedData`) was removed before merge, because the key comes first. To decide before building it again:

- **Custody**: who generates and holds the signing key, and where it lives (a Netlify secret, or something stronger).
- **Publication**: where the signer's address is published so people can trust it: a page on ethereum.org, the repo, an ENS name.
- **Rotation and revocation**: what happens to existing records if the key changes or leaks.
- **Checking**: a way for anyone, not only developers, to verify a record.
- **Format**: plain EIP-712, or EAS-compatible offchain attestations.

There is no leaderboard. Any future ranking counts verified work only (`verified` rows), never browser imports.

## Problem reports

The lesson footer's Report flag saves to `course_report` (`src/lib/courses/server/reports.ts`), signed in or not, with no user or address: the step, the page's locale, the reason, the learner's picks and a one-line note of up to 300 characters. The answer keeps only the step's own ids, so free text fits only in the capped note. The endpoint takes JSON only, and refuses cross-site requests, so other sites can't file reports through visitors' browsers. Each address (an IPv6 one by its /64) can send 20 an hour, in the auth rate limiter's buckets; a bucket outlives its report by up to an hour, so someone holding both the database and `LEARNER_AUTH_SECRET` could tie a recent report to an address. A Matomo event goes out too when tracking is on, for counts, but ad blockers drop those silently, so the table is the record. If saving fails, the dialog offers a prefilled GitHub issue. Browse with a read-only connection (DBeaver's "Read-only connection") and triage on a writable one: `select * from course_report where status = 'new' order by created_at`, then set `status` to whatever the team settles on.

## Databases per deploy

`pnpm learner-db:prepare` runs before `next build` on Netlify (`src/scripts/learner-db/prepare.ts`) and writes its decision to `.netlify/learner-db.json`, which `next.config.js` inlines:

| Deploy                                      | Database                                                                                                      |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Production; branch deploys `dev`, `staging` | their own, migrated at build; a failed migration fails the deploy                                             |
| Other branch deploys (`feat/*`...)          | none: they'd share dev's credentials and run unmerged migrations on it                                        |
| Deploy previews                             | `preview_<PR>`, created and migrated at build, when the PR touches learner code or has the `preview-db` label |
| Fork previews                               | none: the untrusted deploys policy strips the secrets                                                         |

The provisioner role behind a preview's `LEARNER_DB_MIGRATE_URL` owns every preview database, so it is build-only and marked secret, and the untrusted deploys policy must stay on "Require approval" or "Build without sensitive variables", never "Build without restrictions". Timestamp columns are `timestamptz`, and every connection sets the session `TimeZone` to UTC. The build also creates a `preview_<PR>_app` login that can only read and write its own database, and the runtime connects as it. Its password is an HMAC of the role name with `LEARNER_PREVIEW_DB_SECRET`, since Netlify env vars can't differ per PR. `CREATEDB` isn't limited by name, so only ever create `preview_<PR>` databases.

Migrations run at build while the previous deploy is still live and reading the same database, so once accounts are live a migration must keep the old code working: drop or rename a column one release after the code stops using it.

`.github/workflows/learner-db-previews.yml` drops a preview's database and login when its PR closes, and sweeps daily for any left behind. Env vars and scopes: `.env.example`.

## Local

```bash
pnpm db:up && pnpm db:migrate   # Postgres 18 on port 5433 (LEARNER_DB_PORT)
pnpm db:migrate                 # after pulling new migrations: `pnpm dev` doesn't run them
pnpm db:reset                   # wipe and re-migrate
pnpm db:generate                # migration from a schema change
```

`auth-schema.ts` is generated: after changing the auth config, run `pnpm dlx auth@<better-auth version> generate` against a file exporting `auth = getAuth()`, then Prettier and `pnpm db:generate`.
